# Native review operations

These are the existing review mechanics extracted from the everyday-use skill. Project review-train strategy is not changed by this split.

For routine enrollment and order, read `reviews execution` / `review_execution_read`, then use `reviews queue-add PR --expect-config N --key KEY` or `reviews queue-move PR --expect-config N --key KEY` with `--before PR`, `--after PR`, `--first` or `--last`. Add without a destination appends; move requires one. MCP equivalents are `review_queue_add` and `review_queue_move` with the current configuration revision, PR, explicit key and optional before/after/position. These use ordinary project write access, preserve unrelated settings and existing controls, and perform no provider work. A no-op move preserves its revision. Initial execution setup remains administrative. The configured execution queue also supplies Delivery membership and relative order in one write; there is no second display-enrollment step. New PR metadata is filled by the automatic observer, without making configuration wait for GitHub. Retained merged history and explicit retirement remain separate from scheduling. One configured queue can contain standalone PRs targeting the repository's default branch and actual PR stacks. In stacked mode, each PR's published base determines its parent; queue order supplies scheduling priority. See [review identity](https://github.com/benhook1013/FireController/blob/main/docs/reviews.md#review-identity). An authorized oversized exact-target review may deliberately select CLI `reviews request --override-file-limit` or HTTP/MCP `override_file_limit`, overriding only the optional project file ceiling without changing defaults or provider restrictions. Automatic selection never inherits this choice. A deliberately early exact-target request uses CLI `reviews request --out-of-order` or HTTP/MCP `allow_out_of_order`; it preserves the target's other admission checks.

Use `reviews queue --active` (`review_queue` with `active:true`) to select open work before paging. Full queue/history reads retain merged and closed entries. `reviews runs PR` returns each run’s own dates; workspace-origin timestamps do not date a native review. For provider work, prefer one supported bounded `reviews operation OPERATION_ID --wait-seconds N` (`review_operation_read`) while useful work continues. Its stage, cause, evidence handle and next action describe retained facts; a posted trigger is not proof of execution. `--diagnostics` or MCP `diagnostics:true` explicitly loads the original full operation. A capture verification hold requires recovery of that original attempt, not another review.

For multiple decisions or fix references on the same native evidence, `reviews decide-batch EVIDENCE_ID --file PRIVATE --key KEY` / `reviews fix-batch ...` and MCP `review_findings_decide` / `review_findings_fix` apply 1–100 explicit items atomically with one adjudication revision. Every reason or proof remains explicit. A rejected batch changes none of its items; retain the exact request/key after an uncertain response. Finalize when all findings have decisions, before doing fixes: finalization freezes the original counts and automatically queues the GitHub review summary. No separate publish call or wait for fixes is needed. Use single-finding commands for a single edit.

When authorized to grant more reviews, use `reviews rounds grant` / `review_rounds_configure` with the current revision and explicit additional bounds. A grant reopens the selected channel after taper or closure without erasing its earned streak; the next eligible completion evaluates taper again. The minimum still requires the requested additional rounds, and the maximum remains the cap. Already underway or complete-unfinalized work counts toward “more”; exact-key replay never grants again. Changing controls starts no provider request. See [round controls](https://github.com/benhook1013/FireController/blob/main/docs/review-round-controls.md) for the full accounting contract.

An active Hosted `trigger_recorded`, `trigger_posted` or `trigger_recovered` confirms original trigger delivery, not provider execution. Keep its existing observer and use a bounded operation wait while doing other work; do not repost. The operation's `updated_at` is a local state transition, not provider start or last observation. Follow its stage/evidence handle; no exact next-observation time or finish ETA is exposed by this read.

A Hosted `rate_limited` / `hosted_review_rate_limited` operation is terminal: CodeRabbit rejected the issued command. Its raw response remains retained, but it completed no review and earned no taper credit. Waiting on that operation will not resume it. If another review remains authorized, one later fresh request/key uses normal allowance preflight; the rejection alone does not supply an exact retry time. This differs from uncertain delivery, which retains the original key.

A proven `hosted_allowance_cooldown` hold is terminal and posted no review trigger. At or after its retained `retry_not_before` (`allowance.retry_not_before` in full diagnostics), submit one new request/key only while the review remains authorized, with the current configuration revision and qualified head. The original key replays the held result; there is no resume command for this hold. Normal admission still applies. This differs from an unknown outcome, which must retain its original key.

A terminal `hosted_allowance_reply_pending` hold posted no review trigger and does not resume on a late reply. For the still-authorized planned review, use one later fresh request/key and current configuration/head; normal preflight obtains fresh allowance and checks admission. Respect known cooldowns and avoid rapid retries. No manual GitHub repair or additional round grant is needed merely because preparation held; an old available reply cannot authorize execution. Keep the original key for unknown action outcomes instead.

For an actual completed independent Subagent review, use `reviews subagent-record --file PRIVATE --key KEY` / MCP `review_subagent_record` with the reviewed head, reviewer, scope, times and findings. The service derives identities and counts. No prior PR enrollment is needed; a previously unseen PR stays outside Delivery unless explicitly enrolled. Already-adjudicated results, including a clean zero-finding review, can use `finalized:true` in that same call. Otherwise use `reviews subagent-read RUN_ID` / `review_subagent_read`, then `reviews subagent-update RUN_ID --file PRIVATE --key KEY` / `review_subagent_update` for selected decisions, fix proof and finalization under the returned stable run revision. Omitted findings stay unchanged. This is normal writer access; no administrator history import, CodeRabbit capture impersonation or provider allowance is needed. See matching `docs/subagent-reviews.md` for request fields.

Sizing information can appear as `review_size` in queue-enrollment/review receipts, ordinary and active queue reads, and stored next-target views. **Suggested maximum PR size** is an optional project preference; **Maximum review size** remains the separate enforced review policy. The output supplies observed file count, configured settings, headroom or excess when known, and historical completed-review context. An explicit review request omits counts from a different stored head; an absent count is unknown, not zero. Queue and next-target sizes belong to their stored observations, not a freshly verified comparison. Admission still checks the actual materialized diff; do not fetch source just to fill a preview. A suggestion warning needs no acknowledgement, exception, inbox message, job or note and changes no allowance, taper or scheduling rule. Prior completed reviews do not establish coverage of subsequent changes. Project settings and the [sizing contract](https://github.com/benhook1013/FireController/blob/main/docs/reviews.md#pr-size-settings) own configuration; do not copy project values into procedural instructions.

For a `parent_moved` or `predecessor_parent_moved` hold, follow the matching [parent/base metadata recovery](https://github.com/benhook1013/FireController/blob/main/docs/review-source.md#parentbase-metadata-recovery) guidance. It distinguishes real branch reconciliation from stale GitHub PR metadata and preserves the original held request.

For read compatibility failures, matching `docs/agent-client.md` → Client releases and additive reads owns release/reconnect behavior. The error action identifies the running-client check; a read failure does not justify another provider review.

To identify which retained required CI context is pending or failed, use `reviews ci-assess --pr N --diagnostics` or `review_source_ci_assess` with `diagnostics:true` when advertised by the installed tools. This names selected CheckRuns and same-name Commit Statuses without another GitHub read. The outer source applicability and observation time still apply. See matching `docs/review-ci.md` for the bounded detail contract; full provider inventories are not part of this output.

When the installed client advertises `reviews ci-wait` or MCP `wait_for_ci`, use one quiet wait for several PRs with their full expected head SHAs, optionally their base SHAs. It observes the final merge branch's required gate on each actual comparison without queue enrollment or review requests. Keep the call pending while doing useful work; on return, omit completed targets from the next wait. A superseded comparison needs current pins, and unknown or empty requirements do not mean CI passed. Matching `docs/ci-wait.md` owns the result, timing and host boundaries.

A CLI `allowance_timeout` is a terminal pre-review hold, not exhausted quota or evidence of a provider outage. Continue other work; if the planned review remains authorized, one later new request with a fresh key and current configuration/head rechecks allowance. The original key replays the hold. Do not reset rounds or rapidly retry; no retry deadline is established. Matching [execution guidance](https://github.com/benhook1013/FireController/blob/main/docs/review-execution.md) owns the failure boundaries.

For `review_evidence_pending`, current clients include bounded `pending_evidence` references in the operation result: source evidence/finding, and the receiving PR/route where relevant. Resolve the identified existing obligation; an outgoing accepted route without fix proof can hold the source channel. These facts are evaluated now, while the original operation remains terminal. Read the referenced record only when more context is needed; the [operation contract](https://github.com/benhook1013/FireController/blob/main/docs/review-operations.md#pending-native-evidence) owns the representation and recovery boundary.
