# Source Refresh and Observed Policy

## Implemented boundary

An explicit source refresh reads the selected GitHub PR and only the repository and preceding PR facts needed to identify its comparison. It durably queues the operation before provider work starts. A short default wait returns the completed result in the original call when possible; only work that remains pending returns an operation receipt. It does not request a review, invoke the CLI, inspect allowance or download completed review captures. Ordinary operation and assessment reads use stored records without contacting GitHub.

The observed-policy assessment applies current local channel requirements and finding obligations to that stored source comparison. Its source observation time and policy evaluation time are separate. It is an as-of assessment, not a guarantee that GitHub has remained unchanged, a required-CI result or a merge-readiness verdict. The [captured-comparison assessment](review-controls.md#captured-comparison-assessment) remains available for inspecting a particular historical native capture.

## Request and recovery

`POST /api/v1/projects/{project_id}/reviews/source-refreshes` requires project write access, an idempotency key and required `expected_configuration_revision`, `pull_number` and `head_sha`. Optional `include_ci: true` additionally collects [required CI](review-ci.md); optional `include_readiness: true` collects CI plus [review-state facts for readiness](review-readiness.md). Omitting both retains source-only behavior. The PR must be in the configured queue, and the expected revision and head are assertions. The service never substitutes a different target. The HTTP handler waits up to two seconds by default. A completed or held operation returns its compact outcome with HTTP `200`. If work remains pending, HTTP `202` returns its original queued receipt containing ID and revision. The optional `Prefer: wait=N` header selects zero through sixty seconds: zero returns immediately, while a longer explicit wait can return the result without another model-facing call. The supported wait preference follows the purpose of the [HTTP wait preference](https://www.rfc-editor.org/rfc/rfc7240.html#section-4.3); it is result-collection metadata, not part of the idempotent action request.

Retain the original request, key and profile binding until its outcome is known. Exact-key replay preserves the original action and internal receipt; its wait can return the current completed outcome without another provider read. Compatible queued or running requests from the same project, actor and worker can share one operation; changing repository, PR, asserted head, source configuration, capability or either observation option prevents that coalescing. The queue admits at most 64 active refreshes instance-wide and 16 per project. A capacity refusal starts no provider work.

`GET /api/v1/projects/{project_id}/reviews/source-refreshes/{refresh_id}` returns stored state and, for a completed refresh, the exact observed repository, PR, candidate, base and effective parent. States are queued, running, completed and held. A source mismatch, unavailable provider or changed authorization holds the operation with a safe reason. A failed refresh preserves earlier completed observations and their age. Reads do not restart failed work.

One bounded source worker runs independently of review dispatch. Repository and PR reads share a fifteen-second provider budget and run outside database transactions. Including CI gives the combined refresh a thirty-second aggregate budget, while its source phase remains bounded to fifteen seconds. Readiness collection has a forty-five-second aggregate budget and the same fifteen-second source bound. Interrupted running reads can be queued again at restart because they perform no external mutation. Startup and shutdown belong to the daemon's shared worker owner; the database remains open until every owned worker has finished. An installation without configured provider capabilities starts no source polling loop.

Transient local storage admission overload does not stop the worker. It retries local work with cancellable exponential backoff from 100 ms to one second, preserving each transaction's two-second bound. After the provider read finishes, retries retain that exact result and repeat only the guarded completion transaction, rechecking current access and source configuration. Clearing contention therefore completes or holds the running operation without another provider read or a daemon restart. Other persistence failures remain fatal; shutdown may leave interrupted reads for normal startup recovery. This internal worker behavior does not add retries to agent requests or provider calls.

Waits subscribe to bounded per-operation completion notifications outside database transactions. Expiry or cancellation releases the subscription without cancelling the queued action or acknowledging anything. The result is reauthorized before it is returned.

The service checks the original actor's access, stable repository binding and operator capability before fetching and before recording its result. Source configuration changes hold in-flight work. Changing only the execution pause leaves the source comparison valid; pausing a review channel does not prevent an explicit source refresh or erase existing review credit.

## Local assessment

`GET /api/v1/projects/{project_id}/reviews/source/{pull_number}/policy` requires project read access and accepts no query parameters. It evaluates the latest completed source observation and current policy in one authorized database snapshot. Missing source is explicit rather than an empty passing assessment. A changed repository, capability or source configuration holds the old observation; changing only the execution pause preserves it.

The response identifies the refresh, exact target, current configuration and policy revisions, source observation time and evaluation time. Each required channel reports coverage and pending evidence. All required channels need applicable finalized native captures and satisfied finding obligations; pending evidence dominates coverage. Imported history supplies no native credit. Missing channel policy is unconfigured. None of these states authorizes a merge.

## Bound agent tools

The CLI uses its selected private profile:

```sh
fc reviews source-refresh --pr 8 --head SHA --expect-config 2 --key retained-action-key
fc reviews source-operation REFRESH_ID
fc reviews source-assess --pr 8
fc reviews source-refresh --pr 8 --head SHA --expect-config 2 --key retained-ci-key --ci
fc reviews ci-assess --pr 8
```

Source refresh additionally accepts `--wait-seconds N` from zero through sixty; omitted means two seconds. A longer explicit wait extends only that command's client budget to the chosen wait plus five seconds. Other commands retain their normal deadline.

The equivalent MCP tools are `review_source_refresh`, `review_source_refresh_read` and `review_source_policy_assess`. The refresh tool accepts optional `wait_seconds` with the same default and range, and optional `include_ci` and `include_readiness`. `review_source_ci_assess` reads retained CI facts independently of review policy. Refresh is an explicit mutation that schedules provider reads; the other tools are provider-free reads. There is no automatic polling, generated retry key, implicit project selection or per-command queue refresh. Read tools use the normal five-second client deadline; an explicit refresh wait above two seconds extends only that call to the selected wait plus five seconds. A receipt means accepted for background work, not completed.

## Proof and limits

Clean checkpoint `5ca250513e10a6a8d5c08deae66bab305d9caad5` passed eight actual packaged-service groups in 14.904 seconds, using `fc`, `fcd` and the official SDK with packaged `fcmcp`. Each binary identified that exact commit with `vcs.modified=false`; source/assets manifest SHA-256 `eac75b0de1fc53365eb21f405c334fa0c3a72c9c43a91d6475c7a7cd5a00c462` and all binary hashes stayed unchanged. The tested `fcd` hash was `bd0eecd8e1801badbeb2e5d28559abeb32c36a060990776e4ebd654bbb3fd068`.

A fast default refresh returned useful completed facts in 22.5 ms and 693 bytes. A blocked refresh returned its 87-byte receipt after 2.008 seconds while job/inbox reads took 4–5 ms. Explicit immediate return and a later longer wait retained the same operation without another fetch. A legitimate three-read stacked comparison completed in the original call after 10.889 seconds with a fifteen-second preference, crossing the ordinary server write timeout while concurrent coordination reads stayed below 15 ms. Each provider read remained below its five-second bound and the source phase below its fifteen-second aggregate bound.

Client cancellation preserved the queued action; exact-key recovery returned its result without another fetch. SIGKILL/restart safely repeated the interrupted read using the same operation and preserved native evidence, immutable artifacts and imported merged history. Actual SDK calls covered direct results, immediate receipts, longer waits, stored reads and provider-free policy assessment; malformed waits failed before credential access. Current-policy reads left logical SQLite contents and provider counts unchanged. Pause changes preserved applicable coverage.

The passing run made 21 controlled provider GETs, limited to the selected repository/PR and the one required parent in the stacked case. It made zero provider POSTs, Git commands, CLI review invocations or real external calls. Owned processes, listeners and private runtime state were removed. The full repository check/build and focused authorization, capacity, idle-writer and failure regressions provide complementary proof. These are small local measurements with controlled provider responses and an initial native-evidence fixture, not live account behavior, fleet throughput, remote deployment, CI readiness or operational cutover.

## Contention recovery proof

Runtime checkpoint `c51b43db7c18f4fe0e670fc1ab0475ea053c7234` passed an actual packaged `fc`/`fcd` contention case in 8.675 seconds. A real external SQLite writer held the claim path for 3.120 seconds and the completion path for 3.127 seconds, crossing the unchanged two-second local admission deadline. The original queued operation completed 893 ms after the first release. The retained provider result completed 407 ms after the second release, and the next queued PR completed 10 ms later. All three operations used the same daemon lifetime, exactly two selected-source GETs and one completion event each. No provider read was repeated; coordination reads stayed below 6 ms. Internal SQL retry counts were not instrumented.

Stored operation/assessment reads and original-key replay changed neither logical SQLite contents nor provider counts. Explicit zero wait returned the original receipt; a positive wait returned the exact completed outcome. Native evidence, capture bytes and imported merged history stayed unchanged. The run made six controlled provider GETs, zero provider POSTs and zero real external calls. All 353 tracked source/assets files and both application binaries stayed identical; owned processes/listeners and the successful runtime were removed. Two earlier private fixture failures were retained: an eagerly evaluated diagnostic blocked readiness, and a replay assertion incorrectly expected a full terminal result at zero wait. Only those fixture errors were corrected; lock durations, assertions about duplicate work and production deadlines were preserved.

Focused real-contention tests additionally cover read-pool admission, current authorization/configuration changes, pause-only changes, provider failure, fatal storage failure and cancellation followed by startup recovery. The exact post-commit completion-reconciliation branch was inspected, without injected loss of a successful commit. The full source/execution package race suite passed in 215.663 seconds and the daemon package in 4.397 seconds. The inherited handoff tests were corrected to include the immutable pre-admission baseline and gate their barrier after the review POST; they preserve the preparation-reference prefix and require exactly one additional observation. The full runtime race recheck passed in 113.036 seconds at test-correction checkpoint `0ae9c3b`; scoped vet and documentation/link checks passed. This is bounded local contention proof, not broad load, live-provider performance or installed cutover.
