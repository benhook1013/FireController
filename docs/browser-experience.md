## Delivery read contract

`GET /api/v1/projects/{project_id}/delivery` requires project read access and returns `workers` and `jobs`, each an independently bounded `items`/`cursor`/`has_more` collection from one local read transaction. `worker_limit` defaults to 20 and `job_limit` to 50, each capped at 100; `worker_cursor` and `job_cursor` bind the project, principal and ordering. Unknown, repeated or malformed selectors fail validation. Worker order follows configured pins, then name and ID; open jobs use active, blocked, parked then ID. Completed jobs remain outside this overview.

Workers include their identity/name, selected primary job, explicit pause state and a pause-reason preview. Jobs include compact title/state/revision/assignment and worker name, a bounded standing-brief preview, the job's last recorded edit time (any job field), current progress summary/next/blocker previews and optional checklist done/total counts. Each prose preview is at most 240 UTF-8 bytes with its explicit truncation flag; full details remain deliberate reads. A known empty checklist stays distinguishable from an absent checklist. No full briefs, checklist item text, progress evidence, history archives, provider captures or implicit provider refresh are included. These facts share one bounded local transaction and indexed current-state lookups rather than browser request fanout. The [job-state contract](job-state.md) owns the authoritative current record and explicit history.

The browser groups this bounded job slice into lanes. An ordinary complete board has no pagination controls. When a project exceeds the initial bounds, an explicit Load more work action appends one bounded continuation instead of replacing existing lanes or jobs. A refreshed first read discards the old appended tail; late responses cannot restore it. An assigned job whose worker lies outside the worker slice still carries its worker name and never becomes Unassigned. A partial job page does not establish that any lane is complete. Continuation remains explicit without automatically walking an entire fleet. The full queue loads at most one initial bounded round page per displayed PR, shared with the hero through the query cache; further rounds require an explicit action. A partial channel count says that only shown runs are counted. It does not substitute a mixed total for Hosted/CLI counts. Job creation/update, checklist replacement, worker creation/pause/focus and broad resynchronization invalidate this stored summary; unrelated message arrivals do not require rereading every job.

Private Delivery job cards show the job title/status, current Progress, Next and Blocker when supplied, the last-edit age and a full-job link. They do not display clipped standing instructions, a separately maintained audience summary or checklist metadata. Full job detail retains the brief, optional audience summary, checklist, attached reminders, evidence and deliberate history reads. Labels sit beside readable current text rather than forming a stack of tiny uppercase section headings. Empty progress fields add no filler. Public worker cards continue to use explicitly approved summaries; this layout change publishes nothing. The job's last-edit timestamp may reflect any edited field; it does not claim a separate progress timestamp or establish history sequence order. Imported times and clock rollback retain their explicit display behaviour.

## Editorial Project page

Project is the single overview tab: current working entries when authenticated, approved publication when anonymous. A labelled public preview is available without signing out. The authenticated overview contains editorial project content; operational worker lanes and the review queue belong on Delivery. Public review rows reuse the shared presentation components with only approved public fields. The [shared experience](shared-project-experience.md#one-browser-experience) owns audience selection and publication boundaries.

Project explains what the project is, its direction and progress as a coherent website. It replaces the record catalogue as the primary map presentation. Content has flexible editorial depth: a substantial Markdown section, a short update, an initiative with subsections, a milestone, or contextual deferred direction are all legitimate. Progress, dates, status labels, phases and links are optional aids, not a mandatory checklist shape.

Use readable section hierarchy, generous but purposeful typography/spacing and appropriate full-width narrative, cards or columns. Render the actual content in the page rather than requiring a click through each summary. Do not present every entry as the same boxed database row or surround prose with empty metadata placeholders. Preserve project-configurable appearance, the selected default branding and platform attribution.

Markdown is an appropriate authoring format; storage and APIs must preserve its expressive content and deliberate order. Render supported prose, headings, emphasis, lists, quotes, code and safe links as content. Raw HTML, scripts, arbitrary CSS and automatic external embeds do not acquire authority from Markdown. Existing plain editorial records and historical revisions remain readable; optional structured progress remains available. The domain contract at [project map](project-map.md) owns exact persisted shape, bounds, history and import behavior.

A return point can remain editorial context when it explains project direction. Actionable reminders belong on jobs or contextual notes, with links where helpful. Do not automatically reclassify, import, deliver or resolve those records.
