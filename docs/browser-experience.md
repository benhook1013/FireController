## Default Delivery homepage

The project root opens Delivery: one useful view of who is doing what, followed by the review and merge queue. Worker lane cards contain their assigned open jobs, including primary focus and other concurrent jobs. An Unassigned lane contains open jobs without an owner. Cards show concise current activity, job state, blockers and the next useful step with links into full context. Worker pause is an explicit coordination fact, never inferred online presence or a job status. Worker lanes with active work come first, then lanes with blocked or parked work, then workers without loaded open jobs. Within each lane, the explicitly selected primary job comes first, followed by active, blocked and parked work. A parked primary job does not move a lane with other active work behind inactive lanes. Red worker headers provide inbox and filtered job-history links; the lane contains distinct job cards, with status and primary-focus pills beside their titles when space allows. Unassigned work remains a separate lane. Completed jobs remain available in Jobs rather than crowding the default board; lane order does not claim agent presence.

The default view needs no worker selection or filter configuration. Inbox actor selection never filters Delivery. Jobs remains a separate management view with status/worker filters, completed history and a future home for deliberate creation/editing; browser job mutations are not implied by this redesign. Worker details and histories remain secondary links from lanes.

The review/merge queue sits below the lanes, with distinct Hosted and CLI groups, actual findings, taper/limits and CI facts where available. Merged entries remain visible completed history. Remove entries only for explicit defunct/superseded work. Delivery embeds the same full review queue renderer as the focused Reviews route, including per-channel run counts, round history and explicit continuation. The hero links down to that queue. Project-configured review-group headings preserve the queue order rather than rearranging work into label buckets. A coloured rail and signed positions show distance from an established first open head; a partial or ambiguous slice does not invent a global rank. Merged rows and pills use the project’s purple merged palette. The compact guide explains request states and the three-number counts without claiming unavailable source facts. Completed attempt prose and redundant retained-history labels do not crowd the queue. Missing PR details identify the actual unknown fields behind an expandable disclosure. Detailed PR/run pages supplement the overview without making routine monitoring require several screens. Ordinary timestamps use relative ages, with precise dates available on hover or in source details.

The hero is one joined, two-tone surface, with project identity vertically centered on its left. Its right side presents the merge-train head PR with its title, meaningful stored review/CI state and a link to inspect it. Select the head from actual stored queue ordering and eligibility; an incomplete bounded slice cannot establish that no head exists. Keep Hosted and CLI progress distinct and retain freshness/unknown states. This card must not fetch GitHub or start a review. Remove decorative workflow filler. Show one connection indicator and the Refresh action in a compact sticky header so they remain usable while scrolling; keep Disconnect a compact utility. Refresh rereads stored service data and never starts provider work. Remove duplicate hero utilities and visible internal project IDs. With no head, the hero contracts rather than leaving an empty panel.

Reads stay bounded and project-scoped. Reuse stored summaries and live invalidation; never expand every job brief, checkpoint, note archive or provider capture to paint the board. Expose continuation or partial coverage honestly at larger sizes, without presenting a partial page as the full project. ## Delivery read contract

`GET /api/v1/projects/{project_id}/delivery` requires project read access and returns `workers` and `jobs`, each an independently bounded `items`/`cursor`/`has_more` collection from one local read transaction. `worker_limit` defaults to 20 and `job_limit` to 50, each capped at 100; `worker_cursor` and `job_cursor` bind the project, principal and ordering. Unknown, repeated or malformed selectors fail validation. Worker order is stable ID order; open jobs use active, blocked, parked then ID. Completed jobs remain outside this overview.

Workers include their identity/name, selected primary job, explicit pause state and a pause-reason preview. Jobs include compact title/state/revision/assignment, the assigned worker name and their optional latest checkpoint sequence, captured job revision, done/next/blocker previews. Each preview is at most 240 UTF-8 bytes with an explicit truncation flag; full details remain deliberate reads. No briefs, evidence arrays, histories, provider captures or implicit provider refresh are included. Checkpoint revisions remain visible so older progress cannot masquerade as an update to a newer job brief.

The browser groups this bounded job slice into lanes. An ordinary complete board has no pagination controls. When a project exceeds the initial bounds, an explicit Load more work action appends one bounded continuation instead of replacing existing lanes or jobs. A refreshed first read discards the old appended tail; late responses cannot restore it. An assigned job whose worker lies outside the worker slice still carries its worker name and never becomes Unassigned. A partial job page does not establish that any lane is complete. Continuation remains explicit without automatically walking an entire fleet. The full queue loads at most one initial bounded round page per displayed PR, shared with the hero through the query cache; further rounds require an explicit action. A partial channel count says that only shown runs are counted. It does not substitute a mixed total for Hosted/CLI counts. Job creation/update/checkpoint, worker creation/pause/focus and broad resynchronization invalidate this stored summary; unrelated message arrivals do not require rereading every job.

## Authored Markdown

Full job briefs, checklist text, checkpoints, updates, conversation messages, contextual note bodies/reasons and review finding/decision/proof narratives use the same safe Markdown renderer as editorial content. Ordinary prose is valid Markdown; writing does not require a rigid template, special headings or a formatting-lint round trip. Titles, status enums, identifiers, evidence references and truncated list previews stay literal. Render headings within the page hierarchy, lists, emphasis, quotes, code and safe links consistently. Raw HTML stays escaped, unsafe links remain inert and remote images do not load automatically. Rendering stored text never executes instructions or changes authorization, message acknowledgment, job state or review policy. No extra API/history reads are needed to format an already selected body.

## Editorial Project page

Project explains what the project is, its direction and progress as a coherent website. It replaces the record catalogue as the primary map presentation. Content has flexible editorial depth: a substantial Markdown section, a short update, an initiative with subsections, a milestone, or contextual deferred direction are all legitimate. Progress, dates, status labels, phases and links are optional aids, not a mandatory checklist shape.

Use readable section hierarchy, generous but purposeful typography/spacing and appropriate full-width narrative, cards or columns. Render the actual content in the page rather than requiring a click through each summary. Do not present every entry as the same boxed database row or surround prose with empty metadata placeholders. Preserve project-configurable appearance, the selected default branding and platform attribution.

Markdown is an appropriate authoring format; storage and APIs must preserve its expressive content and deliberate order. Render supported prose, headings, emphasis, lists, quotes, code and safe links as content. Raw HTML, scripts, arbitrary CSS and automatic external embeds do not acquire authority from Markdown. Existing plain editorial records and historical revisions remain readable; optional structured progress remains available. The domain contract at [project map](project-map.md) owns exact persisted shape, bounds, history and import behavior.

A return point can remain editorial context when it explains project direction. Actionable reminders belong on jobs or contextual notes, with links where helpful. Do not automatically reclassify, import, deliver or resolve those records.
