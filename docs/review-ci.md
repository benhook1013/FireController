# Required CI Observations

## Implementation status

The provider collector, pure assessment, durable service storage and bound API/CLI/MCP controls are implemented. Focused provider and local integration tests, full repository checks and controlled packaged-service proof pass. Operational cutover remains separate.

## Explicit collection

For current CI checking on one or more PRs, use [CI waiting](ci-wait.md). It returns required-check details using the final merge branch's gate and shares service observation without queue enrollment or a separate source refresh. The retained assessments below keep their existing selected-base meaning: `ci-assess` reads a completed source refresh collected with CI or readiness. If none exists, `reviews_ci_unavailable` means that retained observation is absent, not that authentication or CI failed. Only when a retained selected-base assessment is intended, collect an already-pending CI-enabled refresh or request source refresh with `include_ci: true` (CLI `--ci`), wait for that original operation to complete, then reassess. An assessment read does not silently collect GitHub data or substitute a different gate.

Source refresh accepts optional `include_ci: true`; the bound CLI exposes `--ci` and MCP exposes `include_ci`. Readiness collection also requests CI; omitting both options keeps source-only collection. CI collection uses the same durable operation, two-second default result wait and optional longer wait described in [source refresh](review-source.md). Adding CI changes the action identity: source-only work cannot silently fulfill a CI request. Ordinary operation and assessment reads never contact GitHub.

Source-only collection retains its fifteen-second provider budget. A CI-only refresh (`include_ci: true` without readiness) has one fifty-five-second aggregate budget (fifteen seconds for source acquisition plus forty seconds for the complete gate read), with at most fifteen seconds for its initial source phase. A [readiness refresh](review-readiness.md#service-and-bound-tools) also requests CI and uses a seventy-second aggregate budget, adding fifteen seconds for provider review-state observation. Provider work runs outside database transactions. Cancellation of the caller's result wait does not cancel the accepted operation. Restart may repeat interrupted provider reads, using the same operation identity; collection never posts a review or reserves provider review allowance.

Successful source collection remains useful when CI cannot be established. The operation retains its source comparison and an explicit unproven CI outcome. Provider failure, incomplete pagination, unsupported identity or exceeded capacity never becomes an empty passing result. Raw provider errors and full inventories stay out of ordinary agent responses.

Failed collection retains a bounded reason when known: collection deadline or cancellation, provider rate limit, authorization refusal, missing resource, invalid response, HTTP timeout, server error or redirect. Unknown transport/adapter failures retain `ci_provider_unavailable`; this does not establish a network regression or its cause. Response-body timeouts are transport timeouts, not malformed completed JSON. Other interrupted body reads remain transport failures; size-limit and completed JSON validation failures remain invalid responses. A known collector stage is appended to the safe failure reason, such as `ci_provider_timeout_head_results` or `ci_provider_invalid_response_attempt`, so a failed observation identifies where collection stopped without retaining raw endpoints, messages or partial credit. Workflow status/conclusion movement across independently read, otherwise identical workflow-attempt inventories is reported as `ci_provider_observation_changed_assessment`; it remains unproven and retains no partial CI credit. This differs from malformed facts or a changed immutable workflow/attempt identity. Zero counts after failed collection do not establish an empty required-check set. No raw error text or partial CI inventory is adopted. Old generic failures remain unchanged. Reading or replaying a completed refresh does not retry collection; a subsequent ordinary collection can capture current facts without changing review allowances or CI producer configuration.

A parsed check run whose `completed_at` precedes `started_at`, except a completed skipped or cancelled check, retains the finite `check_run_time_order` issue alongside its existing collection stage. Agent diagnostics identify the check-runs inventory and those fields without exposing provider bodies or private details. The observation stays unproven with no partial CI credit; this neither adjusts provider timestamps nor reruns CI. Historical generic failures cannot gain a reconstructed field cause from a later read.

Check-run totals can change between pages while GitHub publishes jobs. A changed total or bracketing suite count discards the partial inventory and permits one recollection of that same immutable commit within the original time, page, item and byte budgets. A changed count may shift rows from an earlier page onto a later page; that cross-page overlap also discards the entire partial inventory for the same bounded recollection. Duplicate IDs within one page, duplicates with unchanged counts and malformed rows remain invalid. Persistent movement remains unproven with `ci_provider_observation_changed` and the collection stage. This bounded recollection does not retry malformed responses, permission failures, limits or changed selectors, and does not post a review, rerun a workflow or spend review allowance. Normal background observation continues independently; agents need no owner investigation for an inventory race.

## Authority and candidate

Required checks come from the selected base branch's complete applicable branch protection and active repository rules. Exact context and expected GitHub App identity matter. An unavailable or ambiguous authority remains unproven. An explicitly complete empty requirement set means `not_required`, without fetching check runs or workflow jobs. This means that the selected base branch has no required checks; it does not mean that no workflows are running, that workflows passed, or that optional workflow failures are monitored. A stacked PR targeting a feature branch can therefore report `not_required` while current-head CI is running or failing. GitHub merge-state gates remain separate in the readiness assessment.

The documented `copilot_code_review` rule requests automatic review feedback and supplies no required CI contexts. Its optional parameter object accepts only the documented Boolean options; malformed parameters and unfamiliar rule types remain unproven. See GitHub's [branch-rule schema](https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch) and [standalone automatic-review rule](https://github.blog/changelog/2025-09-10-copilot-code-review-independent-repository-rule-for-automatic-reviews/). A compact `ci_authority_unproven` outcome with zero required checks means the collector could not establish the requirement set; it does not mean that no checks are required or that a workflow failed.

The collector binds the repository's stable identity, PR, head, base SHA and base branch. It prefers CI on a verified test merge when that commit has check runs or commit statuses. A completely observed empty merge result may fall back to the head. Failed or incomplete merge observation cannot justify that fallback. A conflicting merge can have head CI facts, but their outcome does not imply that the PR is mergeable.

Complete required-check authority with `Strict:false` does not require the PR to be up to date with its base. When the PR endpoint and its test-merge parent coherently identify the same older base while an independently stable live base has advanced, the collector may assess the actual current PR head instead. It retains the candidate and merge state as unproven and selects only head results; it does not fetch or credit that stale test merge. Current head checks still need the full required context, App, workflow and current-attempt proof, plus the usual final source, authority and result rechecks. A head success satisfies the actual non-strict check policy without claiming that the latest base was tested, proving merge readiness or requiring a new commit merely because the base advanced. Complete empty non-strict authority can instead retain `not_required`, with no selected commit or fetched result/attempt inventory; this is proven absence of required checks, not a passing CI claim. Strict authority, incomplete authority, a moving candidate or any other merge-identity failure retains its refusal. Previously retained unproven mismatch observations stay unproven when read; only fresh collection can establish new head facts.

Before crediting a passing result, collection rechecks the source candidate, requirement authority and selected CI identities. Movement leaves the observation unproven. These checks produce attributable facts as of their observation interval, not an atomic lock on GitHub or a guarantee that later provider state is unchanged.

GitHub may report a PR mergeable while its test-merge commit still has an earlier base parent after retargeting. An unverified test merge supplies no CI credit; the mergeability flag cannot substitute for that proof. The narrow non-strict head assessment above does not verify that merge identity. Compact observations preserve the known candidate reason (`ci_merge_identity_unproven`, `ci_merge_pending`, `ci_candidate_changed` or `ci_target_changed`) instead of folding every case into `ci_target_unproven`. This diagnostic does not change selection, grant CI credit or trigger a retry. Previously retained observations remain unchanged.

When the selected merge object has exactly two distinct parents including the expected PR head, but its other parent differs from a stable independently read base-branch tip, the candidate records `ci_merge_base_mismatch`. Strict required-check authority keeps the CI result unproven; the coherent non-strict case above can separately assess current-head CI. The PR endpoint's `base.sha` and its test-merge parents may match each other while both lag the live branch. Existing successes on that older comparison do not prove CI for the current base, even if the old and current base trees are identical. CLI/MCP explains this distinction directly. When CI still requires a verified current merge comparison, allow GitHub to regenerate its test merge after a retarget or base update and collect a later observation. If the live base stays stable while GitHub retains the stale merge, the repository owner can reconcile the PR branch with that base through its normal authorized merge/rebase workflow, then collect CI for the resulting comparison. FireController source refresh observes the comparison; it does not regenerate GitHub merge refs or update branches. Repeated old-refresh reads, no-op commits, obsolete-run reruns, CI bypass and review/taper resets do not establish the required identity. Moving branches, wrong merge objects and other unproven identities retain their separate refusal paths. Old observations are not reclassified.

Stable mismatch candidates retain `merge_base_mismatch` facts: `pr_base_sha` from the PR endpoint, `live_base_sha` from the independently stable base branch, and the actual `merge_sha` and `merge_base_parent_sha`. These come from the existing candidate reads, after the final PR read still agrees; moving or otherwise unproven candidates supply no such facts. When the outer CI result remains unproven for this mismatch, current CLI/MCP CI assessments and waits show these exact distinct hashes in their diagnostic. The direct assessment and wait HTTP responses include this optional object only with the existing `X-FC-CI-Watch: change-v2` opt-in. Earlier clients keep their original response shape, and older retained observations cannot acquire facts that were never recorded. The object is diagnostic evidence only: it selects no CI commit, changes no gate and causes no extra provider request.

## Current workflow identity

For GitHub Actions, workflow identity and provider run number select the newest run for the selected commit. A newer pending or failed run prevents an older successful run from supplying credit. Event type, timestamps and numerical check-run IDs do not establish currentness by themselves.

Optional [CI-wait failure attention](ci-wait.md) separately retains an earlier failed execution across proven same-name skipped jobs. Its explicitly labelled historical rows can also expose an already-read same-head failure whose latest-job coverage or supersession is unproven. Neither form changes this required-gate selection or reuses an older successful result.

After a positively bound stable test-merge base mismatch, explicitly selected CI waits may observe same-head repair failures with an explicit head-only basis. The workflow run's base comparison remains unknown; these failures never populate this contract's required results, selected CI commit or check counts. Ordinary CI assessments and waits without that selection retain their existing collection scope.

Required check runs must bind positively to the selected workflow run, its current numbered attempt and the actual job's check-run identity. Partial reruns do not inherit earlier successful jobs without that proof. Unsupported provider currentness, missing job identity and ambiguous duplicate contexts remain unproven. Commit statuses retain the provider's newest-first ordering; matching status and check contexts must both satisfy their applicable requirements.

GitHub requires both a check and a same-name commit status to pass when that name is required; see [troubleshooting required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks). An App-bound requirement must have its own attributed native check and current workflow attempt. A same-name commit status is an additional barrier: its latest success, pending or failure state participates in the outcome, but it never supplies the native App proof. A successful status cannot replace a missing, wrong-App, ambiguous or otherwise unproven native check. The collector does not infer an App identity from a status creator or target URL. Requirements without an App binding continue to support status-only evidence.

Previously retained conservative status-origin and same-suite ambiguity assessments remain readable as originally recorded, with their exact inventories, outcomes and counts unchanged. Retained validation accepts only the exact earlier assessment reproduced from the saved facts, including the previously supported origin-only result with current rerun selection; fresh collection uses the current native-check-plus-status rule. Reading or replaying an old refresh does not recollect GitHub or reinterpret it as current success. Restored data containing current assessments requires a daemon that supports this rule. When every unproven required check has the same concrete reason, the compact source CI summary reports that reason; mixed or missing reasons retain `ci_required_checks_unproven`.

A rerun may retain completed check records from earlier attempts in the same suite. An exact current-attempt job/check match for the same context and App can exclude those older completed records; missing, pending, conflicting or duplicate current evidence remains unproven. Completed skipped or cancelled checks and jobs may contain provider start times later than their completion. Preserve those timestamps without deriving execution duration or attempt identity from them; other conclusion intervals must remain ordered. This exception does not change conclusions: a required cancelled job still fails its gate, while an optional cancelled job cannot invalidate the entire required-check inventory. It introduces no additional provider requests or retries.

Collection is finite: at most 128 required contexts and sixteen relevant workflows, in addition to each provider reader's page, item and response-size bounds. Optional workflows do not cause job-fetch fanout. Exceeding a supported boundary is explicit rather than truncating evidence.

## Stored assessment

`GET /api/v1/projects/{project_id}/reviews/source/{pull_number}/ci`, `fc reviews ci-assess --pr N` and `review_source_ci_assess` require current project read permission and perform no provider work. The local CI assessment reports the refresh identity, selected source, CI commit, observation time, state and compact counts. It checks applicability against current local repository, source configuration and capability binding and the latest stored source comparison. A changed head or base cannot inherit earlier CI success. Full typed inventories are private retained evidence with a bounded storage budget, separate from the ordinary response. Source-policy assessment and latest-comparison checks read source metadata without selecting or decoding that CI inventory. Invalid unrelated CI evidence cannot block source-policy assessment; explicit CI assessment and complete operation reads still validate their selected retained CI strictly and fail closed on corruption.

Current assessment clients send exactly one `X-FC-CI-Watch: change-v3` header to request optional retained `merge_base_mismatch` identities. This read also accepts `change-v2`; absent, duplicate or other values retain the legacy response without those identities. This is a projection opt-in, not a watch handshake or wait: no acknowledgement header is required, and an older service may omit the optional facts. The exact PR-base, live-base, test-merge and merge-base-parent SHAs remain subject to the same comparison and privacy validation.

For the names behind those counts, use `fc reviews ci-assess --pr N --diagnostics`, MCP `review_source_ci_assess` with `diagnostics:true`, or the same GET with `?diagnostics=true`. This adds `checks`, at most 128 retained required-context outcomes: context, required App identity, original state/reason and selected `check_run` and/or `commit_status` facts. A CheckRun exposes its real ID, status and conclusion; a Commit Status exposes its real ID and state. A successful native check can therefore appear beside a pending same-name status without conflating the two. Missing or ambiguous result identities remain absent rather than fabricated. No raw logs, target URLs, optional-workflow inventory, provider fetches, CI reruns or durable writes are added. The explicit response budget is 512 KiB; ordinary reads keep their existing compact 16 KiB client budget and omit `checks`.

These details belong to the same retained refresh, selected commit and observation time as the outer assessment. They never override an outer `held` applicability result or reinterpret original evidence. An empty list under an unproven authority still means unknown requirements, not a passing empty set. Previously collected results remain as-of facts; diagnostics do not refresh them.

States distinguish satisfied, failed, pending, unproven and not required. Review-channel coverage remains a separate [policy assessment](review-source.md#local-assessment). Neither assessment authorizes a merge. The separately selected [readiness assessment](review-readiness.md) combines applicable retained observations with current local policy.

## Retained timestamps and clock correction

Fresh CI ingestion checks the bounded collection interval and current-time upper bound before adopting a provider result. Reading retained CI validates each nonzero timestamp and immutable source/target/inventory bindings independently; it does not compare historical observations with the host's current clock or a later evaluation timestamp. A backward clock correction cannot turn otherwise valid stored evidence into unavailable storage. Observation age remains informational, and timestamps do not replace current workflow or source identity checks.

Regressions reproduced retained future-dated source/CI reads and typed assessment rejection, then passed without changing stored timestamps. Fresh future observations and malformed or mismatched retained facts remain rejected. Focused CI/routes normal and race tests plus vet passed; no host-wide clock change or live provider behavior is claimed.

Agent CI assessments explain `ci_merge_identity_unproven` and `ci_merge_pending` without changing their state or credit. A matching GitHub test-merge identity must be available for the observed head/base before its check results establish that comparison. Wait and recollect the matching comparison; do not create a no-op commit or rerun workflows solely to bypass the refusal. These explanations are adapter output, not additional provider work.
