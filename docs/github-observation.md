## Lifecycle and CI

Passive Hosted-history collection validates the selected provider's publications and visible review commands strictly. Contradictory timestamps on unrelated issue comments do not discard independent provider-owned review history. Those raw comments remain retained, and their ambiguous chronology prevents native trigger hints from being inferred; native execution attribution keeps its existing strict validation.

The service observes existing enrolled, visible PRs without an agent maintaining the dashboard or a visitor pressing Refresh. [Execution configuration](review-execution.md#operator-configuration-reference) creates that enrollment and display order atomically, including unknown-metadata placeholders; agents do not separately enroll the PR in the website. Ordinary agent and browser reads remain provider-free. Committed observations reach connected browsers through the existing project event feed.

One scheduler serves configured projects through separate lifecycle and enrichment lanes, with two reserved workers for each lane and at most four workers in total. Each lane has independent project/PR fairness and at most one in-flight observation per project and provider account; the same account can therefore have one lifecycle read and one enrichment read concurrently. A blocked CI or Hosted collection cannot consume the lifecycle workers or delay the remaining metadata sweep. Default lifecycle intervals are one minute for open PRs, five minutes for closed PRs and six hours for merged PRs. Enrichment has its own schedule at those intervals and becomes eligible when the lifecycle lane observes a different comparison. Required CI is collected every five minutes and after a changed head or base comparison, using its own collected-comparison marker rather than the latest cheap head check. Provider throttling and transport failures share one bounded account backoff across both lanes. A successful in-flight read on the other lane does not clear an unexpired cooldown. An incomplete or ambiguous external inventory retains a per-PR diagnostic and normal retry cadence; it does not delay other PRs or projects on that account. A local publication overload reduces the external append batch rather than retrying the same oversized transaction indefinitely. Preparation stops once it has that batch's new results; a later tick skips their retained identities and continues without advancing the discovery frontier. If necessary, that tick publishes lifecycle metadata alone and leaves external results for a later tick, with a per-PR incomplete-inventory diagnostic. Provider reads are retained across local retries; the two-second write deadline and 100-run maximum do not increase. Collection is cancellable; shutdown joins the workers. These intervals describe eligible polling, not a promise that a provider outage or a busy account finishes within that interval.

Repository identity, current enrollment, capability binding and visible/nonretired state are checked before provider work and again before publication. Lifecycle polling publishes only fresh PR metadata; it never waits for CI or Hosted collection. Enrichment independently re-reads the repository and PR, then requires the retained comparison and pinned display facts to remain unchanged before publishing CI or external history. An old-head result cannot move the queue back after a concurrent lifecycle update. Each lane merges only its own health fields, preserving the other lane’s later successful checks. Publication preserves concurrent evidence, queue order, old snapshots and explicit public enrollment. A poll never enrolls or reactivates a PR. Identical observations produce no snapshot or event. A moved comparison cannot retain an inherited passing CI status. Unproven CI remains unknown.

Malformed stored execution configuration holds only its project, and malformed retained PR lifecycle or optional display metadata holds only that PR with a local diagnostic and ordinary retry cadence. Neither creates provider-account backoff or permits publication from the invalid state. SQL failures and corruption of shared history authority still stop the worker. A local native-identity read deadline holds that Hosted candidate; parent cancellation and genuine storage errors still propagate.

Authenticated conditional GETs revalidate cached response bodies with GitHub. The cache is isolated to the adapter's credential and bounded to 256 entries and 16 MiB; it never supplies an unvalidated stale response or caches a write. Its cadence, cache and backoff are process-local. Restored provider holds prevent observation until the operator releases the restored installation.

Automatic CI uses the repository default branch's required-check gate, including for stacked PRs whose actual base has no required checks. The collector evaluates those requirements against the unchanged actual PR head/base candidate, never a hypothetical merge into the default branch. The queue identifies the final gate and the actual base separately, with the last collection time. Missing authority, missing checks, stale comparisons and provider failure remain unknown; only a proven empty final gate is `not_required`. Explicit retained source-refresh CI assessments keep their selected-base contract.

This replaces the previous selected-base CI read rather than adding a second scan. One final repository read verifies that the default branch selection did not change during collection; all reads share the existing forty-second CI budget. Required workflow fanout, conditional revalidation, five-minute fallback cadence and independent metadata/review scheduling remain unchanged. A formerly empty feature-base gate can now require result and current-attempt reads for the final branch's checks. Collection observes only; it never dispatches or reruns a workflow. Actual base drift retains the collector's existing strict/non-strict rules and never credits a stale test merge. Final-gate labels are process-local observation health: a restart or moved comparison cannot label older retained CI as newly verified final-target proof.

## GitHub webhook hints

An operator can configure `fcd --github-webhook-secret-file ABSOLUTE_PATH` to enable `POST /api/v1/hooks/github`. The secret is a private regular file containing 32–4096 printable bytes, loaded at startup separately from agent credentials. Repository hooks use HTTPS, JSON payloads and that secret; subscribe to `pull_request`, `check_run`, `check_suite`, `workflow_run`, `status` and `push`. A signed ping verifies delivery without queuing provider work. A restore provider hold skips both secret loading and ingress registration.

The handler validates the raw SHA-256 HMAC before decoding a bounded four-MiB body. It emits only stable repository, PR, head and branch selectors. Event statuses are never adopted as CI, review or merge facts. Hints match current configured, visible, nonretired PRs; unknown repositories and unrelated or old-head CI events do not enroll or refresh work. Base-branch push hints select affected stored base links.

Webhook notifications are the primary prompt for refreshed observations. Related events coalesce into the existing scheduler, with at least five seconds between event-driven attempts on each PR/lane. Cheap lifecycle and CI enrichment remain separate, and account cooldowns and concurrency reservations still apply. An event arriving during a collection remains pending for a later check. CI hints can collect before the ordinary five-minute CI interval; fresh provider reads still establish every comparison and result. Ordinary polling recovers missed notifications and temporary delivery failures. GitHub does not automatically redeliver failed webhook requests, so this recovery remains necessary.

The endpoint responds after bounded local hint admission, without waiting for GitHub reads. Successful delivery IDs and payload digests are deduplicated in memory for ten minutes, up to 4096 entries. A failed callback releases its claim for retry; overload returns a retryable failure. Raw payloads and secrets are not logged or retained. Restart clears hint and dedup state, while normal polling and retained observations remain available. Use GitHub’s delivery history for delivery-level diagnostics.

## Freshness in ordinary reads

Current CLI/MCP and browser queue reads request `include_observation=true`; the queue API then returns `observer` runtime state and each enrolled row's `observation`: last attempt, last successful retained lifecycle check, next eligible check, safe retry/error code and separately checked CI/Hosted-inventory times and reasons. These are process-local health facts, reset at startup. The ordinary last-success and next-check fields describe the cheap lifecycle lane; the top-level error prefers a lifecycle error and otherwise reports an enrichment failure. CI and Hosted timestamps/errors describe independent enrichment collections and do not overwrite lifecycle success. An unchanged successful poll advances these check times without a new immutable snapshot, event or history row. CI and Hosted diagnostics describe their own collection; a Hosted read skipped because CI encountered a provider cooldown does not advance its check time. Unsupported or malformed PR inventory remains a local diagnostic and does not impose account-wide backoff; actual transport failures and provider cooldowns retain shared backoff. `observed_at` remains the snapshot origin timestamp and must not be interpreted as the last automatic check. A restarted observer reports waiting until it has checked the PR; a stopped/unconfigured observer, a retry/backoff, an overdue check, a different comparison and an unenrolled row remain distinguishable. Unknown CI with a successful collection means the required-CI evidence was unproven, not that the worker must maintain the queue manually. Ordinary reads make no provider calls.

## Hosted reviews started outside FireController

Completed CodeRabbit reviews started directly on GitHub are discovered automatically for those same enrolled PRs. Discovery only reads GitHub. It never posts a review command, queries review allowance, launches a CLI process or creates a controller execution attempt. Deferring review work or enabling the operator's review-request pause does not disable this observation.

Stable numeric bot identity and actor kind establish the provider; the login is display text. Collection must be complete within its finite page, item, byte and time budgets. Discovery groups actual provider publications and run IDs rather than inventing a FireController request or using a matching head as proof of ownership. Inline roots, outside-diff findings and duplicate sections retain their source identities. Replies and empty review acknowledgements do not become rounds. Each observed run keeps its actual reviewed head, including a head that is no longer current. A mutable standing summary exposes the run still present when collected; polling cannot reconstruct a summary that GitHub has already overwritten. Unsupported provider formats remain unproven rather than being guessed.

External runs are appended under a separate GitHub producer to the normal retained Hosted history and finding views. Repeated observation and restart do not append another copy. Native-owned reviews are reconciled against actual retained operation, attempt and trigger identities; a pasted marker alone cannot hide an external review. Incomplete or unsupported inventory is deferred and retried rather than appearing as a clean zero-finding review. Once a supported complete inventory is retained, later collection does not overwrite its captured text, decisions or history. The two run timestamps identify provider publication; the observer does not claim to know execution start time or runtime.

When the observer and native executor retain the same provider publication, current views count it once using the native run and its adjudication. Reconciliation requires the exact captured provider publication or run identity and the same project, repository, PR and reviewed head; matching titles, timestamps or heads alone are insufficient. The native replacement must already be current or be staged in the same transaction before the observer membership is closed. Native publication, publication replay and subsequent observer collections reconcile either arrival order, including duplicates retained before this behavior was installed. The original observer payload, findings and historical snapshot links remain inspectable; no review credit, decisions, routes or fixes are transferred from the observer record.

Later provider edits can make a previously captured publication's finding text unsupported. Exact ownership established through the validated native capture still permits reconciliation without importing that edited inventory. This does not alter the original captured result or credit. Unknown incomplete groups remain held, as do ambiguous or mismatched identities. A new external import requires a supported complete inventory; a marker alone cannot establish native ownership. A confirmed native request explicitly cancelled as `operator_abandoned_pending` relinquishes its native ownership only when it has no final native evidence. A later supported result follows this same external archive path, preserving its actual provider identity, original reviewed head and undecided findings even after the PR advances. It does not reopen the cancelled attempt, reserve work, request another review or earn native completion, taper or allowance credit. Other cancellation reasons retain their existing reconciliation holds.

On first observation of a PR, the service freezes a durable discovery frontier from its latest already retained non-observer Hosted completion, before making provider calls. Automatic discovery considers later results. The frontier never advances when a new native review completes or the service restarts, so late-arriving external results remain discoverable. Existing older history remains retained; historical gaps before that frontier use explicit collection/import rather than duplicating imported runs whose original provider IDs were not retained.

Unknown provider groups with a valid finish time at or before the frozen discovery frontier are outside automatic discovery, including unsupported historical groups. They neither create rounds nor mark current discovery incomplete. Missing timestamps and incomplete relevant newer groups remain explicit diagnostics. Already retained source identities still undergo identity checks and exact native reconciliation on either side of the frontier; the boundary cannot hide an identity contradiction or discard historical evidence.

The browser labels an incomplete Hosted-inventory diagnostic as **Hosted history: Incomplete**, with the last successful PR check in its details. Provider outages and rate limits remain GitHub retry diagnostics. Incomplete Hosted history does not imply that successful PR metadata checks stopped.

Automatic CI observation assesses the selected base branch's required checks, not all current-head workflows. When that requirement set is empty, it records `ci_state: not_required` and the browser shows **Required CI: None**. This is distinct from unknown, passing or failing CI. It does not fetch optional check runs or workflow jobs and cannot report their failures. It publishes observed state; this scheduler is not a separate inbox CI-failure alert service. A repository-owned monitor, if separately configured, needs its own workflow-health contract.

Automatic CI observation uses the same safe failure class and static collector stage as [explicit CI collection](review-ci.md), available in its channel-specific health diagnostic. Raw errors and partial inventories remain private and cannot grant CI success. Account cooldown and ordinary observation cadence remain independent of this diagnostic; reading it never retries collection. Scheduler health is process-local and starts fresh after a service restart.

Each complete external result is retained separately and awaits settlement. Pending external results hold new Hosted work on that PR, including automatic selection and the last check before provider dispatch. The hold names the available result IDs. A queued request for the same PR, including one waiting for cooldown, moves to Held so it cannot spend allowance on a redundant review. A request already posted can finish normally. CLI review remains independent. A hold applies across head changes; the run still describes its original comparison.

### Settle manual Hosted results

Use `fc reviews runs PR` to find pending `github-hosted-observer` results and `fc reviews run RUN_ID` to read each retained finding. After checking the findings and fixing accepted ones, use `fc reviews settle-hosted --pr PR --file PRIVATE_JSON --key KEY` or MCP `review_external_hosted_settle`. Supply `count_round` and 1–10 distinct `runs`. Each entry has a `run_id` and a `findings` array (empty for a verified zero-finding run). Each finding uses its `source_finding_id` as `finding_id`, an explicit accepted or rejected `disposition`, and a nonblank `reason`. Accepted findings require a full lowercase `fix_sha` and `proof_note`. A batch supports at most 100 findings in total. The agent can settle a larger set in smaller batches.

The project writer settles the selected original results atomically. With `count_round: true`, the entire batch consumes one available Hosted round and contributes one taper observation. Any accepted finding resets the clean streak. Use `count_round: false` to settle a batch without changing allowance or taper, including when its channel is already closed or has exhausted its grant. Unselected results remain pending. An already settled run or a result owned by native execution cannot earn credit again. Exact-key retries recover the original receipt. A failed credit request leaves every selected result pending, so the agent can recover with the same key or deliberately submit a new request without credit after a confirmed refusal.

Settlement uses the original immutable history and local review accounting. It creates no execution attempt, provider request or public review comment. A counted and settled batch supplies earned Hosted channel completion for that PR, while its retained findings and reviewed head stay attached to the original runs. Current CI, review threads and merge readiness remain separate. A full administrative history replacement must settle pending verified results first so it cannot erase them.

Independent CLI runs are local to the machine that runs them. They are not discoverable through GitHub and need an explicit submission/import path; CLI reviews requested through FireController already retain their results normally.

## Proof boundary

Focused proof covers multiple provider groups, stable identities and forged actors, zero and positive inventories, replies, partial collections, repeated observations, restart, old heads, native/external deduplication and immutable frontiers. Real existing GitHub results may be read for qualification; no new review is required or authorized by this feature.

## Review schema lineage compatibility

Reviews version numbers 10 and 11 were historically assigned in two orders. Main version 10 installed completed-channel counters; the external-observation review slice added discovery as version 11. Integrated development installed discovery at 10, Delivery selection at 11 and completed-channel counters at 12. Equal older version numbers therefore do not establish equal physical schemas.

Integrated startup recognizes those specific predecessor layouts inside the same exclusive transaction as normal migration and backfill. It checks the exact retained pull-table/read-view definitions and the discovery table/index pair. Main-v10 receives the missing discovery prerequisite before normal migrations; slice-v11 receives the missing Delivery column and view before completed-counter migration. Integrated-v10/v11 follow their existing migration sequence, and a canonical integrated-v12 is unchanged. Retained source records, Delivery selection and frozen discovery frontiers are preserved. A pending migration failure rolls the prerequisite repair and version changes back together. Incomplete or unknown layouts are refused, not guessed or rebuilt.

This is an integrated-startup compatibility path, not a rewrite of published slice migrations or permission to downgrade an integrated database into a review-slice binary. Read-only backup inspection does not run this bridge, and existing backup-format acceptance is unchanged. This startup database compatibility path does not establish direct inspection or restore support for pre-upgrade main-v10 or slice-v11 backup bundles. The backup tests qualify only bundles created after successful conversion to the canonical integrated schema. Controlled fixtures cover actual predecessor migration sequences, unknown-layout refusal, rollback, current-v12 no-op behavior, and canonical backup creation, inspection and inactive restore after upgrade. No live database migration or deployment is implied by those tests.
