# Worker contact and attached clients

## Implementation status

The service, typed CLI/MCP clients and Delivery contact indicator are implemented in source. Focused normal/race checks cover authentication, bounded memory, concurrent request cancellation, restart, read-only state conservation and an actual quiet TCP stream outliving its short authentication deadline. Actual packaged CLI and MCP waits show attached contact, then detach after cancellation with last contact retained and no wait-owned writes or model-facing heartbeat output. Browser API/component checks and integration proof cover the displayed boundary. These local Linux checks do not establish Windows abrupt-disconnect behavior, physical-phone acceptance, installed contact behavior or fleet capacity. Lane order remains based on open jobs and explicit pause state; it does not establish that an agent is running.

## Meaning

Show whether the service has an authenticated agent client attached for a worker, and when it last received an authorized request for that worker. Calls, polls and quiet open waits count. Browser sessions do not count, even when the browser selects an inbox worker. Contact never changes job state, primary focus, pause, messages, acknowledgments or review permission. It is evidence of a client connection, not evidence that a model is reasoning or making progress.

The typed CLI/MCP client generates a random connection ID when it is constructed and sends it on its scoped requests as `X-FC-Session`. IDs are 32 lowercase hexadecimal characters, distinct from project, worker and credential identities. One persistent client retains its ID; a fresh CLI process normally has a fresh ID. The MCP adapter’s owned transport pool retains one connection label across its separately authenticated tool clients; it never retains credentials or profile authority. Several clients for a worker contribute to that worker's contact summary. No repeated agent flags, shared active-profile setting or extra heartbeat tool call is needed. A connection label grants no authority: the service authenticates the credential and checks project and worker membership first. Older clients without a connection ID remain usable and do not claim contact coverage.

## Ephemeral observation

Keep contact in bounded server memory. Ordinary authorized worker-scoped requests update last contact and retain an attached-request lease until their request context ends. Quiet streams retain the actual stream context rather than their short authentication timeout; existing authorization/transport heartbeats maintain the lease. Cancellation and shutdown release leases. No per-poll SQLite writes, durable events, receipts, message changes or provider calls are introduced. A service restart clears observations, so unknown contact must not be presented as proof that an agent stopped. Observations are not imported, backed up or published to the public site.

Keys include project, worker, authenticated principal and client connection. Limit observations to 8,192 keys overall and 256 per principal. Reclaim inactive observations older than one hour, then the oldest inactive observations when needed. Do not evict an attached request to claim another one. Reclaiming an inactive key preserves completeness when an equal or newer observation for the same project and worker remains, including the incoming authorized request. Losing that worker's newest retained contact, or refusing contact admission when every eligible key is attached, makes the incomplete flag sticky until restart. When capacity prevents recording a client, its coordination call still works and the contact summary must not claim complete coverage. Never expose credential, principal or connection IDs in a worker's contact summary.

## Bounded browser read

`GET /api/v1/projects/{project_id}/workers/presence?worker_ids=ID,ID` requires project read access and one list of 1–100 distinct valid worker IDs. Reject unknown/repeated selectors and missing, empty, malformed or cross-project IDs. Resolve membership in one local read transaction before reading the ephemeral observations. Return `project_id`, `evaluated_at`, `observed_since`, `complete` and ordered `items`; each item contains `worker_id`, `attached` and nullable `last_seen_at`. `complete: false` means contact observation was capacity-limited during this server lifetime. Empty observations mean unknown contact, not confirmed inactivity. Reads never contact a provider or modify durable state.

Delivery requests contact for up to 100 loaded workers in stable ID order, shares that query across lane consumers, and refreshes it at most once per 15 seconds while the page is visible. Larger appended boards keep all their lanes; contact outside this bounded selection remains unknown rather than causing an automatic fleet walk. It does not reread the jobs board, reviews or histories to refresh contact. Keep labels compact: “Client attached”, a relative last-contact age, or no contact indicator when unknown. The detail tooltip explains the server's observation window and incomplete coverage. Contact is separate from the existing job-state lane ordering; an attached worker with parked work does not imply that its jobs became active.

## Focused proof

Prove independent projects and principals, browser exclusion, invalid and duplicate connection headers, old clients without a header, overlapping requests from one client, simultaneous distinct clients, cancellation, quiet wait lifetime, revocation, restart and bounded-capacity behavior. Verify that requests, presence reads and long waits leave durable state and message acknowledgment unchanged. The browser must handle unknown/incomplete contact, pause/job-state independence, visibility and project switches, late responses, authorization failure and cancellation. Packaged client/server proof must demonstrate contact during a real quiet wait without adding model-visible heartbeat output.
