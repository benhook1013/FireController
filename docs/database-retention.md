# Database retention

Database maintenance runs every six hours by default, with one non-overlapping pass per daemon. Its first automatic attempt waits the shorter of the configured interval and five minutes after startup. A configured backup phase lease is acquired without waiting; when a backup or deployment holds it, the entire pass is skipped without a report. A busy-lease skip before the first actual pass retries after that same short delay. After the first actual pass, including a failed pass with a report, the worker waits the unchanged configured interval between attempts. Each deletion transaction visits up to 500 rows, yields between batches, and never runs a provider call. The most recent completed pass reports timestamps, dry-run mode, per-table counts and a safe error category in metadata key `retention:last_pass`. In dry-run mode the counts are eligibility estimates from the current database, not deleted rows. The pass writes its report but does not advance a history floor, delete any history, or reclaim pages.

Use `--retention-interval=0` to disable the worker. The daemon accepts positive Go durations for `--retention-review-history`, `--retention-job-history` and `--retention-receipts` (default `720h`, thirty days), and `--retention-diagnostics` (default `336h`, fourteen days).

The review history floor is the newest existing immutable snapshot at or before the horizon, independently per project. The observed floor snapshot is already committed. Maintenance confirms its persisted revision, durably raises a single monotonic `retention:review_history_floor:<project_id>` before destructive batches, and then collapses visibility intervals at the floor without changing the snapshot's bytes or identity. Older snapshot IDs and their cursors return the existing unavailable response even when a physical snapshot remains for proof. Interrupted execution resumes from the published floor; the visible window never exposes partially collapsed older data. Current and at-or-above-floor historical reads are unaffected. Referenced immutable versions and snapshots remain, including run and attempt identity, first native finalization, retained finalized findings, and original external Hosted capture evidence. Only an actually discarded snapshot's matching `review.observed` events are removed; other events remain.

All jobs retain revision 1, the latest twenty distinct revisions per owner and rows within the horizon for their full-state history, progress, summaries and deferred note revisions. Progress retains every entry attached to those newest twenty owning job revision values and every revision-1 entry, independent of archive sequence. An in-window progress entry protects its entire owning revision; the current progress evidence also protects its owning revision so backup validation remains intact. Current state and valid retained history do not require older revisions to be contiguous. Idempotency receipts expire after their horizon; each migrated receipt receives a migration timestamp, not an invented original receipt time. See [local API idempotency](local-api.md#mutation-keys-and-retries) for retry behavior. Selection diagnostic history uses its last-observed time. No execution tables, imported collection data, inbox, capture files or backup cadence are pruned by this worker.

## Rollout and recovery

Daemon startup and `fcd migrate` install composite indexes for review history's snapshot references. These let retention check references within the normal bounded write budget. The index upgrade adds no history rows and preserves the review data format.

For the first authorized deployment, use `python3 tools/deploy/deploy.py --retention-mode dry-run`. This explicitly adds the daemon flag through the normal deploy. Do not confuse this with the deployment tool's separate build-only `--dry-run`. Routine deployments omit `--retention-mode` to preserve the existing daemon setting. Check the first non-skipped dry-run status before authorizing a deploy with `--retention-mode enabled`. The worker skips any scheduled pass if deployment or backup still owns the lease; do not bypass that lease to obtain a report.

Startup and `fcd migrate` perform a one-time SQLite conversion to incremental auto-vacuum before serving. This conversion is a physical database rewrite even if the retention worker is in dry-run mode; predeploy rehearsal tests it on the snapshot copy. Provision temporary disk headroom and retain a compatible pre-conversion backup and binary; subsequent startup does not repeat it. A non-dry pass uses bounded incremental vacuum calls after pruning. Verify the first live report against database and backup size, SQLite quick check, and managed backup inspection. Source-only tests do not establish live size or growth results.
