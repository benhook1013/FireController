# Native Review Execution

## Implementation status

Native execution is the active delivery boundary. The [stored workspace and bound read tools](review-workspace.md) work independently; development reviews still use a separate executor until the native adapters and recovery paths pass their checks. This document owns the implementation boundary for replacing that executor. The [review contract](reviews.md) owns identity, admission, evidence and policy requirements.

The daemon accepts an optional private operator catalog for CLI, hosted, or both review channels. Configured capabilities compose fresh selected-source checks, immutable Git workspaces, account/target reservations, capture retention and native browser publication. Without a catalog, coordination and stored evidence controls run without provider workers. Requests return durable receipts before background work; terminal attempt state alone creates no review credit.

The concrete CLI pipeline checks actual changed files, fresh included allowance and pending evidence before its one-use process action. The hosted pipeline journals a fixed non-review allowance query, checks attributed availability and provider activity, posts one admitted fixed review command, and retains complete observations before interpretation. Restart observers recover only originally bound issued work and never repost. Local finding decisions, guarded fix proofs, finalization and explicit captured-comparison policy assessment use the shared immutable evidence ledger and [bound evidence controls](review-controls.md).

Both CLI and hosted daemon pipelines have packaged controlled-provider proof. Hosted source, allowance, dispatch and recovery also have standalone and focused race proof. Explicit [source refresh and observed policy](review-source.md) reuse source selection and native coverage without starting a review. Live CodeRabbit execution, full review cutover, routing, required-CI assessment, public checkpoint publication and fleet throughput remain unproven or unimplemented.

Focused race tests cover duplicate requests, concurrent reservations, independent channel/account slots, revocation and configuration changes before dispatch, retained trigger intent, interrupted preparation versus possible execution, malformed results, bounded SQL cancellation, strict provider pagination and captures, and process interruption/output limits. The full repository check/build passed. Separate live checks verified real GitHub response shapes and complete collections, fetched and verified pinned public Git objects, and obtained a real CLI allowance observation from the isolated workspace without starting a review. These establish adapter behavior on Linux/WSL, not completed native review execution, deployment cutover, fleet performance or other-platform runtime support.

### CI provider observations

The GitHub adapter implements independently bounded read boundaries for the next required-CI slice: PR/test-merge identity, applicable branch requirements, an exact commit's check/status inventory, all Actions runs for that commit, and a selected check suite's current numbered attempt. Each uses a fifteen-second aggregate deadline with five-second individual requests. Collection work shares finite page, item and byte budgets; missing permissions, partial collections and ambiguous identities cannot become empty passing gates. These readers are internal components. They are not yet connected to a service refresh, agent command, required-CI evaluator or merge-readiness assessment.

Requirements combine classic branch protection with every applicable active branch rule, retaining exact context and provider-app identity. Unknown integration gates remain unproven. Check inventory explicitly requests all runs and retains commit-status history. GitHub's [commit check-run endpoint](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference) limits its view to the newest 1,000 suites; suite-count observations guard that boundary instead of presenting provider truncation as complete history. At that boundary the initial adapter refuses the inventory. It does not launch an unbounded per-suite walk.

The candidate reader observes the selected PR before and after inspecting its test merge. A verified merge binds exactly two distinct parents to the observed base and head without assuming parent order. Pending merge computation and identity movement remain unproven. A conflicting merge retains head/base facts without establishing merge readiness.

The Actions readers bind repository identity, head, suite, workflow, run, event and numbered attempt. A head-scoped inventory includes all workflows and suites, so a newer run in another suite is not hidden by the selected-suite query. It retains workflow-scoped run numbers and refuses GitHub's 1,000-result filtered-search boundary. The attempt reader obtains complete numbered-attempt jobs and rechecks the run afterward; movement leaves the observation unproven. It neither guesses currentness from timestamps nor treats an older successful job as the current attempt. Selecting the latest applicable workflow, carrying forward jobs after a partial rerun, selecting head versus test-merge CI, combining required contexts with results and storing a service assessment remain integration work.

Focused HTTP and race checks exercise origin ambiguity, retry identity, malformed records, collection boundaries, cancellation and pagination scope. A separate read-only live check verified these adapters against selected public PR and immutable commit facts in about 7.1 seconds, including the suite-count guard, requirements, check/status history, complete head-scoped workflow inventory, attempt-specific job-to-check identity and test-merge parent binding. That limited check did not evaluate CI satisfaction, trigger a workflow or establish fleet performance.

## Ownership and fast requests

The service owns review admission, provider work, retained artifacts and attempt recovery. An agent supplies its bound project plus an expected PR, channel and candidate head; it never supplies a GitHub credential, executable path or mutable working directory. Ordinary queue, job and inbox reads remain provider-free.

A review request validates local arguments, authorization and configured capability, records a durable request and returns a compact receipt before provider preflight. Provider reads, Git preparation and subprocess execution occur under supervised background workers. A waiting adapter follows that operation through the service; an explicit detached request exposes the same receipt for recovery. A lost tool response does not imply that no request or external action happened.

Queued requests, external attempts and completed review evidence are distinct records. A request can be held before any action. An external attempt records preparation, possible posting or process start, active work, and a proven terminal or uncertain outcome. Its retained transition history identifies the actor, expected head, admitted comparison, configuration revision, provider account and external identifiers. Reusing an idempotency key with the same request returns its original receipt; changing the request conflicts.

Each local attempt mutation records one effective UTC timestamp shared by its operation update and transition. It cannot precede valid retained operation or attempt chronology, including after restart or a backwards wall-clock adjustment. Malformed retained timing is rejected without changing the journal. Effective recording time does not establish physical elapsed duration or adjust provider, capture or source-observation timestamps; their attribution and freshness checks remain separate.

## Bound execution tools

Use the existing private profile for these commands; project and worker are inherited from that binding:

```sh
fc reviews execution
fc reviews request 42 --key review-42-cli-a1 --expect-config 3 --channel cli --head 0123456789abcdef0123456789abcdef01234567
fc reviews operation review_operation_0123456789abcdef0123456789abcdef
```

`reviews execution` reads stored project configuration and its revision without checking provider availability. Missing configuration returns `reviews_unconfigured` for reads and requests; `review_not_configured` identifies a selected PR or channel outside the stored configuration. `reviews request` explicitly authorizes background review work against the selected PR, channel, candidate and configuration revision. Its compact receipt contains only operation ID, initial `queued` state and revision; it does not mean a review started or completed. `reviews operation` reads current retained state and its stable reason. Reads make no provider calls and do not poll automatically.

The corresponding MCP tools are `review_execution_read` with no fields, `review_operation_read` with `operation_id`, and `review_request` with `idempotency_key`, `expected_configuration_revision`, `pull_number`, `channel` and `head_sha`. Only the request tool authorizes external work. All calls use the shared five-second client budget; server preparation and execution continue independently of the request connection. Invalid selectors fail before loading credentials or contacting the service. After an unknown response, recover with the same explicit key and exact request; neither interface generates a new key or automatically retries.

`GET /api/v1/projects/{project_id}/reviews/execution/configuration` returns stored `project_id`, `revision`, `capability_id`, `mode`, `queue`, `channels` and `paused`. It is a project-scoped read with instance/authorization checks, including when no runnable capability is installed. It exposes no account credentials or private paths and makes no sufficiency or CI assertion.

## Operator capabilities and project configuration

Private startup configuration supplies named provider capabilities: the GitHub credential reference, CLI executable and its protected authentication context, and explicit provider-account scheduler identities. These are operator-owned settings. Project administration selects permitted capability IDs and channels, queue mode/order, required channels and allowed source configuration through revision-guarded service records. New requests bind both their execution configuration and current project-policy revisions. Local preparation, admission and the final action guard recheck those bindings, actor access and channel pauses; older unbound requests remain held. Project content and worker requests cannot select arbitrary server files, environment variables or commands.

Each queued operation retains a fingerprint of its selected capability, including the configured provider account, channel set and private authentication context. Changing that binding holds old queued work; it never silently adopts a replacement account or credential. Existing unbound operations from the earlier journal schema are retained and held. Replaying an already successful configuration or request key returns its original receipt after local capability changes, subject to current caller authorization; a new action requires a new explicit request.

The catalog is versioned strict JSON, limited to 64 KiB and 32 named capabilities, read from an explicitly selected private regular file. It accepts operator-owned Git/CLI executables and an allowlisted map of authentication home/configuration directories. An optional GitHub credential-file reference resolves relative to the catalog; the token is required for hosted posting and is never passed to the CLI. There is no shell or environment-expression expansion. Safe metadata and formatted diagnostics omit private paths and credentials. Select it explicitly with `fcd --review-catalog /private/path/catalog.json`. Capabilities select `cli`, `hosted`, or both; each channel uses its own driver and reservations with no cross-channel fallback. A hosted-only capability requires no CLI executable. Hosted settings bind provider identity and the explicitly configured progress surface as described below. The default empty catalog starts no provider worker or review polling loop.

The service obtains source through the verified project repository and creates its own bare object cache and per-attempt immutable workspace under its private data directory. A developer checkout is not the execution workspace. Git commands disable ambient hooks and configuration; source preparation does not execute repository install/build hooks. The CLI receives a minimal explicit environment and only its required authentication context, never the service's GitHub credential or another project's profile. This is a trusted local executor capability, not a hostile multi-customer sandbox.

One service process supervises two global work slots. Startup validates driver bindings and commits interrupted-attempt recovery before accepting HTTP requests; asynchronous worker completion has a single retained result. Shutdown cancels owned work and waits within a finite budget before closing storage. Account and exact-target reservations allow at most one active action per provider account and channel and exclude another action against the same repository, PR and channel. Finite deadlines bound each action. One project can occupy both slots; per-project scheduling fairness is not implemented. Coordination remains usable when provider work is slow or unavailable. Multiple active service replicas and remote executors remain outside this delivery.

## Admission and provider boundaries

Resolve the selected project repository by its stable identity and obtain its current canonical name. Refresh the selected PR and the predecessor/default-base facts required by the configured queue; do not refresh unrelated queue members or recapture completed evidence on every request. Cached observations retain time and completeness. Provider pagination must terminate completely before a collection can support admission.

The expected PR/head are assertions. Admission verifies current lifecycle, repository identity, candidate head, effective parent/base and canonical patch identity, applicable active-provider activity, operator stops, required fresh facts and observed account allowance. It records the exact evidence used. A mismatch or incomplete fact holds the request without falling back to another PR.

Before an external action, atomically reserve `(provider, repository_id, PR, action_class)` and retain the attempt intent. Provider-account scheduling is separate from that target reservation. Conflicts remain opaque across project grants. Recheck the external target at the final action boundary; record the admitted identity even if a later provider result belongs to an older head. No provider call or subprocess wait occupies a database transaction.

Hosted and CLI channels have independent cycles and allowance observations. Exhaustion or activity in one does not hold the other unless a real shared reservation or account resource applies. No adapter purchases credits, seats or overage, or selects paid execution after an included allowance is exhausted. Unknown allowance or an ambiguous action remains an explicit hold/uncertainty.

When native projection is enabled, each journal transition updates its browser attempt in the same transaction. Preparing and held are distinct states; held attempts retain their actual stop time. Interrupted active or posting work becomes uncertain without an invented finish time. A missing current PR observation leaves the transition ledger-only; a trusted fresh observation can establish that first row. Publication preserves current PR facts and imported history, and exact replay creates no new snapshot. Initial metadata is a fallback inside the publication transaction: if another observation creates current PR facts after a missing-row read, those current facts take precedence over the prepared fallback. If retained attempt capacity is already full, the request is durably held before creating an attempt or reservation. If a later administrator observation replaces the snapshot, omits the live native attempt and fills its capacity, automatic transitions remain ledger-only; they neither copy snapshot rows nor block execution or restart recovery. Existing native rows still update at capacity. Explicit publication retains its atomic capacity refusal. Other projection failures roll back the journal transition as well.

Attempt settlement retries only the same guarded local journal transition within a finite budget. It reconciles an already committed transition before retrying and never repeats provider dispatch. If the outcome cannot be recorded, the supervisor reports a failure, cancels its other work and retains reservations for inspection and recovery.

## Hosted adapter

A hosted attempt records its exact command body and unique intent marker before posting a GitHub comment. Retain the returned comment ID and posting time. On a lost response or restart, search the complete scoped provider history for that intent before deciding whether posting occurred. Never blindly repost an uncertain request.

The implemented trigger helper generates only the fixed full-review command and a versioned marker binding operation, attempt and exact head. Its pure recovery resolver consumes an explicitly complete scoped comment collection and the configured posting actor's stable numeric identity and kind. It can identify one exact, unedited command in the known posting window. Missing or partial history remains uncertain; duplicates, edits and contradictory attribution remain ambiguous. Neither state permits automatic reposting, and adoption establishes a trigger only, not completion or review credit. This helper has focused normal/race proof.

The scoped hosted observation adapter reads every page of reviews, review comments and then issue comments under one 15-second budget, without posting or retrying. Reading command history last includes competing triggers that arrived before an observed publication and closes attribution to an earlier trigger. Only a successful complete collection receives an observation time; a failed later collection preserves earlier complete collections for diagnosis. The reply-parent identity distinguishes attached roots from replies. Current and original multiline coordinates and diff-side metadata are preserved; missing/null metadata stays unknown rather than inheriting another location. Combined observations are bounded to 10,000 items, 64 KiB per body and 16 MiB of body text.

The pure publication resolver recognizes explicit version-1 publication markers in the configured provider actor’s reviews, bound to the exact trigger window and head. Review submission must be strictly later than the trigger timestamp; equal timestamps cannot prove their order. Every batch must agree on publication identity, provider attempt and total, and the primary actionable-comment count must match attached roots with the same actor and original head. A later review/resume command closes attribution for the earlier trigger. A non-provider comment edited at or after the trigger also closes its attribution window, even if the current prose no longer contains a command; its original body cannot prove absence of a competing request. Missing batches remain active; contradictory or malformed evidence remains ambiguous. Markerless reviews cannot establish completion. Original batch/root bodies and eligible summary bodies remain available, including unclassified outside-diff text. An attributed inventory is not extracted findings, completed review coverage, allowance or merge readiness. Focused real-HTTP tests prove pagination, shared deadlines, partial failures and cancellation; pure resolver tests prove attribution and inventory checks.

CodeRabbit can also publish a zero-result review by editing its standing issue comment without creating a new review object. The supported standing-summary format requires an explicit empty inventory, provider run UUID, exact full comparison, matching current-head coverage marker, validated selected/ignored file counts, configured provider actor and a finished-command reply within the trigger window. The observed root coverage envelope accepts the `Low` and `Minimal` labels. An absent ignored-files block denotes zero only when the next block is a valid selected-files inventory; present ignored blocks remain mandatory to validate in full. Selected files remain nonempty, counted exactly, valid and unique across both lists. Raw bodies remain in the immutable private capture; public evidence exposes only the real summary comment ID, provider run UUID and edit time alongside the trigger and comparison. It fabricates no GitHub review, publication or provider-attempt identity. Unknown or competing findings and partial batches cannot fall through to this zero-result path. A bare “Full review finished” acknowledgement cannot prove an empty inventory, including when an older clean publication exists.

A current standing-summary body alone does not prove a new review. Before retaining final evidence, the runtime checks the latest qualifying immutable pre-review capture for the same allowance query, attempt, source and actors, completed no later than the exact local admission timestamp retained in the journal. Once allowance is available, preparation captures all three complete provider collections before admission; pending allowance checks continue to fetch only their issue-comment history. Query-only captures cannot prove a complete standing-summary baseline. The new provider run UUID must be absent from its provider-owned comment and review bodies. Missing, mismatched or incomplete baseline facts retain the raw observation without final credit. Provider trigger matching retains GitHub's whole-second boundary; baseline ordering uses the local journal's nanosecond timestamp so fast preparation does not require an artificial delay. Standing-summary evidence still requires explicit settlement, finding finalization and the ordinary exact-comparison coverage checks.

A private hosted capture store retains successful complete scoped collections even when their publication is active, uncertain or ambiguous. Each versioned record binds repository, PR, local attempt/intent, both actors and the measured observation window, preserving original bodies and location metadata. Observations are immutable and content-addressed: exact replay returns the same reference, while later observations for one attempt create additional records. Atomic no-replace publication, file/directory synchronization, private permissions, strict reference-checked reads and an additional 48 MiB encoded-record ceiling bound this component. The store neither polls nor lists provider observations. The trusted runtime journals each correct-target reference before interpretation; recovery reads use that durable index rather than scanning artifact filenames. The same bounded journal explicitly distinguishes allowance-query captures from admitted review observations, retaining complete pending, cooldown and unsupported query histories even when preparation is held. Query references bind the original query anchor and intent; they establish no final evidence or review credit. Real-filesystem race tests cover replay, reopening, corruption, cancellation and private-file boundaries on Linux. Live provider, broader crash fault injection and native platform proof remain separate checks.

The finding decoder resolves publication attribution again, then extracts individually fingerprinted inline, outside-diff and duplicate findings from recognized source structures. The primary actionable count counts attached root comments; one root can contain multiple atomic findings. Summary category counts and per-path duplicate counts are checked separately. Unsupported formats, missing fingerprints, conflicting counts or more than 100 findings retain an incomplete inventory without invented placeholders. Full finding titles, paths, explicit severities, original location metadata and literal detail spans remain separate from nested examples and agent prompts. Bounds are 500 bytes per title and 16 KiB per detail. The final evidence input also has a 2 MiB canonical JSON budget, including escaping. An individually valid hosted inventory that exceeds that aggregate budget remains a raw retained observation with `finding_inventory_limit`; it receives no final evidence slot, fabricated counts or completed coverage.

The trusted hosted retainer saves and reference-checks the private observation before interpretation. A final capture additionally requires exact attempt/repository binding, complete atomic inventory and an explicit provider declaration of the full PR comparison ending at the admitted candidate and beginning at its effective parent or merge base. Unknown or conflicting declarations stay unproven; attribution to a head alone does not establish that scope. Only proven final results enter the shared immutable evidence ledger. An incomplete observation remains a raw retained reference and does not occupy the attempt's unique final evidence slot, allowing a later complete observation to be interpreted. Retention does not post, settle an attempt or publish browser state. The durable reference journal preserves incomplete and final observations across restart, with exact replay and a bounded 200-reference limit per attempt. It validates the admitted intent, anchor, channel and capability identity without advancing execution or adding final evidence. The configured daemon owns admission and scheduled observation recovery.

The trusted one-pass recovery path reads the original admitted attempt and capability binding, resolves its stable repository ID to the current canonical read URL, and retains complete scoped observations before adopting an exact trigger. The posting window comes from the retained admission transition, floored to GitHub's second precision. Incomplete or ambiguous evidence retains its reservation without a repost. Proven final evidence enters the existing browser projection before execution settles; finding decisions and source finalization remain separate. If publication or settlement fails after capture retention, the next pass reuses that final evidence without provider reads. Completed replay is local and read-only. Pausing new work or revoking its original caller does not erase observation of an already admitted action; changing the installed capability binding refuses recovery. The daemon starts one recovery observer for each hosted capability after startup interruption recovery commits. Selection includes uncertain attempts and active attempts adopted by recovery, while excluding live driver-owned activity. It preserves the original capability and posting actor even after the caller is revoked or new work is paused. Normal pending work is observed at 15-second intervals; failures and ambiguity back off from 30 seconds to five minutes and honor provider retry-after delays up to 24 hours. At the 200-reference bound, recovery stops before provider reads or new artifacts and retains an explicit uncertain outcome and reservation. An already retained final capture can still publish and settle offline at that bound. Shutdown waits for both dispatch and recovery workers.

Hosted preflight must journal its fixed non-review allowance query separately from the eventual review trigger. The preparing attempt binds the original operation, capability, actors and exact source anchor before any query POST. Only the caller that newly creates that intent may make its one post; an existing or uncertain intent requires observation-based recovery and never permits blind reposting. Retain the exact returned or recovered query comment even if preparation later stops. A query grants no review admission or coverage. New query intents recheck current authorization, configuration, policy and source identity; retained query reads and response recording preserve already-issued work. Preparing may perform this journaled non-review metadata query, but may not post a review or spend its allowance before review admission. The query journal, one-pass query observer, immutable availability retention and final hosted guard are implemented components. The concrete hosted driver and configured daemon call them.

Edited competing comments close attribution even when their current bodies removed or hid the command. Unknown replies stay unproven. The pure resolver performs no I/O. A separate one-pass runtime component journals query intent before its one fixed metadata post and recovers an uncertain response without reposting. It saves and reference-checks immutable query source before interpretation. Commit statuses require the provider bot's stable numeric identity and the `CodeRabbit` context; check runs require the configured GitHub App ID, exact candidate and `CodeRabbit` check name. Unknown states, partial pages and conflicting identities remain unproven. A terminal status, including a successful “review skipped” status, establishes no review coverage. Check-run observation retains any trusted nonterminal run without guessing creation order from IDs or nullable timestamps. These observations do not establish account-wide or other-head idleness. ## CLI adapter

Native CLI process execution requires a supported Unix host. Each invocation owns a separate process group; cancellation, timeout, output overflow and wrapper exit terminate remaining workers in that group. Unsupported hosts reject the native CLI capability before launching a process. Windows clients can still use a remote controller, and installations without a native CLI capability retain their coordination/browser behavior. Equivalent native Windows process-tree ownership remains unimplemented; cross-builds do not establish that runtime guarantee.

The CLI adapter verifies included allowance, prepares the admitted candidate/comparison objects in the owned workspace and executes one allowlisted argument vector. Before issuing its one-use process permit, the runner also requires an explicit available billing observation with usage billing inactive; missing, active or unknown billing facts hold execution. This conservative check matters because [automatic usage billing](https://docs.coderabbit.ai/management/usage-based-addon) can continue beyond included allowance without a per-review credit flag. A user-scoped billing-period response does not establish the selected organization's continuation mode. The observation neither reserves provider quota nor prevents an external actor from changing account settings between observation and dispatch; that account-level safety boundary remains unproven for operational cutover. It retains exact source/comparison and executable identities plus bounded stdout/stderr artifacts. Parsing structured review output distinguishes completed capture from failure, cancellation, rate limiting and partial output; exit zero alone is insufficient. Raw capture retention accepts the full unsigned 32-bit exit-status range on a 64-bit reader, including crash statuses; the derived review outcome cannot turn a nonzero exit into completed coverage.

The driver retains one immutable included-allowance observation before admission, tied to its source anchor, actual changed-file count, original actor, policy/configuration revisions, private capability binding and account. Exact local replay has no extra event or permission. New observations recheck current access, source freshness and project file ceiling. These records describe the observation; the runner still consumes its separate fresh one-use permit before starting the process.

Private captures preserve exact stdout/stderr bytes, process-start status, exit code and the measured capture window in a versioned envelope. The start/finish timestamps are explicit canonical UTC values retained before ledger ingestion; they describe the invocation/capture window even when the process did not start. Exact artifact replay reuses both bytes and timestamps. Invalid, missing or reversed timing and unsupported formats fail closed without replacing retained bytes. Their references carry a checksum and byte count rather than a filesystem path. Publication is immutable: an exact retry reconciles the existing artifact, while different bytes or a corrupt existing artifact fail without replacement. Capture storage bounds stdout to 16 MiB and stderr to 64 KiB. Retention alone establishes neither successful execution nor completed coverage.

Capture-store construction resolves existing parent aliases once and retains the canonical root, including when child directories must first be created. An existing requested capture root must itself be a private directory rather than a symlink. Later alias changes cannot redirect an opened store. File and directory checks do not establish protection against a hostile same-user filesystem race.

Transport keepalives and routine process progress stay out of model-facing output. A dispatched command that loses its supervising process is recovered as interrupted or uncertain from retained state; a replacement process does not silently spend another review. Canceling local execution does not recover allowance or erase its evidence.

Provider source reads retain the full validated UTF-8 title within a separate 4096-byte adapter bound. Browser PR metadata uses a trimmed prefix at a complete UTF-8 character boundary within its 500-byte display budget. That display limit does not reject an otherwise valid source comparison; the adapter bound is a local resource limit, not an asserted GitHub title maximum.

Hosted trigger and allowance-query recovery permit a fixed five-second provider-clock lag at the retained admission lower boundary, in addition to flooring local sub-second precision. The upper observation bound, exact immutable command bytes, stable actor identity, unique match and complete collection remain required. Retain the original provider timestamp; an older or otherwise ambiguous match stays held and never authorizes reposting.

## Evidence and the native workspace

The shared CLI/hosted capture ledger is independent of browser snapshots. Trusted runtime integration binds its checksum, timing, structured findings and scope to the exact stored attempt anchor and capability fingerprint. An exact retry returns the original capture receipt after settlement; different evidence conflicts. A scoped full read rechecks current authorization. Recording a capture neither releases its reservation nor marks the attempt completed, finalizes findings or establishes policy sufficiency. The optional configured CLI and hosted drivers retain and publish this evidence; the default unconfigured daemon exposes only stored controls.

Current local adjudication rechecks project access, uses revision guards and idempotent receipts, and appends an audit row and compact event with each change. The daemon updates an already-published native browser run in that same transaction; projection failure rolls back the ledger, audit, events and receipt. Missing initial publication remains ledger-only. Finalization requires a completed attempt, complete capture and all findings decided; it freezes the original source counts, including legitimate zero-finding runs. Later decision or fix-reference corrections retain original captures, counts and audit records. A proof-bearing accepted finding cannot be silently rejected and lose its proof. The [evidence controls](review-controls.md) expose these operations through bound agent clients and document stored administrator policy configuration, whose revision and channel pauses are enforced by the local journal; source-dependent file ceilings remain driver-owned. Browser mutations remain unavailable.

Trusted initial publication builds a channel-specific native run from the retained capture and its current adjudication. The captured head remains separate from current PR facts. Publication can precede attempt settlement, but cannot finalize the source or grant coverage. It preserves original finding identities, partial-result limitations, effective fix references and finalized source counts. Exact replay is read-only; a source present only in historical snapshots cannot be silently recreated.

A missing current PR projection leaves successfully retained CLI evidence in the authoritative ledger without changing a completed execution to uncertain or keeping its reservation. It does not recreate browser facts or finalize the source. Other publication failures remain recoverable failures; a failed retention never becomes a completed capture.

Hosted publication does not confer CLI comparison credit. The shared channel-explicit comparison check keeps current-comparison coverage separate from pending evidence. Each invocation selects `cli` or `hosted`; pending evidence and coverage never cross that channel boundary. Coverage requires a completed native attempt and complete finalized capture for the exact current repository, PR, candidate, base and effective parent, with every finding decided and accepted findings carrying fix proof. Pending completed native evidence is checked across all heads of the selected PR: missing captures, unfinished decisions/finalization and accepted findings without proof block another spend. A ready capture cannot hide another pending capture. The final local action guard repeats this check in its authorization snapshot. Imported history never becomes native execution credit. Repository renames preserve coverage when stable identity and Git objects still match. Hosted captures additionally require their retained command/trigger identity and complete publication metadata; they never fabricate a reviewed-file list. The indexed lookup examines at most 100 completed operations in the selected channel for the selected PR before loading evidence; excess history produces an explicit capacity hold instead of an unbounded scan or another provider spend. This predicate does not establish aggregate policy sufficiency, CI success or merge readiness. The concrete CLI driver supplies fresh source observations, selects only CLI comparison credit for its target and predecessors, and repeats local authorization before its one-use process action. Hosted comparison support alone enables no hosted dispatch.

New attempts, run evidence, findings, decisions, effective fix proofs and observation freshness are native durable records. Source finalization freezes source counts and identities. Adjudication/fix corrections append guarded evidence; they preserve earlier values and never replace finding text to reuse an old count. Public checkpoint publication is a separate recoverable external action.

Publish workspace projections from those records while preserving imported run IDs, original source identities and retained snapshots. A new native event cannot relabel imported historical evidence as a newly executed run. Native progress publication must not require exporting the whole queue through the administrator import route or reading the old database. Preserve stable historical drill-down and source-count conflicts.

Each run summary carries its original producer in `source`; snapshot metadata identifies the publisher of that observation. Those values can differ. A publication about one target does not refresh the observation age or establish completeness of unrelated PRs. Retained projection capacity is bounded; reaching it must refuse a publication atomically rather than truncate history. Increasing retained scale and reducing snapshot write amplification require separate measured storage work before claiming large review-history throughput.

The browser keeps separate chronological Hosted/CLI rows. It displays real attempt/progress facts and configured policy outcomes when available; missing policy is explicit. Review completion, aggregate sufficiency and merge readiness remain distinct. Humans perform merges. Existing worker, job and message paths remain independent of this domain.
