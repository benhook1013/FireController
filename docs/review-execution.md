## Ownership and fast requests

The service owns review admission, provider work, retained artifacts and attempt recovery. An agent supplies its bound project plus an expected PR, channel and candidate head; it never supplies a GitHub credential, executable path or mutable working directory. Ordinary queue, job and inbox reads remain provider-free.

A review request validates local arguments, authorization and configured capability, and records a durable request before supervised provider preflight. The caller can collect a terminal result within a bounded wait; pending work returns the compact original receipt. Provider reads, Git preparation and subprocess execution occur under supervised background workers. A waiting adapter follows that operation through the service; an explicit detached request exposes the same receipt for recovery. A lost tool response does not imply that no request or external action happened.

Queued requests, external attempts and completed review evidence are distinct records. A request can be held before any action. An external attempt records preparation, possible posting or process start, active work, and a proven terminal or uncertain outcome. Its retained transition history identifies the actor, expected head, admitted comparison, configuration revision, provider account and external identifiers. Reusing an idempotency key with the same request returns its original receipt; changing the request conflicts.

Each local attempt mutation records one effective UTC timestamp shared by its operation update and transition. It cannot precede valid retained operation or attempt chronology, including after restart or a backwards wall-clock adjustment. Malformed retained timing is rejected without changing the journal. Effective recording time does not establish physical elapsed duration or adjust provider, capture or source-observation timestamps; their attribution and freshness checks remain separate.

## Bound execution tools

The explicit [channel-front start](review-round-controls.md#one-explicit-channel-front-run) adds `fc reviews start` and MCP `review_start`. One finite background selection links to one ordinary exact-target operation. `run-read` and `review_selection_read` follow that original link; the historical run read remains separate. The selection and native operation share the caller’s bounded result-wait budget.

Use the existing private profile for these commands; project and worker are inherited from that binding:

```sh
fc reviews execution
fc reviews request 42 --key review-42-cli-a1 --expect-config 3 --channel cli --head 0123456789abcdef0123456789abcdef01234567
fc reviews operation review_operation_0123456789abcdef0123456789abcdef
```

`reviews execution` reads stored project configuration and its revision without checking provider availability. Missing configuration returns `reviews_unconfigured` for reads and requests; `review_not_configured` identifies a selected PR or channel outside the stored configuration. `reviews request` explicitly authorizes background review work against the selected PR, channel, candidate and configuration revision. Within its bounded result wait it can return a terminal operation; otherwise its compact receipt contains only operation ID, initial `queued` state and revision. The receipt alone does not mean a review started or completed. `reviews operation` reads current retained state and its stable reason. Reads make no provider calls and do not poll automatically. Daemon shutdown detaches operation, source-refresh and checkpoint-publication result waits before draining ordinary request handlers. Ending result collection changes no retained operation; provider workers follow their separate supervised shutdown and recovery contract.

The corresponding MCP tools are `review_execution_read` with no fields, `review_operation_read` with `operation_id` and optional `wait_seconds`, and `review_request` with `idempotency_key`, `expected_configuration_revision`, `pull_number`, `channel`, `head_sha` and optional `wait_seconds` and `allow_out_of_order`. Only the request tool authorizes external work. Ordinary calls use the shared five-second client budget; an explicit review-result wait extends only that call; server preparation and execution continue independently of the request connection. Invalid selectors fail before loading credentials or contacting the service. After an unknown response, recover with the same explicit key and exact request; neither interface generates a new key or automatically retries.

An explicit `reviews request --out-of-order` skips only predecessor-completion scheduling. HTTP and MCP accept `allow_out_of_order: true`; omission or false retains ordinary ordering. CLI also accepts `--out-of-order=true` or `--out-of-order=false`, once, without consuming the next argument. The [review contract](reviews.md#explicit-requests-outside-queue-order) owns the unchanged target and effective-parent guards. Incoming routed findings hold direct requests at enqueue, preparation, admission and the final action boundary, including ordinary requests. A route arriving after preparation cannot be bypassed by this flag. Automatic `reviews start` rejects the option and still selects the channel front.

The accepted operation retains `allow_out_of_order: true` when selected; false is omitted for ordinary wire compatibility. Review execution schema seven adds the guarded boolean column with false defaults for existing operations. Exact-key retries retain the original scheduling choice; changing it conflicts. Older supported backups retain their absent false value without inspection-time migration. Automatically selected child operations with a bypass flag are invalid. A terminal response with different ordering intent is an unknown outcome, never a reason to request another review automatically.

`GET /api/v1/projects/{project_id}/reviews/execution/configuration` returns stored `project_id`, `revision`, `capability_id`, `mode`, `queue`, `channels` and `paused`. It is a project-scoped read with instance/authorization checks, including when no runnable capability is installed. It exposes no account credentials or private paths and makes no sufficiency or CI assertion.

## Operator capabilities and project configuration

Private startup configuration supplies named provider capabilities: the GitHub credential reference, CLI executable and its protected authentication context, and explicit provider-account scheduler identities. These are operator-owned settings. Project administration selects permitted capability IDs and channels, queue mode/order, required channels and allowed source configuration through revision-guarded service records. New requests bind both their execution configuration and current project-policy revisions. Local preparation, admission and the final action guard recheck those bindings, actor access and channel pauses; older unbound requests remain held. Project content and worker requests cannot select arbitrary server files, environment variables or commands.

Each queued operation retains a fingerprint of its selected capability, including the configured provider account, channel set and private authentication context. Changing that binding holds old queued work; it never silently adopts a replacement account or credential. Existing unbound operations from the earlier journal schema are retained and held. Replaying an already successful configuration or request key returns its original receipt after local capability changes, subject to current caller authorization; a new action requires a new explicit request.

The catalog is versioned strict JSON, limited to 64 KiB and 32 named capabilities, read from an explicitly selected private regular file. It accepts operator-owned Git/CLI executables and an allowlisted map of authentication home/configuration directories. An optional GitHub credential-file reference resolves relative to the catalog; the token is required for hosted posting and is never passed to the CLI. There is no shell or environment-expression expansion. Safe metadata and formatted diagnostics omit private paths and credentials. Select it explicitly with `fcd --review-catalog /private/path/catalog.json`. Capabilities select `cli`, `hosted`, or both; each channel uses its own driver and reservations with no cross-channel fallback. A hosted-only capability requires no CLI executable. Hosted settings bind provider identity and the explicitly configured progress surface as described below. The default empty catalog starts no provider worker or review polling loop.

The service obtains source through the verified project repository and creates its own bare object cache and per-attempt immutable workspace under its private data directory. A developer checkout is not the execution workspace. Git commands disable ambient hooks and configuration; source preparation does not execute repository install/build hooks. The CLI receives a minimal explicit environment and only its required authentication context, never the service's GitHub credential or another project's profile. This is a trusted local executor capability, not a hostile multi-customer sandbox.

One service process supervises two global work slots. Startup validates driver bindings and commits interrupted-attempt recovery before accepting HTTP requests; asynchronous worker completion has a single retained result. Shutdown cancels owned work and waits within a finite budget before closing storage. Account and exact-target reservations allow at most one active action per provider account and channel and exclude another action against the same repository, PR and channel. Finite deadlines bound each action. One project can occupy both slots; per-project scheduling fairness is not implemented. Coordination remains usable when provider work is slow or unavailable. Multiple active service replicas and remote executors remain outside this delivery.

## Admission and provider boundaries

Resolve the selected project repository by its stable identity and obtain its current canonical name. Refresh the selected PR and the predecessor/default-base facts required by the configured queue; do not refresh unrelated queue members or recapture completed evidence on every request. Cached observations retain time and completeness. Provider pagination must terminate completely before a collection can support admission.

The expected PR/head are assertions. Admission verifies current lifecycle, repository identity, candidate head, effective parent/base and canonical patch identity, applicable active-provider activity, operator stops, required fresh facts and observed account allowance. It records the exact evidence used. A mismatch or incomplete fact holds the request without falling back to another PR.

Before an external action, atomically reserve `(provider, repository_id, PR, action_class)` and retain the attempt intent. Provider-account scheduling is separate from that target reservation. Conflicts remain opaque across project grants. Recheck the external target at the final action boundary; record the admitted identity even if a later provider result belongs to an older head. No provider call or subprocess wait occupies a database transaction.

Hosted and CLI channels have independent cycles and allowance observations. Exhaustion or activity in one does not hold the other unless a real shared reservation or account resource applies. No adapter purchases credits, seats or overage, or selects paid execution after an included allowance is exhausted. Unknown allowance or an ambiguous action remains an explicit hold/uncertainty. CLI usage failures retain only four safe command categories when proven: `allowance_command_not_started`, `allowance_timeout` for the existing fifteen-second command deadline, `allowance_command_failed` for a started command or bounded-capture failure, and `allowance_response_unproven` for successful output that fails strict allowance parsing. Other context, source, configuration and unclassified failures keep their existing fallback; a proven zero included balance remains `allowance_exhausted`. These reasons expose no raw output, private path or credential and grant no review permission, new quota, retry or completed coverage. Earlier held attempts remain unchanged.

When native projection is enabled, each journal transition updates its browser attempt in the same transaction. Preparing and held are distinct states; held attempts retain their actual stop time. Interrupted active or posting work becomes uncertain without an invented finish time. A missing current PR observation leaves the transition ledger-only; a trusted fresh observation can establish that first row. Publication preserves current PR facts and imported history, and exact replay creates no new snapshot. Initial metadata is a fallback inside the publication transaction: if another observation creates current PR facts after a missing-row read, those current facts take precedence over the prepared fallback. Retained archive totals do not hold a new attempt. If a later administrator observation omits the live native attempt while retaining current PR facts, automatic transitions restore that attempt from its actual journal without copying snapshot bodies. Genuinely absent PR facts still leave transitions ledger-only; explicit publication requires current metadata or its trusted initial fallback. Individual record/detail limits remain atomic publication guards. Other projection failures roll back the journal transition as well.

Attempt settlement retries only the same guarded local journal transition within a finite budget. It reconciles an already committed transition before retrying and never repeats provider dispatch. If the outcome cannot be recorded, the supervisor reports a failure, cancels its other work and retains reservations for inspection and recovery.

## Hosted adapter

A hosted attempt records its exact command body and unique intent marker before posting a GitHub comment. Retain the returned comment ID and posting time. On a lost response or restart, search the complete scoped provider history for that intent before deciding whether posting occurred. Never blindly repost an uncertain request.

The implemented trigger helper generates only the fixed full-review command and a versioned marker binding operation, attempt and exact head. Its pure recovery resolver consumes an explicitly complete scoped comment collection and the configured posting actor's stable numeric identity and kind. It can identify one exact, unedited command in the known posting window. Missing or partial history remains uncertain; duplicates, edits and contradictory attribution remain ambiguous. Neither state permits automatic reposting, and adoption establishes a trigger only, not completion or review credit. This helper has focused normal/race proof.

The scoped hosted observation adapter reads every page of reviews, review comments and then issue comments under one 15-second budget, without posting or retrying. Reading command history last includes competing triggers that arrived before an observed publication and closes attribution to an earlier trigger. Only a successful complete collection receives an observation time; a failed later collection preserves earlier complete collections for diagnosis. The reply-parent identity distinguishes attached roots from replies. Current and original multiline coordinates and diff-side metadata are preserved; missing/null metadata stays unknown rather than inheriting another location. Combined observations are bounded to 10,000 items, 64 KiB per body and 16 MiB of body text.

The pure publication resolver recognizes explicit version-1 publication markers in the configured provider actor’s reviews, bound to the exact trigger window and head. Review submission must be strictly later than the trigger timestamp; equal timestamps cannot prove their order. ## Collecting review results

`POST /api/v1/projects/{project_id}/reviews/requests` accepts a strict `Prefer: wait=N` header with an integer from 0 to 900; omission selects two seconds. This preference is not part of the action fingerprint. Review admission requires project write access, which also requires current read access under the project grant model. Positive waits, including the default, reauthorize read access when returning results. `wait=0` changes only result collection and does not admit a write-only grant. Within that wait, HTTP 200 returns an authorized terminal operation; otherwise HTTP 202 returns the original `{id,state:queued,revision:1}` receipt. That receipt identifies the accepted action, not its current execution state. Replaying the exact action and key with another wait preference never starts another review.

CLI `reviews request` exposes `--wait-seconds`, default two. MCP `review_request` exposes `wait_seconds` with the same result-collection semantics and an MCP-specific range of 0–50 seconds; CLI/API waits retain their 0–900 range. Zero requests immediate return; a longer wait lets a capable host retain the call in the background and receive its result without model-visible operation polling. Ordinary coordination calls retain their five-second budgets. The selected longer wait extends only this operation's client/adapter and response-header budgets; an earlier caller/host deadline still wins.

`GET /api/v1/projects/{project_id}/reviews/operations/{operation_id}` accepts the same header, default zero. CLI `reviews operation ID --wait-seconds N` and MCP `review_operation_read` with `wait_seconds` can reattach explicitly to retained work without authorizing provider activity. The MCP read also caps its wait at 50 seconds; the CLI/API maximum remains 900. This read returns the latest operation at completion or bounded expiry. Queued, preparing, posting and active states remain pending; completed, failed, cancelled, rate-limited, uncertain and held states end collection. An uncertain or held operation is a returned fact, not a claim that external work completed successfully.

The service registers each bounded waiter before its first authorized read and uses coalesced postcommit notifications rather than database/provider polling. Limits are 256 open review-result waits per engine and eight per principal. When POST wait capacity is occupied, the accepted action returns terminal facts if already available or its original pending receipt. A waiting GET may report overload; it never enqueues another action. Results recheck project access, including after revocation.

Canceling or losing the result connection detaches collection without canceling the retained action, releasing its reservation or retrying an external request. Daemon shutdown also detaches result observation: an accepted review, source-refresh or checkpoint-publication POST whose caller remains connected returns its original HTTP 202 receipt after fresh read authorization. It reports acceptance only. A canceled caller or failed fresh authorization/read retains the existing error path; a detached GET does not claim a terminal result. A postaccept read failure preserves `outcome_unknown` and original-key recovery. A GET failure remains a read failure. Actual agent-host background scheduling, tool timeout behavior and idle wakeup remain separate proof; service/client support alone does not establish them.

## Retained allowance timing on held results

A held CLI or Hosted review can include an optional `allowance` observation in its operation and linked selection result. This is a provider-free read of validated facts retained for that exact operation and attempt. It is absent on older holds without retained facts; omission never means zero or current availability. The fields grant no permit, purchase, automatic retry, account-wide cache or new provider action. Routine successful coordination commands gain no output.

`kind: cli_exhausted` contains `observed_at`, `remaining` (zero), `limit`, `full_capacity_in_ms` and `rolling_window_ms`. The duration estimates when the whole allowance pool becomes full relative to the observation; it is not the next available review time. A known zero estimate remains zero, without implying available quota. Activity by other clients can invalidate the estimate. The process returns these strictly parsed facts only after its source, context and generation checks, and creates no review permit. Native preparation retains the bound observation before returning its original exhaustion hold.

`kind: hosted_cooldown` contains `observed_at` and `retry_not_before`. Retention requires the existing complete, strictly attributed allowance-query response and its rounding margin. The raw capture remains journaled before interpretation. The observation can guide a later explicit request, whose normal fresh admission checks still apply; reaching the timestamp grants no permission.

Both variants reuse their channel’s immutable preflight observation storage. Positive observations retain their existing bytes and permission checks. An exhausted or cooldown row is valid retained data and cannot satisfy positive dispatch validation. Corrupt, mismatched or foreign retained records fail closed. Operation and linked result reads expose the same bounded projection through HTTP, CLI and MCP, without opening capture files, querying a provider or expanding a private account binding. No new MCP tool is required. Canonical backup inspection and restore validate and preserve positive and held observations without requiring historical observations to remain fresh.
