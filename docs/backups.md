# Managed Backups

## Implementation status

Local operator bundle creation, read-only inspection, inactive restore, managed scheduling and retention are implemented. Local coordination activation establishes fresh access with a persistent provider hold. Proof and limits are recorded below. Recovery-generation backups retain prior activation provenance and support explicitly configured local scheduling under the provider hold. Provider reconciliation/resumption remains unfinished. [Installed QA proof](hosting.md#recovery-generation-qa-upgrade) includes a manual pre-upgrade backup; an installed recurring backup policy and complete disaster recovery workflow remain unproved.

## Canonical data and local format

A local version-one bundle is a private immutable directory named `backup_` plus an opaque identity. It contains a self-contained consistent SQLite snapshot, canonical manifest with SHA-256 sidecar, and an inventory of immutable files from the managed `review-captures` and `hosted-review-captures` stores. Include final capture files published before their ledger insert as retained forensic evidence; their presence does not establish review credit. Validate references from native evidence and hosted observations, including allowance baselines. Preserve database resource IDs, messages, jobs/history, receipts, events, review decisions/routes and imported history.

The manifest binds source instance, snapshot start/end window, the snapshot's event sequence, database size/hash and sorted artifact paths/sizes/hashes. Snapshot timestamps use one UTC start anchor and monotonic elapsed time for the finish; a wall-clock adjustment during capture cannot reverse that window. The interval describes local snapshot timing, not independently verified provider time. It does not invent an exact provider recovery time or include provider bodies in ordinary output. A completed bundle is published only after validation and durable writes; partial staging never becomes a usable backup. Local files remain private and destination paths cannot target the source data directory. Inspect verifies hashes, SQLite integrity/foreign keys, supported schema and artifact references without modifying the bundle. Unknown or modified SQLite triggers and foreign-key definitions are unsupported; the two exact canonical review-revision triggers and supported schema versions remain valid. Hidden/generated columns are not part of this format. An ordinary installation or a validated coordination-active restored installation can be a source. An inactive or malformed recovery remains unsupported as a backup source. Inspection validates recovery provenance without granting serving or provider authority.

Operator credentials, bootstrap token files, profiles, executables and external catalog/authentication directories are not backup artifacts. Git source caches and derived executor workspaces are operator runtime state rather than retained review evidence. Shared-clone alternates are not copied or represented as self-contained artifacts. Restore does not resume admitted executor work; re-provisioning and exact-source verification are prerequisites to any later executor activation. Missing source stays an explicit hold.

## Inactive restore

Restore accepts a verified bundle and creates a new private destination, never overlays existing data. It preserves canonical records and captured evidence, generates a new instance/signing identity, and revokes every restored API credential before the result can be used. Original grants and credential history remain retained; access is not silently revived. Record the predecessor instance, bundle and recovery window in restored metadata so pending work and receipts keep their originating provenance.

The first restore result is explicitly inactive. Daemon startup rejects an incomplete restore marker and an inactive restored database before worker startup or serving. No bootstrap credential or automatic provider resumption is created by this slice. Original provider intents stay retained and possible post-backup effects remain unresolved. Normal restart of an ordinary installation keeps its instance identity.

Local coordination activation implements the fresh-access and held-startup portion of the [recovery boundary](architecture.md#storage-operations-and-growth). The operator still owns predecessor fencing and explicit client rebind; provider reconciliation and resumption remain separate unfinished work. Old profiles, cursors and retries cannot silently continue against a new instance or relabel old keys.

Receipts now store their originating instance in the mutation-key identity. Base schema version two preserves those origins across restore; new mutations and exact replays select the current instance. Startup migrates version-one receipts atomically without changing fingerprints or response bytes. Ordinary installations use their existing instance; a supported inactive restored copy uses its validated predecessor metadata. Inspection and restore accept either supported schema without migrating the bundle. This prerequisite does not admit restored clients or resume provider work.

## Operator commands

The operator commands are:

```sh
fcd backup --data-dir SOURCE --destination BACKUP_ROOT
fcd backup-inspect --bundle BUNDLE_DIRECTORY
fcd restore --bundle BUNDLE_DIRECTORY --data-dir NEW_DESTINATION
fcd backup-status --data-dir SOURCE
```

Local coordination activation is a separate explicit command:

```sh
fcd restore-activate --data-dir RESTORED --expect-instance NEW_INSTANCE --fenced-predecessor SOURCE_INSTANCE --admin-token-file PRIVATE_NEW_TOKEN
```

Fence the predecessor outside this command before asserting its exact identity. The command records that operator attestation; it does not contact, stop or independently verify the predecessor. Supply the restored instance from the restore result and a fresh high-entropy administrator token in an owner-private regular file. The token is 32–256 printable nonspace ASCII bytes, with an optional file line terminator. Any token hash already retained in credential history is rejected, including revoked credentials. The command never prints the token or its path.

Activation validates the completed restore's private database, schema, integrity, foreign keys and provenance. It atomically adds one new administrator and records `coordination_active` with `providers_held: true`, leaving original credentials revoked, receipt origins unchanged and provider intents retained. It does not rehash all capture files or establish their current review credit. An exact retry with the same identities and token returns the historical activation result without adding or reviving access; a changed identity or token conflicts. If output is lost after commit, retry that exact command rather than choose a replacement credential.

An activated copy can serve local coordination and stored review reads after explicit client rebind and fresh project access grants. Every provider path remains held: startup ignores supplied provider catalogs and GitHub token files, creates no executors and starts no review, hosted-recovery, source/CI/readiness or public-checkpoint workers. Retained queued and uncertain work stays retained. Repository verification is unavailable. Changing project settings or restarting with an old catalog cannot release this hold. Old pending requests remain bound to their predecessor; rebind is not authorization to submit them as new actions.

Provider reconciliation/resumption remains unfinished. Keep verified predecessor bundles according to the retention policy. Local activation and repeatable local recovery do not establish a complete operational disaster-recovery workflow.

### Recovery generations

A backup of a coordination-active restored installation uses the same bundle format. Each subsequent restore generates another instance/signing identity, revokes all copied credentials and returns an inactive destination. Its current recovery metadata describes its immediate predecessor and selected bundle. A versioned `recovery_history` component retains each earlier activated generation as a row keyed by its instance identity, with the exact nine recovery metadata fields in canonical JSON. Restore archives the source generation before replacing the current metadata; existing ancestor rows remain byte-identical. Ordinary installations and older bundles need no history table. The supported history is at most one thousand archived generations with a 4 KiB per-row bound. Backup-source validation reserves room to archive the source generation on the next restore; a source already at that limit is rejected without publication rather than produce an unusable new bundle.

Validation requires a connected predecessor chain with no cycles, unlinked records or current-instance record. Historical activation credentials and recovery windows remain attributable after credential revocation; an archived activation administrator must remain revoked. An inactive destination cannot become a backup source; malformed or unsupported history is rejected without changing the source. Current metadata retains its strict inactive or coordination-active shape. Receipt origins, retained provider intents and the durable provider hold survive every generation; backing up or activating a later generation never grants provider resumption.

Coordination-active startup supports explicitly configured local managed backups. It does not adopt a predecessor's stored schedule or due time. The scheduler retains historical attempts, successes and bundle ownership, starts the new generation's first explicit schedule after its interval, and can resume that generation's own recorded due time after an ordinary restart. Retention only considers bundles owned by the current source instance and selected destination. A predecessor's last success remains visibly attributable to that predecessor until a genuine new success replaces it. New attempts record their source instance explicitly; timestamp ordering alone cannot establish generation ownership. Recorded completion or interruption timestamps do not precede their retained start even if the local clock moves backward. These effective timestamps do not establish elapsed duration or an independently verified external completion time. Omitting schedule flags disables scheduling.

Each command accepts `--timeout DURATION`, defaults to five minutes and permits a positive duration up to twenty-four hours. Duplicate/unknown flags, positional arguments and invalid durations fail before filesystem work. The operator uses read-only SQL on its source without initialization, migration or writer admission. SQLite may still create transient WAL/SHM sidecars; a WAL-mode source mounted read-only by the operating system is not supported when those files are absent. A backup source must already be a valid private installation; a wrong path cannot silently bootstrap a new database. Restore never overlays an existing destination, including an empty directory.

Commands use explicit local filesystem authority, bounded execution and compact JSON; they never load a provider catalog or make network calls. A caller may retain a long local command in its host background. These are operator actions, not per-worker coordination calls or a reason to return pending receipts for quick local mutations.

Use a short private destination path. The bundled SQLite VFS imposes a smaller database-path limit than the filesystem; generated bundle and database names also consume that space. An unsupported destination remains a reported backup failure rather than a successful backup.

## Managed scheduling and retention

Scheduling is an explicitly configured daemon feature. The operator supplies `--backup-destination`, `--backup-interval` and `--backup-keep` together; no destination or automatic schedule is invented. The interval is one minute through thirty days and the retained count is one through one thousand. Optional `--backup-timeout` defaults to five minutes and accepts the same positive maximum twenty-four hours as the manual command. Creation and retention each receive that full bounded phase budget, both derived from the worker context so shutdown still cancels them. A completed snapshot does not consume the time available to verify and prune older copies. Invalid or incomplete configuration fails before creating installation state, including destinations whose encoded status could exceed the output budget. One active service replica remains the supported deployment. With scheduling disabled, startup still reconciles retained backup status but does not require backup-source inventory compatibility. Explicit backup creation and enabled scheduling retain their source-validation requirements.

The daemon owns one serial backup worker using the existing store's read pool. After an attempt settles, it waits the configured interval; elapsed periods do not build a queue of catch-up work. On restart a due schedule can run immediately, and an interrupted prior attempt remains a failure rather than invented success. Shutdown cancels and joins the worker before closing storage. Destination failures do not stop ordinary coordination or readiness.

Managed creation carries its already verified manifest and original directory identity into a separate bounded ownership settlement; it does not hash the full bundle again under an expired snapshot deadline. A transaction error is not proof of rollback: an independent bounded read may recover only the exact retained ownership and atomic success record. If registration cannot be confirmed, preserve the published bundle and previous success, report `backup_registration_failed` with an `unregistered_bundle` summary, and hold that source instance's selected destination. The held worker stays idle until daemon cancellation, preserving ordinary coordination and readiness. It creates no further copies there, including after restart or disabling and reenabling scheduling. Each unresolved publication has a separate retained hold, so selecting another destination cannot erase the first destination's hold. An operator can inspect and preserve the reported bytes and explicitly select a new empty private destination; returning to a held destination does not resume it. No automatic adoption, recursive deletion or hold-clearing command is provided. Failure to persist the hold is reported and stops further attempts in this worker; process/storage failure between filesystem publication and durable settlement remains a recovery boundary, not a claim of crash-atomic publication.

A small versioned local ledger retains configuration, last attempted outcome, last verified success and managed bundle identities. A failed attempt preserves the previous success. Retention failure is reported independently of successful creation. `fcd backup-status --data-dir SOURCE` reads compact stored operator facts without snapshotting, hashing all bundles, calling providers or changing state. Stored success identifies a past verification; `backup-inspect` verifies present bytes. Status output is bounded to 16 KiB so long configured destinations and retained success locations remain reportable; manual backup, inspection and restore summaries keep their 4 KiB bound. It is not a per-worker tool or an automatic notice attached to unrelated calls.

Retention runs only after a newly verified managed success and affects only ledger-owned bundles for that source instance and selected destination. Preserve at least the configured count, including the newest verified copy. Manual, foreign-instance, changed, unrecognized or unverified directories are never adopted or deleted. If the current source and destination have no owned retained bundle beyond the configured keep count, retention returns without hashing protected bundles. Otherwise, verify every protected keeper before pruning older copies, then reinspect each deletion candidate against its stored identity and manifest binding. Verification is not cached across pruning passes. A phase budget too small for the required full verification reports retention failure and preserves the copies; it never permits unchecked deletion. Suspicious or partial remnants remain explicit cleanup failures; a failed backup does not start pruning. Cancellation positively known to precede every unlink leaves the untouched candidate retained for a later attempt. An interrupted read-only verification does not establish corruption or present validity; the next attempt fully verifies the candidate again before admitting deletion. If deletion may have begun, including an interrupted deletion found on startup, the cleanup hold remains. A cleanup failure is scoped to its source instance and destination. An operator can inspect and preserve the affected bundles, then select a new empty private destination and restart with explicit scheduling to resume managed pruning there; the old directory and ledger remain held for inspection. Destination transfer and provider resumption remain separate boundaries.

## Functional proof

Prove online SQLite snapshot consistency while writes continue; self-contained reopen after removing the source; complete database/reference/artifact validation; unreferenced final-capture preservation; atomic failed publication and no replacement of existing destinations; privacy/symlink/path/hash/schema failures; source unchanged except intended writes; cancellation; inactive restore with new instance and revoked credentials; original IDs, receipts and source provider intents retained; daemon refusal before listener/worker/provider work. Prove actual packaged commands and ordinary startup independently. Also prove serial scheduling and restart without catch-up, separate creation and retention outcomes, read-only status, unchanged ordinary coordination during blocked or failed backup work, and preservation of valid older copies when protected keepers are damaged or missing. These functional goals do not assert fleet throughput, cloud durability or a completed operational disaster cutover.
