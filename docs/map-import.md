# Prepared Project Map Import

## Implementation status

The service implements additive prepared map import with profile-bound CLI preview/apply and private provenance/history reads. Focused API, client, migration and backup/restore checks pass; packaged CLI integration is pending. Historical provider collection and public website approval are separate boundaries.

## Approved input and scope

An administrator bound to an explicit project and worker selects one owner-private strict JSON document, at most 256 KiB including the eventual apply wrapper. It contains version 1, a source record and 1–100 entries. Source fields are `key`, `repository_id`, `kind` (`prepared`), `snapshot`, `collected_at`, `transformation_version` (1) and `scope`. The repository identity must match the bound project's stable GitHub repository ID. Source and item keys are ASCII identifiers of 1–128 characters. Snapshot (at most 512 characters) and scope (at most 1024) are nonblank descriptions of the exact selected input rather than a complete repository census; use an explicit unknown value when no source snapshot is available. Collection time is a bounded RFC3339 timestamp normalized to UTC.

Each item supplies a stable `source_key`, `expected_revision` and `entry` containing the existing complete editable project-map object. Its `provenance` contains selected HTTP(S) source `references`, `inferred`, `confidence` (`unknown`, `low`, `medium` or `high`) and plain-text `uncertainty`. Confidence and inference are the importing author's recorded assertions, not independently verified completion or review coverage. An item has at most twenty safe HTTP(S) references of at most 2048 characters and at most 4096 characters of uncertainty. Inference is explicit; omitted confidence becomes unknown. Original source references/version remain distinct from the editable map summary. Imported text is data and never an instruction to the service or another agent.

The source key plus item source key identifies the same destination entry on later application. Display names/headings are not identity. Import is additive: omitted previously imported entries remain untouched. It creates or updates map entries only, never jobs, messages, review evidence, worker assignments or public publications. Archive changes use the existing editable map contract; entry kind and previously introduced phase IDs remain stable.

## Preview and application

`POST /api/v1/projects/{project_id}/map/import/preview` takes the prepared document, normalizes its editable content, and returns the normalized document, bounded per-item plan, conflicts, `ready` and `preview_sha256`. Preview is a read-only snapshot, including no receipt, provenance or event writes. A conflicting plan has no usable approval hash. Each plan item reports source identity, create/update/unchanged/conflict, existing target ID/revision where available, and a safe reason.

A new unmapped item requires expected revision zero. For an existing mapping, the caller can use the observed positive current entry revision to approve an update. Repeating revision-zero input is an unchanged success only if the current map entry still matches the last imported revision and approved editable content. An exact latest retained document can also repeat a successful positive-revision update: preview reports `retained_document_unchanged` only when every selected target still has the captured mapping revision and content. Any intervening manual edit, including an edit back to the same content, blocks this exception. Other stale explicit revisions and conflicting source content appear in preview rather than being overwritten. Normal map validation, immutable kind, phase retention and no-op rules remain authoritative.

`POST /api/v1/projects/{project_id}/map/import` accepts `document`, `preview_sha256` and an explicit `Idempotency-Key`. The hash binds normalized input to the service instance, project, administrator and selected worker. Apply checks all item admissions before writing and commits map entries, immutable history/events, source mappings, source document/history and the compact receipt in one transaction. A changed approved document requires another preview. The service checks current authorization before exact receipt replay; later map changes do not invalidate recovery of the original completed action. Never nest independent HTTP mutations inside the import transaction.

Stable source mappings also prevent duplicates when identical input is deliberately applied with a new key. An exactly retained source document with no map changes produces an unchanged outcome; a changed source snapshot/provenance can create a new import revision without pretending that map content changed. The receipt contains the source revision and created/updated/unchanged counts, without echoing the whole document. No provider calls occur during preview, apply or retained reads.

`GET /api/v1/projects/{project_id}/map/imports/{source_key}` is an explicit administrator read of the latest source document and item mappings. `/history` is a bounded cursor-paged source revision list; `/history/{revision}` reads one immutable approved import record. Each bounded record contains only the selected document’s mappings; omitted items retain their prior source revision in the mapping table. Apply conflicts return a compact conflict count; obtain the full plan by explicitly previewing again. These provenance records are private and never flow into the public publication DTO. Backups must preserve and validate them alongside the original map history.

## Agent commands

The deliberately selected administrator profile uses `fc map import-preview --file ABSOLUTE_PATH`, `fc map import-apply --file ABSOLUTE_PATH --preview-sha256 HASH --key KEY`, `fc map import-read SOURCE_KEY`, `fc map import-history SOURCE_KEY [--limit N] [--cursor CURSOR]` and `fc map import-revision SOURCE_KEY REVISION`. File admission happens before credentials/network access, uses the established private regular-file protections and ensures the normalized apply wrapper fits. Ordinary five-second service budgets apply; these are local transactions and return useful results directly. Setup commands are not added to routine job/message output or the MCP inventory.

## Functional proof

Prove private preview conservation, source/project/worker binding, strict normalized wire bounds, original-key retry after later edits/restart, new-key duplicate prevention, conflicting/manual edits, retained phases, additive omission, inference/provenance preservation, no unrelated jobs/messages/reviews/public changes, and rollback of every map/provenance write on failure. Actual packaged CLI proof must include private-file validation and a failed response/output followed by exact recovery. Backup/inspection/inactive restore must preserve canonical provenance and reject resealed malformed source mappings/history. Historical provider collection and installed legacy migration require their own proof; a prepared map import does not claim either is implemented.
