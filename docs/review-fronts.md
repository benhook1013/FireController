# Stored Review Fronts

## Implementation status

The service stores bounded source frames from native queue selection and exposes their current local assessment to the browser. Focused core, HTTP, backup/restore and browser tests pass. Packaged front-read integration is recorded in [channel-front review selection](../tools/packagedsmoke/README.md#channel-front-review-selection); installed runtime qualification belongs to [own-project live proof](review-execution.md#own-project-live-qualification) and [deployment proof](hosting.md#executed-deployment-proof). Do not infer a front from the first open merge head or retained review counts. Selection regressions cover an 86-entry queue with 49 retained merged PRs, eight held open candidates, 28 paused donors and a final eligible successor: both channels use exactly one repository read plus nine open-PR reads, with zero merged/donor reads. Additional proof covers no lookahead past an open head, closed-unmerged reopening, restart/cross-channel terminal reuse, actual paused parents and concurrent invalidation.

## Purpose and authority

Expose a provider-free, as-of explanation of each configured channel's current position. Hosted and CLI can have different fronts. This display does not reserve capacity, authorize dispatch, establish CI readiness or permit a merge. Actual requests acquire fresh source facts for live candidates and their actual comparison dependencies, retain known terminal history, and use the canonical native admission path.

The native queue-selection evaluator owns ordering and holds. Completed local requirements and merged PRs are skipped. Unresolved routes or evidence hold that PR. They also hold its CLI dependants, but Hosted can advance to a ready child whose full named-parent source chain remains verified. Comparison-local source problems still hold actual dependants in both channels. An independent verified PR later in the priority queue can also become the front. Account, transport and configuration failures remain source-wide holds. The first eligible open PR is the front. The display reuses that evaluator rather than implementing another interpretation of the rules.

## Bounded source cache

Retain at most one current source frame per project and channel. A frame records the configured repository ID and configuration revision, the local check time, and the ordered prefix assessed by that selection. Known merged entries retain their original source facts and observation times; an unrelated paused entry carries only its identity and an explicit local pause marker, with no source fields or observation time. Each prefix entry retains only the source fields required by the evaluator: PR identity, state/merged flag, head/base/ref, effective parent identity and source observation time. A separate boolean records whether that entry was visible in the stored workspace when the frame committed. Titles, diff statistics, captures, credentials, actor instructions and historical review bodies do not belong in this cache.

Prefixes contain at most one hundred configured PRs in the leading order selected for that operation, with canonical JSON bounded to 128 KiB. A derived order is retained with the frame when it differs from configured order. A changed derived order invalidates its current position claim. They distinguish complete source coverage from a prefix that stopped at a front or hold or includes unacquired paused entries. A local pause marker never counts as verified source coverage. A failed read without a verified prefix records unavailable source rather than leaving an apparently fresh successful front. The cache replaces its prior frame; it does not append a full source prefix to every selection's lifetime history. Existing operation, attempt, capture and selection histories keep their own retention semantics.

Persist the frame in the same final transaction that records selection after current repository, configuration and authorization checks. A changed binding cannot install an old frame. Recording an expected-PR mismatch may still retain its verified actual source prefix; that failed assertion does not redefine the channel's real front. Existing selection events notify clients, including when PR display metadata is unchanged. Explicit single-PR source refresh does not claim to have acquired a queue prefix. No new provider reads, timer crawl or review invocation are introduced.

Source acquisition reads one required candidate at a time and never launches speculative successor reads. Repository-bound merged facts already retained in the current workspace, or in a valid source frame for an unimported predecessor, require no new PR fetch. A merged GitHub PR cannot reopen; a closed-unmerged PR can, so closed-unmerged and open candidates still require fresh source. Current visible workspace facts take precedence over older frames. Retired or removed visible entries cannot inherit an old frame's exemption. Retained merged facts keep their original observation times and are not republished as a new provider observation.

Selection checks local source obligations even for retained merged history. It skips unrelated paused entries anywhere in the configured queue, including donors before a later actionable PR. A freshly acquired comparison that names a skipped PR as its parent forces ordinary acquisition of that parent and its actual source chain, whether the parent appears earlier or later. A pause marker supplies no completion credit, comparison identity or permission to review. Final selection persistence rechecks retained lifecycle/comparison facts and all skipped pauses; a concurrent correction, removal or unpause holds the attempt as `selection_changed` without publishing a frame or creating a child. Ordinary source and binding checks still apply to the selected target.

After establishing a held prefix, selection can also stop before an entirely paused suffix when no acquired entry depends on a PR in that suffix. This suffix proof is rechecked before recording the selection. Unpausing a source-free entry invalidates its cached front explanation until ordinary fresh selection acquires the newly relevant source. Merged and paused history stays visible in the configured queue.

## Read API

`GET /api/v1/projects/{project_id}/reviews/fronts` requires project read access and accepts no query fields. It returns the current repository, configuration and policy revisions, current workspace snapshot when available, configured queue order and separate channel results. An unconfigured response has `configured:false`, zero configuration/policy revisions and empty queue/channel arrays. Responses never include raw source prefixes, private captures or provider diagnostics. A source-failed frame with a matching repository and configuration includes `source_progress`: the retained leading verified PR count (stopping before any source-free pause marker), configured queue count and, when present, the next unverified queue PR number. This identifies the contiguous source coverage boundary, not an exact failing request or stage: later active entries may have been acquired beyond paused donors, or repository or comparison-parent resolution may have failed. It adds no provider reads and supplies no readiness claim. Historical failures are not inferred from current healthy frames. This is a browser read, not an additional agent tool or a request to acquire source.

## Local assessment

Assess the cached prefix against current local requirements, routes, evidence and closure controls in one bounded read transaction. A policy change can therefore change the display without calling GitHub. Reaching the end of an incomplete prefix after local requirements have advanced means unknown, not queue complete; an explicit fresh queue selection obtains the next source prefix through the ordinary workflow.

The read-only front explanation distinguishes finalized fix work from unsettled review results. A native evidence hold is displayed as **Fixes pending** (`review_fixes_pending`) only when every remaining pending native proof for that project, PR and channel has finalized adjudication. Missing or incomplete captures, unfinalized results and mixed stages retain **Results pending** (`review_evidence_pending`); explicit pending adjudication still displays **Needs adjudication**. This distinction reads the current native ledger, not a bounded recent-run preview. It changes no scheduler hold, operation reason, source counts, fix obligations or review permission.

Corrupt carried-obligation records hold the affected front as `source_obligations_unavailable`. They grant no admission and do not cancel healthy selection of other eligible work. Operational query failures remain errors; transient local storage overload during front verification follows bounded selection retry and does not itself establish a carried-obligation hold.

Refuse a provider-ready claim when the current repository or configuration differs, the frame is malformed or absent, or a cached prefix's visible stored PR lifecycle/head/base no longer matches. The separate local-position display below never supplies that readiness. An entry visible at acquisition cannot disappear or become retired without invalidating that explanation. A predecessor absent at acquisition may remain absent: observing a source prefix does not require importing unwanted historical PRs into the website. If that entry later appears, compare its current facts normally. A ready front itself must be visible and match; a held diagnostic may identify an unrepresented blocker without claiming readiness. A newer administrator edit or retirement must not be overridden by a cached frame. Include the current workspace snapshot identity in the assessment so a browser can reject a response for another loaded queue version. Unknown or absent source stays explicit; timestamps describe observations rather than a continuously checked state.

Return configured channels independently with `ready`, `held`, `complete` or `unknown` state, a bounded reason where needed, the implicated PR number/head/base where established, and source/local check timestamps. Held results identify the actual blocking PR when known. Preserve the existing admission evaluator's behavior for its callers while exposing this richer diagnostic result. Native pause or restore recovery cannot become permission to request a review; display any such hold explicitly.

During browser refresh, retain the last matching queue and front assessment as one display frame until both replacement reads agree on their snapshot. A temporary mismatch is not a transition to Queued. Keep the existing source/lifecycle checks, project/page isolation and independent closure controls; apply a genuine front change when its matching queue arrives. If a write lands between completed reads, perform only a bounded, provider-free reconciliation rather than requiring another user refresh. The hero and queue share this behavior.

## Storage and recovery

The optional `review_fronts` schema version one owns a project/channel current-frame table, foreign project identity and strict canonical row validation. Ordinary current lookups use its primary key. Older canonical backups without this optional domain remain supported; backups containing it validate its exact schema, bounded canonical data, source identities and prefix invariants. Inactive restore preserves its historical observation facts and the normal recovery fence. Cached source never bypasses the fresh-request or restore-resumption boundary.

## Browser use and proof

Delivery and Reviews share one bounded local front read. A response must match the displayed current workspace and relevant PR identities before a front badge is shown. Current round closure remains separate from source position. Queued means an established position behind a channel's known front, not a promise that all provider or admission checks would pass. Historical snapshot pages do not present current front state as historical permission.

Proof covers different channel fronts, blocking predecessors, incoming routes/evidence, closure/taper and policy changes, incomplete-prefix exhaustion, source failure, concurrent configuration/display changes, retirement, restart/backup/restore validation and scope isolation. Front reads add no provider calls. Browser proof covers mixed/unknown states, stale responses and narrow layouts; no live provider or operational cutover claim follows from synthetic fixtures.

## Queue display during an operator stop

An operator review-dispatch stop or absent provider frame does not erase the visible local queue position. The service identifies each channel’s first stored open entry with remaining rounds from the complete matching workspace snapshot and current round controls in the same read transaction. It reads only the configured queue's bounded scalar lifecycle/comparison fields, once for both channels, and never loads review bodies or calls a provider. The browser’s recent-history window or pagination cannot turn a known merged predecessor into an unknown gap. A genuinely missing, retired or unknown configured predecessor still stops local selection rather than being skipped.

The local fallback applies only to a dispatch stop, absent frame, changed configuration/visible source, or an exhausted incomplete prefix. It never replaces a known admission hold, malformed frame, repository mismatch, capability refusal or restore-recovery hold. Its selected channel is `held` with reason `local_queue_position`, an exact stored PR comparison and `checked_at`; `source_observed_at` is omitted because no provider prefix was verified. An exhausted local scan does not claim provider queue completion. The browser validates and presents this service result instead of independently selecting fronts from a filtered page.

Review front, Queued and Review closed remain queue explanations; none authorizes a request or establishes fresh provider readiness. The operator stop is not an additional ordinary PR status. A channel derived only from local queue order says **Queue position**, while a verified ready front says **Up next**. A known matching admission hold identifies carried work, unsettled results or an unfinished dependency on that channel instead. Active or pending requests keep their own precedence; none of these labels changes review controls or authorizes dispatch.

## Independent queued priority

Each channel may also expose `queued_priority`, the first remaining PR under the configured order and current local round controls, with its stored PR number/head/base/ref. This is independent of the verified eligible front: a provider budget failure, cooldown, admission hold or recovery stop does not erase known local order. The source assessment retains its own state, reason, timestamps and `source_progress`; unknown source never becomes ready because priority is known. An eligible front can differ from queued priority when an earlier independent PR has unresolved work.

Priority uses the complete matching workspace and repository binding, skips locally closed/merged entries and finished channel controls, and stops at missing, retired or unknown predecessors. It neither requests reviews nor changes grants or scheduling. The browser places **Review front** on the earliest PR among these channel priorities. It advances when that PR has no review rounds remaining or leaves the open queue. Later eligible or running reviews show their status in their own channel. Source verification failure does not move the row label. Known admission holds and active/pending request status retain their own explanations. Source snapshot or comparison mismatches invalidate the corresponding priority; later entries are Queued only behind an established priority or front.
