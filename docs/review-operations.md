# Retained Operation Discovery

## Contract

`GET /api/v1/projects/{project_id}/reviews/operations` reads one compact page of retained native review operations under current authenticated project read permission. It performs no provider requests, review execution, retries or allowance changes. A list is discovery; select one operation for the compact status read below. The original [full operation read](review-execution.md#bound-execution-tools) remains available for explicit diagnostics.

Optional filters are `pull_number` (positive PR number), `channel` (`cli` or `hosted`) and `status` (`pending` or `all`, default `pending`). Pending includes queued, preparing, posting, active and uncertain operations, plus held operations only when their matching execution attempt still owns a reservation. `all` includes terminal and held history so a lost receipt can be recovered. Operations from other workers in the authorized project remain discoverable with attribution.

Pages default to five items, with an explicit `limit` from 1 to 100. Ordering is newest first by `(created_at, id)`. The signed `cursor` binds the service instance, principal, project and filters; preserve filters when continuing. Changing the page limit is permitted. Each page rechecks authorization and current operation states. Pagination is a keyset continuation over retained rows, not a historical snapshot across mutable states. No offset, automatic pagination or implicit continuation is provided.

The response contains `project_id`, `items`, `has_more` and a `cursor` only when more items exist. Each item contains only `id`, `pull_number`, `channel`, `head_sha`, `worker_id`, `state`, `reason`, `attempt_id`, `revision`, `created_at` and `updated_at`. Empty pages return an empty items array. Credentials, raw captures, allowance payloads, actor identities, configuration and policy are excluded. Invalid filters, malformed or mismatched cursors, and corrupt selected summaries fail explicitly without adopting partial results.

## Compact operation status

`GET /api/v1/projects/{project_id}/reviews/operations/{operation_id}/status` normally reads only `id`, `pull_number`, `channel`, stored `state`, `revision`, `stage`, `reason`, `attempt_id`, optional `evidence_id`, paired optional `review_finished_at` / `evidence_recorded_at`, optional `retry_not_before`, `updated_at` and `next_action`. The [pending-evidence expansion](#pending-native-evidence) adds selected blocker references. It rechecks current project read permission and performs no provider requests, capture-file reads, source refresh, Git work, execution or accounting changes. Unknown additive metadata is ignored by compact clients and is not forwarded into tool output; required known fields, canonical names and state/action validation remain strict. The existing full operation GET is unchanged for clients that need diagnostics.

When the exact current attempt has an admitted original comparison, compact status also includes `settlement_target`: `attempt_revision`, `repository_id`, `head_sha` and `external_id`. Together with top-level `attempt_id`, these are the current guard values for [explicit attempt settlement](hosted-settlement.md); `revision` at the top level remains the operation revision. The target is read from the same authorized local snapshot, including when no result evidence exists. It is omitted before admission. An empty external ID is retained honestly, including for CLI attempts. Invalid or mismatched retained admission facts fail the read rather than borrowing current PR metadata. These values do not assert settlement eligibility, verify that external work has stopped, or grant permission to retry; settlement still checks authorization, state and all guards atomically. A later transition requires a fresh compact read. The full operation response is unchanged.

`Prefer: wait=N` retains the existing notification-based result collection, from zero through 900 seconds; zero returns immediately. Cancellation detaches collection without cancelling the operation or reposting a review. After the wait, a fresh authorized local read selects the compact status and its exact attempt binding. The response always preserves the stored operation state; a display stage cannot override execution rules.

Stages derive from durable facts. Queued and preparing operations report those stages. Posting or active operations without a complete bound capture report `provider_wait` and `next_action: wait`; an issued trigger alone does not prove that a provider is running. When their exact complete evidence is already retained, they report `result_captured` and `wait` while native publication/settlement finishes; this does not invent terminal completion or finalization. An uncertain Hosted operation with reason `hosted_finished_inventory_unproven` reports `capture_blocked` and `contact_controller_owner`. Other uncertain operations retain `uncertain`. Held or rate-limited work reports `held`, failed work reports `failed`, and their next action is `read_diagnostics`; cancelled work reports `cancelled` with no next action (`none`).

A completed operation reports `evidence_ready` and `read_evidence` only when its actual same-project, same-operation, same-attempt evidence ledger record has matching original admitted anchors and a complete successful capture. Its evidence ID is the native ledger identity, never a browser projection or an invented handle. Failed or incomplete evidence can retain its handle but cannot supply ready coverage; a completed operation with such a capture reports `capture_blocked`. Completed state without a matching retained evidence record reports `unknown` and `contact_controller_owner`. A bare finished acknowledgement cannot establish an empty result. Evidence readiness alone does not establish finalization, policy sufficiency or merge readiness.

When the bound retained evidence has valid timing metadata, compact status includes `review_finished_at` from its original capture and `evidence_recorded_at` from the native evidence ledger. For Hosted reviews the first is the provider-reported publication finish; for CLI reviews it is the captured process finish. The second dates controller retention. `updated_at` remains an operation transition, including final settlement on completion; none records when an agent fetched or adjudicated the result. Their separation distinguishes delayed observation/retention from later settlement or worker collection without another full capture read. These are different clocks: no ordering, elapsed-time estimate, completion ETA or readiness guard is inferred from them. Unknown or invalid timing is omitted as a pair, not invented.

For a held Hosted `hosted_allowance_cooldown`, `retry_not_before` is the original validated deadline retained for that exact attempt, included when known. It remains visible after it passes; elapsed time does not grant permission or resume the terminal hold. The deadline is an earliest allowance recheck, not a reserved start time. This terminal hold retains neither the next shared provider slot nor a waiting queue position; another authorized request can use the next allowance. CLI/MCP diagnostics state this directly so a project can coordinate competing requests under its own priority policy. Other states and channels omit the deadline, and absent timing remains unknown. The compact read validates the same bound local allowance record used by full diagnostics without fetching provider state or opening capture files.

Without the pending-evidence expansion, the reader projects bounded identity and completion metadata from that one normalized evidence row; it does not load finding narratives or reparse provider bodies. It cannot invent finer preparation phases or provider progress that the durable journal does not record. Unknown facts remain unknown.

## Pending native evidence

Matching CLI/MCP clients request `X-FC-Review-Blockers: true` on operation/status reads and review-request result collection. Only a held `review_evidence_pending` result gains `pending_evidence`: `evaluated_at`, at most five `items`, and `has_more`. Each item identifies its source `operation_id`, optional `evidence_id` and zero-based `finding`, a reason (`capture_missing`, `capture_incomplete`, `finding_undecided`, `finalization_pending`, `fix_pending`, `route_undecided` or `route_fix_pending`), and the `route_id`/`target_pull_number` when a receiving obligation is unresolved. No finding narratives, rationale, proof text or provider data are repeated. Requests without this response-expansion header retain their existing shape.

These are **current local obligations**, not a reconstruction of what was pending when an earlier operation held. The selected expansion reads bounded retained capture/adjudication and route records under current project read authority; it makes no provider request, repairs no index and changes no review state. Other status reads retain their lightweight scalar-only path. An empty current list leaves the original operation terminal and does not establish readiness under other admission rules. CLI/MCP give the corresponding recovery action without requiring an owner investigation. The [route contract](review-routes.md) owns source and receiving requirements; resolving a route never erases original attribution or counts.

## Original source refusals

A newly retained `held` / `predecessor_parent_moved` operation includes optional `source_refusal`: the ancestor `pull_number`, its `parent_pull_number`, `observed_base_sha` and `expected_parent_sha`. Preparation records only these bounded original facts with the same guarded journal transition; diagnostic reads perform no provider work. A new `parent_unavailable` hold may instead retain `{pull_number,base_ref}` for the original child PR and base branch whose open parent could not be resolved. The child can be an ancestor of the selected PR. No parent identity or SHA is invented when unavailable. The selected target remains the outer operation PR. This metadata changes no source guard, scheduling, authorization, allowance or review accounting.

A `predecessor_unfinished` hold may retain `{pull_number,cause}` naming the actual blocking ancestor, different from the selected operation PR. The finite cause is `not_in_queue`, `discovery_incomplete` or `incoming_route_pending`. Incomplete discovery can mean pending evidence, incomplete configured rounds or missing coverage; it does not establish that findings remain. These original guard facts distinguish an ancestor dependency from the selected PR’s own `review_evidence_pending` hold. Read `reviews pull PR` and `reviews rounds read --pr PR --channel cli|hosted` for current scoped progress, following retained evidence and route handles when needed; queue absence also calls for `reviews execution`. These reads do not refresh providers. Explicit out-of-order selection bypasses predecessor progression only; the selected target’s own source, evidence, policy and provider guards remain.

Matching clients request `X-FC-Source-Refusal: v3` for compact/full operation reads and terminal request collection, accepting the strictly validated variants. Version `v2` clients retain the two original parent variants and omit the new unfinished-predecessor variant. Legacy `true` full reads and legacy compact reads retain only the original predecessor-mismatch variant; the unavailable-parent variant is omitted. Full responses without a supported opt-in retain their original shape. Older holds and pre-feature snapshots omit these facts; the client states that the original blocker was not retained and directs current scoped queue inspection without reconstructing the historical cause from current branch state. Backup inspection validates the bounded same-journal facts and restore preserves them.

## Bound clients

`reviews operations [--pr NUMBER] [--channel cli|hosted] [--all] [--limit N] [--cursor CURSOR]` reads one page. `reviews operations --help` is local and requires no profile, credentials or service connection. Select `reviews operation OPERATION_ID [--wait-seconds N]` after discovery for compact status. Add `--diagnostics` for the full retained operation, including its directly bound `evidence_id` when present. The wait range is 0–900 seconds; listing and status reads do not request replacement work. An `evidence_ready` result supplies the ID for the existing `reviews evidence EVIDENCE_ID` read.

MCP `review_operations_list` accepts optional `pull_number`, `channel`, `status`, `limit` and `cursor`. It uses the same bound typed client and authenticated HTTP API. Defaults and output are identical to the native list; the tool never polls or advances pages automatically. MCP `review_operation_read` returns compact status by default, accepts `wait_seconds` from 0 through 50 and optional `diagnostics: true` for the full operation with the same directly bound evidence handle. Its wait is result collection, not permission for another provider action.

For the exact Hosted `uncertain` / `hosted_observation_pending` case with an original attempt identity, CLI and MCP project `next_action: wait_for_observation` instead of an immediate owner escalation. The issued trigger is awaiting scheduled observation; the stored state, reason, stage, identities, timestamps and reservation stay unchanged. Continue other work and read status at a later useful checkpoint, without reposting or immediate polling. An uncertain state still ends the bounded result wait immediately. Escalate if observation remains stuck or a specific capture/identity failure appears; other uncertain reasons retain their existing owner guidance. This is client guidance, not provider execution proof or a change to the raw HTTP result.

For an active Hosted operation, `trigger_recorded`, `trigger_posted` and `trigger_recovered` confirm only that the original trigger exists on GitHub. Recovery of its delivery is not proof that CodeRabbit started or is still running. Compact and full CLI/MCP output explain this directly, retain the original facts and direct the existing owner to a bounded status wait and the returned stage/evidence handle. `updated_at` dates a local transition, not the last provider observation; repeated pending observations need not change it, and identical source can reuse its existing immutable capture. The optional observer metadata below reports actual local check activity and the scheduler’s next eligible check; these operation reads expose no provider-start timestamp or completion ETA. The service's [recovery scheduler](review-execution.md) observes the original attempt without reposting; its backoff and provider limits do not require another agent observer or review request. A result may already be captured while settlement is pending, so the trigger reason alone must not override `result_captured` or other evidence facts.

For held `hosted_allowance_reply_pending`, compact and full CLI/MCP output explain that the original non-review query was observed but no attributable reply arrived in the bounded preparation window. The terminal hold does not resume when a late reply arrives. Its compact agent next action is `new_request_to_recheck_allowance`: for the still-authorized planned review, use one later fresh request/key and current configuration/head. Normal preflight obtains fresh allowance and rechecks admission. Respect known provider cooldowns and avoid rapid retries; no manual GitHub repair or additional round grant is needed merely because preparation held. An old available reply is not fresh permission. Original-key replay preserves the hold, while unknown action outcomes still require their original keys; never repost the old query or reset controls. `hosted_allowance_unproven` directs an explicit full diagnostic read to the original query link and retained source handles without inventing the provider cause. These hints preserve all stored fields and raw HTTP status behavior; a held preparation has no scheduled review execution to wait for.

Full operation reads and review requests from matching clients send `X-FC-Operation-Evidence: true`. For a full read or a collected terminal request result, the service projects the optional `evidence_id` from the same bounded, project/operation/attempt/anchor-checked ledger lookup as compact status, in the same authorized database snapshot as the returned full operation. It does not load captures or findings, fetch provider data, change completion/accounting, or make an additional client request. Responses without that expansion retain the journal-only shape. The handle alone makes no completeness or coverage claim; compact status owns that assessment. This response metadata is not persisted in the operation journal.

## Original Hosted observer diagnostics

For a Hosted operation in `posting`, `active` or `uncertain` with a current attempt, compact status and full operation reads include an `observer` object when the client sends `X-FC-Hosted-Observer: 1`. Matching clients request this automatically. The object is bounded process-local metadata for that exact admitted project, operation, attempt and configured capability; it is never retained as execution authority. A process restart reports `state: unknown` with no invented timestamps until that attempt is checked again. Historical captures and lifecycle observation of the PR do not establish this observer’s current activity.

`checking` means an actual live or scheduled pass is running; overlapping checks remain `checking` until all have returned. `waiting` means the latest completed pass returned without a collection/local error, `retrying` carries a static safe error class, and `stopped` means the owning recovery worker ended. `last_check_at` dates a completed pass, including a failed one. `last_source_at` dates the latest validated complete provider collection by this process, before identical source is deduplicated into an earlier immutable capture. Successful unchanged polls advance these facts without adding journal entries or captures. Local publication or settlement using already-retained evidence can update the check time without inventing a source collection. Optional `next_check_at` is the recovery scheduler’s chosen next eligible check, subject to interruption and subsequent activity; it is neither a reserved provider start nor a completion ETA. Clock corrections do not impose ordering between these timestamps.

The bounded `reason` describes the latest check’s semantic result, separately from the durable operation reason. A complete source check can return `attribution_window_closed`, `publication_not_proven` or another unresolved result with an empty `error`; that establishes neither provider activity nor review completion. Provider and local failures expose only static safe `error` codes, never response bodies or exception text. Reading these fields invokes no provider, advances no operation or round, and does not wake result waits on each poll. Preserve the original request and attempt while observing its outcome.

## Hosted activity guard diagnostics

Hosted activity checks are separate from the non-review allowance query. A terminal activity refusal can occur before preparing that query or at the final guard before posting the review trigger. New operations retain bounded failure classes in their existing reason: provider API rate limiting, access rejection, missing resource, invalid response, unavailable read, conflicting or unknown progress, and invalid observation timing. A known active progress signal remains its own refusal. These classes change neither review allowance nor guard acceptance and expose no raw provider responses or private configuration.

Compact and full CLI/MCP output explains the retained class and the corresponding access, source, activity or later-request recovery. Reads do not fetch provider data or retry an operation. Old generic activity holds and failures cannot identify their lost subcause; a successful current read is not evidence of what failed earlier. A still-authorized planned review can use a later fresh request under current source/configuration and all normal checks; an unknown action outcome must preserve its original key. Grants, prior reviews and canceled timer requests are not reset by this recovery.

## Original Hosted allowance-query diagnostics

Matching clients send `X-FC-Hosted-Query: 1` only on the explicit full operation read (CLI `--diagnostics`, MCP `diagnostics:true`). For a held Hosted allowance preparation, optional `hosted_query` identifies the original retained `query_id`, confirmed `query_comment_id` and `query_url`, plus the latest verified `observation_id`, `capture_id` and `captured_at` when retained. Open the query URL to inspect that original non-review command and adjacent provider reply. A missing comment means posting was not confirmed; a missing capture does not mean no provider action occurred. Preserve the original request/key rather than reposting an uncertain query. A proven terminal `hosted_allowance_unproven` hold authorized no review trigger: if that planned review remains authorized, one later fresh request/key repeats normal current source/configuration/round/provider checks. This is not automatic retry permission; a still-running or unknown outcome must keep its original request/key.

The projection uses the same currently authorized project/operation/attempt snapshot. It exposes no raw bodies, private paths, credentials, current allowance or inferred parser cause. Capture handles identify private retained source; they are not download URLs or execution permission. The read performs no provider request or capture-file access. Compact reads and clients without the exact opt-in retain their existing response shape; older operations with no retained query have no invented diagnostic.

## Proof boundary

Focused offline checks exercise discovery and compact status through the native reader, public handler, bound client, CLI and official SDK tool discovery/calls using synthetic retained operations. They cover exact evidence binding, incomplete/missing captures, wait cancellation and fresh authorization, strict output validation, compact/default and explicit diagnostic views, and unchanged source/accounting records without provider work. Installed-host behavior, live provider state and packaged deployment are separate integration proof.

## Authorized operator recovery

Use [explicit attempt settlement](hosted-settlement.md) for its supported local verified-stop or abandonment action and original target guards. A routine local abandonment already covered by the operator’s authorization does not require a human to certify remote information unavailable to both the human and the agent. Make the explicit abandonment choice honestly instead of claiming an independently verified stop. Escalate an actual authority gap, a consequential choice outside the authorization, or information only the human can supply. Local settlement does not stop a provider, authorize another review, grant credit or erase late results; preserve the original identities and history.
