# AI-Guided Onboarding

## Goal and implementation status

Let a user ask their AI to add FireController to an existing project and receive a working, verified setup with clear ownership of the imported information. Local private profile creation and POSIX bound launcher commands are implemented. The bundled [onboarding skill](../skills/firecontroller-onboard/SKILL.md) guides the implemented API, client setup and prepared review/map imports; a dedicated onboarding wizard remains unimplemented and the [selected historical provider collector](history-collection.md) provides explicit acquisition, retained checkpoints and private export. The [prepared map import](map-import.md) implements additive preview/apply with stable source mappings and private provenance; its owning contract records proof and limits. The [prepared review import](review-import.md) preview/apply boundary uses the existing administrator observation API; its owning contract records current proof and limits. This is a first-release usability requirement; broad importer coverage is delivered incrementally.

## Supported setup flow

1. Discover the intended repository, remotes, current project instructions, and available FireController instance. Report the selected repository identity; do not infer that another checkout or an already-configured instance is the intended project.
2. Offer simple local installation or connection to an existing instance. Resolve the repository's stable provider identity before creating its project. If that repository already belongs to a project in the instance, report the duplicate and offer to connect to the existing project within the caller's access; do not silently create another. Otherwise create an isolated project. Keep credential handling in the application, not generated shell arguments or tracked files.
3. Select project display name and appearance, worker names/roles, and preferred CLI/native-tool integration. Create private per-agent profiles and any distinct launchers through the supported application commands. The [client contract](agent-client.md) prevents shared mutable actor context.
4. Ask what history should be imported before broad provider collection: date range or PR range, open work only versus selected completed history, review captures if available, and approved repository documents or existing controller exports. Explain expected provider scope and the distinction between public and private source material.
5. Discover candidate project-map tracks, phases, return points, current jobs, and history from those selected sources. Mark AI-inferred structure as a proposal, with source pointers and confidence/uncertainty; do not present an inferred milestone or historical completion as a verified fact.
6. Preview the normalized import, conflicts, public fields, source provenance, missing evidence, and proposed map. Let the user adjust scope and approve the concrete import when required by their onboarding request. An explicit approved plan may be applied without asking again for each row.
7. Apply idempotently through the same authenticated APIs as ordinary clients. Verify project isolation, profile resolution, one job round trip, message delivery, and retained source attribution. Return the useful commands, current assignment pointers, and any unfinished import work.

Onboarding should use a few meaningful questions, not a long setup checklist or repeated permissions for routine reversible steps already authorized. A read-only preview never grants permission to publish private history. Default imported data remains private; enabling public status requires an explicit visibility choice.

## Private agent setup commands

Private client setup is local filesystem work, separate from project registration, historical import and service authorization. The selected commands are:

```sh
fc --profiles-file /private/agent/profiles.json --profile project-builder profile create --server https://controller.example.com --instance INSTANCE_ID --project PROJECT_ID --worker WORKER_ID --credential-file credentials/worker.token
fc --profiles-file /private/agent/profiles.json --profile project-builder profile launcher --output /private/bin/fc-builder
```

`profile create` requires an explicit absolute profile-file path and explicit profile selector. It stores a version-one private configuration containing the supplied binding and credential reference; it never reads the credential, contacts a service or verifies the remote identity. A relative credential reference resolves against that profile file as usual. Use `doctor` for authenticated verification. The command creates a new file atomically and never modifies an existing configuration. Its immediate parent must be a real private directory; existing higher ancestors may resolve through directory symlinks, including platform system directories. A matching existing profile is an idempotent success with no write; a conflicting selection is refused while preserving every existing profile and byte. Use a separate private file for another agent when its desired binding is absent.

`profile launcher` requires an existing selected profile and an explicit absolute output path. On supported POSIX hosts it creates an executable shell launcher that binds the absolute profile file, profile name and current `fc` executable, with an optional explicit `--executable` path. It quotes paths/selectors as literal arguments, forwards caller arguments, and rejects conflicting profile options through the normal duplicate-option guard. Process defaults do not change its binding. Installation never edits PATH, project instructions or another agent's files. Existing identical launcher bytes are an idempotent no-write success; different existing files are refused. Native Windows launcher generation is unsupported in this initial boundary; explicit profiles and per-process `FC_PROFILE` remain available there.

Keep the generated launcher in an owner-private directory. To expose its short command through an existing POSIX PATH directory such as `~/.local/bin`, create a new symlink to that absolute private launcher; leave the shared directory permissions alone and refuse an existing destination. The launcher remains private and keeps its fixed profile binding when invoked through the symlink.

Both commands use compact structured output and safe diagnostics. They publish private files without replacement, preserve unrelated configuration, and report local publication uncertainty instead of removing a file that may already be usable. They create no worker, grant, credential, job, message, review or pending-operation receipt. Project and access registration use the setup API above; selected history acquisition and prepared review/map imports have their own commands. Selected current jobs/checkpoints, historical messages and effective review settings have a separate [legacy adoption path](legacy-adoption.md). Other historical coordination classes and a dedicated graphical wizard remain outside that path.

## Private setup proof

The profile/CLI integration passed full `make check build` before the final executable-access correction, followed by focused profile/CLI race tests, vet, formatting and documentation checks for that correction. Clean runtime checkpoint `b1756115e76632f9feefb81b0110cd23f810efe0` then passed six actual packaged groups with 28 CLI invocations and no service requests. The groups cover private creation with absent credentials, byte-preserving replay and multi-profile conflicts, literal launcher execution with interleaved project identities, strict arguments/FIFO refusal, concurrent identical creators, and a real failed stdout write followed by exact recovery. Independent integration inspection caught the executable-access defect: a file with only another permission class's executable bit could produce an unusable launcher. The corrected current-user access check has a failing-before/passing-after regression and actual shell execution proof.

These checks ran on Linux/WSL with POSIX launchers. They do not establish native Windows launcher support, hostile same-user filesystem race protection, power-loss durability, remote authorization, credential provisioning or the broader guided import flow. Local setup returns configured facts rather than a verified connection or a pending-operation receipt.

An independent forward test used the bundled skill with fresh packaged `fc`/`fcd`, a synthetic repository checkout, one isolated local instance and two workers. All six groups passed using eight setup API requests and 37 profile-bound CLI calls: authenticated bindings, separate grants/profiles/launchers, per-worker job round trips and exact retries, bidirectional synthetic messages/full reads/acknowledgment, unchanged read state, private files and preserved binaries. The tester needed the linked command tables for exact job/message spellings, without reading implementation source. Its owned service/listener stopped afterward. This proves the supported fresh setup path, not a historical importer, host installation, automatic startup service or remote deployment.

An independent skill-guided prepared-map forward test used clean packaged source `ee344a0d36edb98065f6761647c54c7bb1467f44` and eighteen real profile-bound CLI calls. Three documentation-derived entries retained explicit inference/uncertainty and source provenance through preview/apply, original-key replay and a new-key unchanged rerun. A manual edit by a separate ordinary worker remained at its newer revision after a conflicting preview, refused stale apply and exact recovery of the original import receipt. Import history remained one source revision, no duplicate entries were created, and all owned daemons stopped with zero external HTTP and unchanged binaries. Synthetic repository-identity setup was separate from the real daemon/profile/CLI workflow; this does not prove live registration or provider history collection.

## Project appearance setup

After creating the project and its explicit administrator/worker profile, use the [presentation commands](project-presentation.md#agent-use-and-proof) to read current settings and optionally replace a complete configuration from an owner-private JSON file. Defaults need no write: an absent record is revision 0 with the project's current name and the refined fire theme. Ask for desired branding only when it would improve setup; accepting defaults is sufficient. Keep settings out of ordinary job/inbox context. The browser applies authorized changes live without rebuilding assets; this does not configure hosting or install the browser into an existing deployment.

## Import semantics

The [legacy adoption contract](legacy-adoption.md) owns conversion from earlier controller exports. Its optional utility inspects sealed snapshots and prepares selected current jobs/checkpoints and messages for guarded native preview/apply. Effective review controls use separate source-helper preparation with complete source evidence and authoritative finding/route clearance. Other historical coordination classes remain outside the selected path; it does not reconstruct all prior job revisions.

The user controls historical depth. Support bounded ranges and resuming interrupted collection; do not download all repository or provider history by default. Record source repository, scope, snapshot/version or immutable provider IDs, collection time, and transformation version. Imported text and events are data, not executable instructions.

Keep original facts separate from AI summaries and current editorial structure. An import timestamp is not the original creation time of a job or review. Unknown historical times, missing captures, incomplete pagination, and unavailable proof remain explicit. Selected completed history can populate map/history views without creating active jobs or granting review coverage.

Stable source keys make repeated application idempotent. Conflicting source facts or newer application revisions require a reviewed resolution rather than silent overwrite. Preview fingerprints bind the approved source set; changed inputs trigger another preview. Avoid positional matching by headings or worker display names when stable IDs are available.

Onboarding reads only selected repository sources and scoped provider data. It must not scan unrelated project databases, user-home credentials, other agents' private profiles, or every file under a shared workspace. It must preserve existing project instructions and expose the small proposed integration diff rather than replace `AGENTS.md` wholesale.

## Optional agent skill

The bundled [firecontroller-onboard skill](../skills/firecontroller-onboard/SKILL.md) guides installation or connection, project/worker access setup through the implemented API, private profiles, POSIX launchers and verification. Use it from a matching FireController checkout/release with the agent host's supported skill installation, or ask the agent to read its `SKILL.md` directly. It is optional and is not installed into a host implicitly. Existing connections use the short [everyday skill](../skills/firecontroller-use/SKILL.md); its job-writing, coordination and editorial references load only when relevant. The separate [review skill](../skills/firecontroller-reviews/SKILL.md) retains existing review mechanics without selecting new review-train strategy. Install whole skill directories, including referenced files.

Distribute the skill with the matching supported release. It describes discovery, scope questions, profile binding, quiet tool use, the optional [agent workflow](agent-workflow.md), and verification using actual documented commands. Clearly separate required tool semantics from recommended working habits. A skill is guidance; it does not replace API validation, impose checkpoint cadence, add hidden quotas, perform automatic external messaging, or imply permission beyond the user's request.

Installation into an agent host is optional and explicit. CLI onboarding works without a particular host or model. Host capability detection identifies whether native tools, asynchronous results, and isolated connection binding are supported. Generated guidance must name limitations instead of promising unsupported wakeups.

Local review execution additionally needs administrator-configured source availability on the server, as owned by [review execution](reviews.md#admission-and-execution). Check server-configured source availability separately from connecting a client checkout; the current skill does not verify this executor capability. [New review enrollment defaults](review-round-controls.md#operational-controls) initialize each absent channel plan. For migration, apply verified source-owned controls before enrolling those PR/channel pairs. Required review channels are selected explicitly before aggregate sufficiency can be reported; a jobs/messaging-only project needs no review executor setup. Repository binding still requires its documented provider identity verification.

## Acceptance scenarios

- Add a second project with an identically named worker; the first project's profiles, messages, map, and settings remain unchanged.
- Select open work only or a bounded historical range; collection and imported projections honor that scope, including provider pagination and rate limits.
- Preview without applying, revise the map, and apply twice; one resulting import retains provenance and creates no duplicate job/message/review.
- Interrupt collection or application and resume; retained scope and idempotency keys prevent duplication or silent widening.
- Import incomplete historical evidence; unknown times and unproven review coverage remain visible, and generated summaries do not count as captured review proof.
- Onboard using CLI alone and using an AI-assisted flow; both resolve the same project/worker context and pass the same isolation and communication checks.

## Optional public website

Ask whether the project needs a shareable anonymous view. Private is the default. When requested, use the [publication preview/apply commands](public-site.md#agent-setup-commands) under an explicit administrator profile to select approved branding, summaries, links and PR enrollment. Show the resulting public fields and destinations before applying within the user's authorized scope. Share the canonical `/projects/{handle}` address. Signed-out visitors see only approved public content; signing in at that same address enables authorized private content. Never share a credential. Existing private messages, briefs, notes and findings remain private regardless of publication. The public website contract records current executable proof and deployment limits.
