# Per-PR review rounds

## Project defaults

Newly enrolled PRs receive product bounds of minimum two / maximum three Hosted reviews and minimum two / maximum six CLI reviews unless the project policy explicitly supplies `round_defaults`. That optional policy object contains both `hosted` and `cli` bounds, each with explicit `minimum` and `maximum`; minimum can be zero, maximum is finite from one through one thousand, and minimum cannot exceed maximum. New Hosted and CLI controls both require two consecutive eligible zero-accepted rounds for early taper, after satisfying their minimum.

Set defaults through the existing guarded project policy configuration, using its current revision and explicit key. The selected bounds initialize only missing PR/channel controls during enrollment. Updating defaults leaves existing grants, completed counts, taper and closure intact; deliberately change an existing PR through its ordinary round controls. Every policy write replaces `round_defaults`; omitting the field removes previously stored project defaults and restores product defaults for later enrollments. These values are project preferences rather than provider quota or permission to dispatch automatically.

## Implementation status

The native service, bound CLI and MCP implement the contract for explicit per-PR/channel grants, minimum and maximum requirements, settings-only taper, closure/reopening and persistent native completion accounting. Source preparation and final admission recheck the grant independently of captured coverage. Policy/readiness reads expose outstanding round requirements; backup validation preserves control history and native completion links.

Carried operational adoption is supported through independently guarded preview/apply, retaining source provenance and minimum-only policy. External Hosted settlement/credit, browser progress and automatic channel-front scheduling remain separate consumers. A grant performs no provider action and does not weaken the separate [review policy](reviews.md#project-policy).

## Operational controls

Hosted and CLI retain independent per-PR channel state. Each explicit start selects at most one eligible target in queue priority order, preserving actual-parent dependencies. A cooldown or active review in one channel does not hold the other channel. Automatic scheduling remains a separate consumer. Minimum and maximum count additional completed rounds. Equal values express an exact count; the CLI's `--exact` is only shorthand for those equal bounds. A maximum permits early taper once the minimum is satisfied.

New execution enrollment atomically initializes missing PR/channel controls using the selected [project defaults](#project-defaults): explicit policy `round_defaults` take precedence over product bounds, and new controls use taper two. A re-added pair with any retained native review operation is excluded from this initialization, so an older unconfigured pair remains unconfigured. Reordering, pausing or changing capability leaves existing enrolled pairs untouched. Existing grants and controls, including explicit controls installed before enrollment, are preserved.

Default early taper is two consecutive eligible rounds with zero accepted findings in either channel. A selected minimum still applies. A useful accepted correction resets the applicable dry streak; failed, incomplete, ambiguous and rate-limited attempts cannot supply successful dry rounds. Preserve the distinction between exhausted allowance, taper completion and explicit closure.

Closing a channel affects only that PR/channel. Every explicit additional-round grant reopens that channel, including after taper or explicit closure, while preserving its earned streak and completed history. A maximum-only grant permits another eligible result before taper is evaluated again; it does not silently increase the requested minimum. While the channel remains open, an explicit minimum still requires that many additional completed rounds. No implicit project-wide closure or reopening follows from a local change.

Candidate, base, effective-parent or history movement after start preserves earned PR/channel completion, completed rounds, allowance history, taper, limits and closure. It never automatically reopens the channel or requires more rounds. Original captures still identify only the code actually reviewed. Extra review is deliberately requested through the existing controls. Closing, tapering or exhausting a channel does not erase unfinalized evidence, accepted/routed findings or imported obligations across any head, establish current CI or authorize a merge. Explicit closure waives any remaining round minimum for that PR/channel, while required-channel coverage and outstanding obligations remain enforced. Closure does not create review coverage; current source readiness is a separate assessment.

## Native control semantics

A per-PR/channel grant is an explicit project write operation, separate from administrator-owned project-wide required channels. Requested additional maximum is between one and 1,000; additional minimum is between zero and that maximum. The service stores checked cumulative stopping thresholds while preserving consumed counts, the accounting epoch, imported provenance and original operation attribution. Cumulative counters stay within 9,007,199,254,740,991. Historical controls retain their original representation and proof; an explicit edit moves the current rule to cumulative semantics. Existing unconfigured allocations remain unconfigured when already enrolled or re-added with retained native operations; eligible missing controls receive the selected [project defaults](#project-defaults) under the [enrollment rules](#operational-controls). Earned completion follows the [PR/channel rule](reviews.md#retained-native-channel-completion) in either case.

One eligible completion has a completed native operation/attempt, validated attributable complete capture and finalized source counts. An operation counts once, independently of whether its accepted findings have been fixed. Original finalized accepted counts determine its historical streak contribution; later decision/fix corrections remain separate obligations and do not rewrite consumed rounds. Failed, rate-limited and incomplete attempts consume no completed round. Queued, preparing, posting, active and uncertain work occupies capacity. An attributable complete terminal result awaiting finalization also occupies its original capacity, without receiving completion credit early.

Discovery completes when the maximum is consumed, or an eligible completion since the latest additional-round grant reaches the minimum and the retained clean streak meets taper. The immutable grant's completed count marks that boundary; no new accounting epoch or reset of earned streak is needed. A maximum-only grant of two on a tapered channel therefore permits up to two more rounds: one clean completion may taper again using the preserved streak, while a completion with accepted findings resets the streak normally. A minimum of two additional rounds prevents stopping until those two complete even if the streak already meets its target. An accepted completion resets the cumulative rule's streak, including a result already posted before closure or taper. Previously retained grants and exact-key receipts keep their original meaning; deployment alone never reopens a channel.

A taper update changes only the selected clean-streak threshold and its derived completion state. It preserves consumed rounds, the current streak, minimum/maximum, explicit closure, accounting epoch, original grant binding and imported baseline/provenance; it grants no additional review and never reopens a closed channel. Existing controls retain their stored threshold until explicitly updated. The original carried streak can satisfy a newly lowered threshold once the minimum is met; a later additional-round grant still requires a new eligible completion. A historical reached-taper flag alone does not satisfy a newly selected threshold. Updates use the same guarded endpoint, atomic history and exact-key replay as other controls. Setting the already selected threshold is a no-op: the receipt retains the current revision, with no setting event or reinterpretation of historical taper proof.

Close stops new dispatch, including queued/prepared actions at their final guard, and does not cancel a possibly posted action. A posted result can still be captured, adjudicated and counted once with its original operation binding. Changing limits includes underway and complete-unfinalized work: “one more” includes that round. To require a round after it, wait for its finalization before granting the additional requirement. The service refuses a new maximum smaller than unavoidable occupied work. Exact-key replay never purchases another round or changes the retained request.

Work accepted while a PR/channel was unconfigured has no round grant binding. The service refuses a grant with `review_round_inflight` while that pair has unbound queued, preparing, posting, active or uncertain work, or an attributable complete result awaiting finalization. Closing the pair first does not bypass this refusal. Finish or settle that work before granting additional rounds; the new grant neither binds it retroactively nor awards it completion credit. Failed, incomplete and finalized terminal results do not occupy this unbound capacity; their separate evidence and finding obligations still apply.

The first explicit conversion of a legacy rule reconstructs only its clean streak from immutable, already-counted current-epoch completions. This handles older rules that froze the displayed streak after taper: all-clean results preserve earned progress, and a recorded accepted result resets it. It adds no completion credit, changes no original capture/counts and leaves the previous history bytes intact. Backup replay validates the same evidenced transition. Older past epochs and imported history remain historical evidence, not new native completions.

Per-PR changes use their own revision and actor attribution rather than changing the project policy revision or holding unrelated PRs. Requests retain their original grant binding and recheck the current same-epoch limits, closure and obligations before preparation and provider dispatch. Both source preparation and final transactional admission allow another round after earned PR/channel completion only while the bound grant still requires discovery. They preserve pending-capture/finding obligations, source identity, current authority, provider limits and reservations. For ordinary stacked progression, an explicitly finished grant replaces the predecessor single-capture requirement; outstanding evidence/fix obligations still hold dependent work. Closure or exhausted allowance without validated native completion remains a separate readiness limitation and never manufactures earned credit; later Git movement alone does not create that limitation.

If a queued request’s target no longer matches its original comparison, preparation holds that request rather than rebinding it. Follow the [review-execution](review-execution.md) contract with a qualified current comparison and fresh authorized request/key; preserve retained rounds and known cooldowns instead of resetting grants. The recovery does not itself change configured PR queue order.

Control reads are local, compact and provider-free. Project write mutations use the ordinary authorization, expected revision, idempotency and atomic event/receipt rules. Their compact change events identify the affected PR/channel resource and its revision; the durable event cursor remains the delivery deduplication identity. Storing a grant does not authorize provider calls. Carried adoption uses the separate administrator controls below; explicit channel-front selection uses the independently durable contract below.

## Refusals and recovery

New review requests check configured rounds during acceptance, not only at dispatch. A closed, tapered or exhausted channel refuses the new request immediately; occupied capacity can also refuse it. Preparation can instead hold an already accepted queued operation, while final admission and action verification return conflicts. Neither outcome grants another round or erases the original operation.

| Code | Where it applies | Caller action |
| --- | --- | --- |
| `review_round_revision_conflict` | Grant, close or taper with a stale expected revision; details include `current_revision`. | Read the current control and reassess the intended change before a new mutation with its current revision. |
| `review_round_unconfigured` | Taper without an existing control. | Read the selected PR/channel; establish a grant only when additional rounds are authorized before changing its taper. |
| `review_round_revision_exhausted` | A control mutation cannot advance its retained revision. | Stop retrying the mutation and seek operator investigation; do not reset retained history. |
| `review_round_inflight` | A grant encounters unbound unfinished work or requests less capacity than already occupied. | Finish or settle unbound work first. For bound work, wait for finalization or choose an explicitly authorized maximum that includes it. |
| `review_round_closed` | New request acceptance, preparation, final admission or action verification finds explicit closure. | Leave the channel closed unless a new additional-round grant is authorized; closure is not a transient retry condition. |
| `review_round_complete` | Those review gates find taper or consumed maximum. | Stop requesting rounds under that completed grant. Reopen only through an explicitly authorized additional-round grant. |
| `review_round_capacity` | A grant would overflow safe cumulative counters, or review admission finds occupied allowance or a counter ceiling. | Inspect the control and retained operations. Wait for occupied work or obtain an authorized additional grant where appropriate; a counter ceiling requires operator investigation, not repeated requests. |
| `review_round_changed` | Binding or later review gates find a missing or incompatible original grant binding. | Read the retained operation and current control. Resolve the changed binding; if further review remains authorized, use a qualified current comparison and fresh request/key rather than reviving a terminal operation. |
| `forbidden` / `unauthorized` | Control reads, writes or exact-key replay lack current permission or valid credentials. | Restore the required access through the authorized owner before retrying; a retained receipt does not preserve withdrawn authority. |

A definite refusal is different from an uncertain write outcome. Recover a possibly accepted mutation with its original binding, body and key before proposing a changed request. Any later authorized review still obeys source, finding, provider and known-cooldown guards.

## Bound commands and API

`fc reviews rounds --help` identifies the existing settings read, and `fc reviews rounds read --help` explains its selectors and counters without loading profiles or contacting the service. The read selects one explicit PR and Hosted or CLI channel; inspecting both channels uses two reads.

Commands use the selected project profile with ordinary project write permission. Workers can grant, close and reopen a PR/channel directly; no Overseer identity or administrator handoff is required. Read-only credentials and read-only browser sessions cannot change controls. Reads retain the ordinary five-second budget and perform no provider work. `--min` defaults to zero; `--exact` is exclusive with `--min` and `--max`. The older `--expected-revision` spelling remains a compatible alias; supplying both spellings is refused. A close requires the current revision and omits allocation fields. A taper update requires the current revision and `--taper` from one through one thousand, without allocation fields.

```sh
fc reviews rounds read --pr 42 --channel cli
fc reviews rounds grant --pr 42 --channel cli --expect-revision 1 --max 8 --key cli-42-grant
fc reviews rounds grant --pr 42 --channel hosted --expect-revision 1 --min 2 --max 2 --key hosted-42-grant
fc reviews rounds taper --pr 42 --channel cli --expect-revision 2 --taper 2 --key cli-42-taper
fc reviews rounds close --pr 42 --channel cli --expect-revision 3 --key cli-42-close
```

`GET /api/v1/projects/{project_id}/reviews/rounds/{pull_number}/{channel}` returns the compact configured state, revision/epoch, bounds, consumed/dry counts, taper and closure. An unconfigured read explicitly returns `configured:false` with revision zero. Project-authorized write `POST` at the same route accepts `expected_revision`, `action` (`grant`, `close` or `taper`), grant-only `minimum`/`maximum`, and taper-only `taper`, with the explicit idempotency header. The receipt contains only pull number, channel, revision, epoch and outcome. Exact-key replay returns that original result after later changes or restart. Replay requires current project write authorization: after write permission is withdrawn the service refuses it with `forbidden`, and after credential revocation it refuses it with `unauthorized`.

MCP `review_rounds_read` and project-write `review_rounds_configure` use the shared typed client, bound project/worker and strict declared arguments. MCP grant arguments use explicit minimum and maximum; exact means equal values. Neither tool refreshes source, starts a review or silently generates a key. A dispatched write with missing or invalid output is uncertain: retain its original binding, request and key for exact recovery.

## Carried rule adoption

An administrator can preview and apply one prepared effective PR/channel rule before execution enrollment. Adoption requires revision zero, no configured destination control and no unresolved native operation for that channel. Enrollment preserves the adopted rule. Preview binds the normalized input to the instance, project, administrator and worker; apply rechecks repository identity, authority and guards transactionally. Exact-key replay returns its original receipt without overwriting subsequent changes.

The prepared record retains remaining minimum and maximum, dry streak, taper threshold, reached taper and closure with source identity/key and digest. Native used starts at zero: imported configuration is not a native attempt, captured result or completed round. Genuine native completions advance the carried policy. Explicit additional grants stay finite and clear minimum-only state while retaining the carried origin and cumulative history.

Version-two records can preserve an absent maximum using maximum_unbounded true and maximum_remaining zero. This differs from an exhausted finite allowance. Remaining minimum may reach 9,007,199,254,740,991; native counters refuse overflow. Finite prepared limits remain at most 1,000, and dry/taper limits retain their native bounds. Unknown source rules must refuse rather than invent a cap or reset.

Use fc reviews rounds adopt preview --file PATH, then apply with the same file, --preview SHA256 and --key KEY. Files must be bounded owner-private regular JSON files. MCP exposes review_round_adoption_preview and review_round_adoption_apply with the same native guards. The [carried-obligation contract](adoption-obligations.md) owns source-policy linkage, admission holds, guarded resolution and retargeting. Source acquisition and offline preparation are separate tooling work; prepared input never grants live review authority.

See [refusals and recovery](adoption-obligations.md#refusals-and-recovery) for round-adoption refusal codes and caller actions.

## One explicit channel-front run

`reviews start --channel cli --key KEY` accepts one durable selection before provider reads and authorizes at most one ordinary exact-head child operation. Hosted uses the same independent contract. The service considers configured queue priority while preserving actual published parent dependencies: a Draft, comparison-local refusal or pending earlier PR evidence does not block independent later work, but cannot be bypassed by its real dependent. These are PR-local holds; a queued, active or uncertain native operation in the same channel holds new selection with `review_inflight`, even for independent later work. Incoming routes and retained source obligations remain guards even after round completion or captured coverage. Verified external Hosted results still awaiting native reconciliation hold that PR's Hosted channel; imported labels alone are not authority, and old-head obligations survive metadata movement. Fresh verified merged entries can be skipped. Closed, tapered or exhausted grants do not erase unfinished evidence or fix obligations.

Acceptance binds the authenticated actor/worker and current configuration, policy and installed capability. `--expect-pr NUMBER` is an assertion, never forced selection. Optional `--expected-configuration-revision REVISION` asserts acceptance against a known configuration. Both assertions reject explicit null HTTP values. Paused execution returns `reviews_paused`; an unconfigured channel returns `review_not_configured` without storing a request or receipt.

Each selection acquisition phase performs source reads outside transactions within one cumulative fifteen-second budget, excluding local storage retry time. If a capacity race returns the selection to `queued`, its later acquisition starts a new budget. Contiguous metadata windows contain at most four PR reads per worker, with two owned workers. When an expected PR is present in the configured queue, acquisition is bounded by its queue prefix. If it is absent, the worker can read the full queue before reporting `expected_pr_mismatch`. Acquisition coalesces identities and cancels and joins discarded lookahead. Only the consumed verified prefix participates in selection and metadata publication. An open target is resolved through ordinary comparison acquisition; speculative reads cannot authorize a child. Transport, account, configuration and storage uncertainty cannot masquerade as a skippable PR-local refusal.

The final transaction rechecks authority, configuration, policy, repository, source obligations, incoming routes and current progress before ordinary child admission and atomic selection linking. Selection grants no rounds and captures no provider credit. States are `queued`, `selecting`, `selected`, `held` or `empty`; selected records permanently identify their one original child. Restart recovers only unfinished read-only selection. A terminal hold never resumes itself: after resolving its cause, a newly authorized start uses a new key. Automatic Hosted scheduling and automatic CLI re-admission are not implemented by this capability.

Selection admission has a separate global limit of 256 queued or selecting selections. If that limit is occupied, a new start returns HTTP 503 `overloaded` before acceptance, storing no selection or receipt; retry the exact original request with the same key and binding after capacity becomes available. Ordinary request capacity leaves an accepted selection pending. Scheduling skips projects with 32 unfinished requests and waits while the service-wide 256-request limit is occupied, without source reads. If capacity fills during source acquisition, child admission rolls back and returns the same selection to `queued`, freeing its worker for other eligible projects. The existing half-second idle wait bounds checks when nothing is eligible. Once capacity is available, the selector rechecks current bindings and reacquires source facts before linking at most one child; terminal 409 refusals remain holds.

After the current configuration, policy and capability checks pass, a different key while a selection is queued/selecting returns `review_busy` with only the validated selection ID, channel and pending state. A request that fails an earlier check receives that refusal instead; for example, a stale expected configuration revision returns a revision conflict rather than a busy handle. The `review_busy` refusal has no receipt and does not adopt the other caller's expected PR. Original accepted-key replay preserves the original selection even after configuration changes. With a zero wait it returns the same immediate receipt; a positive wait can instead return a terminal selection result (HTTP 200). The CLI defaults to a two-second wait, so use `--wait-seconds 0` when an immediate receipt is required. Recover lost stdout by replaying the exact original request body and key with the original authenticated principal and instance/project/worker binding, or read a known ID with `reviews run-read --selection-id ID`; MCP exposes `review_start` and `review_selection_read`. These reads follow the original child and never submit replacement work. Local `run-read --help` requires no connection or credentials.

Selection and child waits share one caller-selected deadline and the existing finite subscription capacity. Every read reauthorizes. Interrupted authenticated GETs reconnect only to the same selection with a shrinking wait budget. A durable POST interrupted by daemon observer shutdown can return its original receipt only after fresh authorization; actual lost POST outcomes remain uncertain and are never automatically replayed. Cancellation detaches observation without canceling accepted work.

The independent `review_selection:1` backup domain preserves original historical bindings. Inactive restore disables credentials and holds providers. Explicit provider resumption atomically abandons queued/selecting selections as `restore_abandoned`; selected child identity survives ordinary reconciliation, and abandoned records cannot create work after restart. Parent review-execution and retained-history schema versions remain unchanged. Stored front APIs/browser presentation, Delivery enrollment, notification following and external settlement controls remain separate work.
