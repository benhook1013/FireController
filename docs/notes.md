## Scope and state

A note is private project coordination data. It records a `reminder` or `source` body for later use. At least one of `worker_id`, `job_id` or `phase` is nonempty. Worker and job IDs select existing objects in the same project; a note naming both does not require that job to be assigned to that worker. Assignment is not note ownership. Phase is an exact freeform label, not a scheduler state or authorization grant. Job reassignment does not edit notes.

Current state contains `id`, `project_id`, `worker_id`, `job_id`, `phase`, `kind`, `body`, `status`, `status_reason`, `revision`, `created_at` and `updated_at`. Empty worker/job IDs mean no such selector. Creation starts at revision one with `status:"pending"` and empty reason. Status is `pending`, `consumed` or `dismissed`; dismissing requires a nonblank reason. Pending and consumed states require an empty reason. Earlier bodies, scope, status and reasons remain available in immutable revisions. A note never changes a job brief, assignment, status, focus, pause, checkpoint, message or review policy.

Bodies are nonblank UTF-8 text of at most 16 KiB. Reasons are at most 1024 bytes; phase labels are at most 200 bytes. Bodies and reasons allow newline and tab but no other control characters. Phase labels allow no control characters and must be nonblank when nonempty. Preserve valid submitted text rather than trimming it. Kind and status use only the exact enumerated values. IDs use the existing native identifier rules.

## Guarded API

Routes are relative to `/api/v1/projects/{project_id}`. Ordinary project permissions govern reads and writes; the authenticated worker header provides attribution, independent of the note's target worker. There is no worker-exclusive permission or cross-project lookup.

| Endpoint | Contract |
| --- | --- |
| `POST /notes` | Required `worker_id`, `job_id`, `phase`, `kind`, `body`. Returns HTTP 201 `{id, revision, outcome:"created"}`. |
| `GET /notes/{note_id}` | Full current state. No seen/consumed transition. |
| `PATCH /notes/{note_id}` | Required `expected_revision`, plus at least one of `worker_id`, `job_id`, `phase`, `kind`, `body`, `status`, `status_reason`. Returns HTTP 200 `{id, revision, outcome}`. |
| `GET /notes` | One compact filtered page. |
| `GET /notes/{note_id}/history` | One compact newest-revision-first page with actor attribution. |
| `GET /notes/{note_id}/history/{revision}` | One full immutable historical state with flat current-state fields plus `actor_id`, `actor_worker_id` and `recorded_at`. |

All POST fields are explicit strings; empty scope strings are valid only when another selector exists. Patch fields omitted from a request are preserved. Null, unknown and duplicate fields are refused. An explicit transition to pending or consumed clears a previous dismissal reason unless a reason was explicitly supplied, which must be empty. An explicit dismissed status requires a nonblank reason in that request. Body-only corrections to an already dismissed note preserve its reason. A patch cannot remove the last scope selector. These rules avoid resubmitting large unchanged bodies merely to consume or reopen a note.

Mutations require the existing idempotency key and transaction boundary. Patch guards range from one through `MaxInt64-1`. Stale writes return HTTP 409 `note_revision_conflict` with `details.current_revision`; a missing note returns `note_not_found`. Invalid worker/job targets use the existing missing-target codes. Guard validation precedes no-op detection. A changed patch advances the note revision and atomically records current state, a complete immutable revision, one compact event and its receipt. A no-op returns `outcome:"unchanged"` without another revision, timestamp or event. Exact-key replay returns its original receipt under current authorization, including after later revisions or restart. Changed arguments under the same key conflict. Storage failures roll back every part of the mutation.

Creation also records its first full revision. Compact `note.created` and `note.updated` events identify only the note and revision; they contain no body, phase or dismissal reason. Reads and pagination perform no provider work, durable writes, automatic message acknowledgments or note consumption.

## Selection and output

Lists default to pending notes and accept exact `worker_id`, `job_id`, `phase`, `kind` and `status` filters; `status=all` explicitly includes every status. Omitted scope filters select the project's notes, while supplied filters combine with AND. A supplied empty filter is invalid; omit it to leave that dimension unrestricted. Valid but nonexistent worker/job filter IDs yield an empty page rather than a target-existence error. An explicit `include_assigned_jobs=true` requires a nonempty worker filter and broadens just that worker predicate to notes naming the worker OR notes whose job is currently assigned to it. Other filters still combine with AND. This is a scoped SQL selection, not a request for job briefs or archives.

Current lists sort by immutable `created_at` and ID, descending. Note writers use nine fractional UTC digits so lexical timestamp sorting preserves timestamp order. Timestamps describe recorded wall time, while revisions define mutation order; clock rollback neither clamps stored times nor invalidates a record. History sorts by descending revision. Both return `{items, cursor?, has_more}`, default 20 and maximum 100, and never paginate automatically. Cursors bind instance, principal, project, route, selected note and effective filters. Cross-filter and cross-resource cursors fail. Pages observe current data rather than promising a transaction spanning multiple requests.

Compact items contain note identity, revision, scope, kind, status, creation/update times, a `body_preview` of at most 240 UTF-8 bytes and `body_truncated`. History items additionally include actor IDs and recorded time. They omit full body and reason. Full current and individual revision reads retain exact text; previews never replace authoritative content. No ordinary job read implicitly expands its note archive.

## Agent interfaces

The typed client exposes create, patch, current read, filtered list, compact history and individual revision read. Validation of supplied arguments happens before credentials or network access; the normal five-second total client budget and original-key recovery rules apply. Full current/revision responses allow a 128 KiB encoded budget for escaped body/reason text; compact pages have a 512 KiB encoded budget so a requested 100-item page can contain valid escaped phase labels and previews. The default remains 20 items. Invalid UTF-8, malformed state, wrong target/project, mismatched previews and impossible revisions are invalid responses rather than successful partial objects.

CLI commands are `notes add`, `notes update NOTE_ID`, `notes read NOTE_ID`, `notes list`, `notes history NOTE_ID` and `notes revision NOTE_ID REVISION`. Add defaults to the bound profile's worker and `kind:reminder`, with optional job and phase. `--clear-worker` explicitly creates a job-only or phase-only note. List defaults to that worker plus its currently assigned jobs; an explicit `--worker ID` selects that worker in the bound project; `--all-workers` explicitly selects project scope, and `--direct-only` suppresses assignment expansion. Project scope cannot be combined with a worker selector or direct-only selection. Explicit job/phase/kind/status filters narrow the selected scope. Updates send only supplied fields and require `--expect-revision` and `--key`; explicit clear flags remove worker, job or phase selectors. Bodies accept literal text or a private UTF-8 body file, never both. File input enforces owner-only POSIX mode where supported; Windows uses its native access model rather than treating synthetic POSIX bits as an access-control check. Regular-file, symlink, UTF-8 and 16 KiB bounds apply on both platforms. A status change needs no unchanged body echo.

MCP tools are `note_create`, `note_update`, `note_read`, `note_list`, `note_history` and `note_revision_read`, with equivalent defaults and explicit keys/guards. Creation's optional `worker_id` defaults to the bound worker; an explicit empty string clears that selector. List's optional nonempty `worker_id`, `all_workers` and `direct_only` mirror the CLI without changing the profile's authenticated actor. Updates preserve omitted fields and allow explicit empty scope strings. No tool silently consumes a note or interprets note text as authority. Compact list truncation is explicit; one selected full read supplies its complete content.

## Proof boundary

Backup inspection and inactive restore preserve current notes and every revision and reject malformed schemas before writes. Actual CLI and official-SDK MCP calls exercise the API before provider review, including lost committed responses and large escaped text. Browser presentation and combined resume context have separate executed proof under [browser coordination](browser-coordination.md) and [job resume context](job-context.md); host wakeup is outside this notes checkpoint.
