## Scope and state

A note is private project coordination data. It records a `reminder` or `source` body for later use. New notes must name at least one existing worker or job in the project. Phase is an optional label, never a sufficient attachment. Retained phase-only records and their immutable revisions remain readable and can be consumed or dismissed; they are never silently assigned to an inferred target. Any explicit scope change must leave a worker or job attachment. Worker and job IDs select existing objects in the same project; a note naming both does not require that job to be assigned to that worker. Assignment is not note ownership. Phase is an exact freeform label, not a scheduler state or authorization grant. Job reassignment does not edit notes.

Current state contains `id`, `project_id`, `worker_id`, `job_id`, `phase`, `kind`, `body`, `status`, `status_reason`, `revision`, `created_at` and `updated_at`. Empty worker/job IDs mean no such selector. Creation starts at revision one with `status:"pending"` and empty reason. Status is `pending`, `consumed` or `dismissed`; dismissing requires a nonblank reason. Pending and consumed states require an empty reason. Earlier bodies, scope, status and reasons remain available in immutable revisions. A note never changes a job brief, current progress, assignment, status, focus, pause, message or review policy.

Bodies are nonblank UTF-8 text of at most 16384 decoded UTF-8 bytes (16 KiB). Character counts and the JSON-encoded size are different measurements; multibyte characters can reach this bound before 16384 characters. Reasons are at most 1024 bytes; phase labels are at most 200 bytes. Bodies and reasons allow newline and tab but no other control characters. Phase labels allow no control characters and must be nonblank when nonempty. Preserve valid submitted text rather than trimming it. Kind and status use only the exact enumerated values. IDs use the existing native identifier rules.

## Guarded API

Routes are relative to `/api/v1/projects/{project_id}`. Ordinary project permissions govern reads and writes; the authenticated worker header provides attribution, independent of the note's target worker. There is no worker-exclusive permission or cross-project lookup.

| Endpoint | Contract |
| --- | --- |
| `POST /notes` | Required `worker_id`, `job_id`, `phase`, `kind`, `body`. Returns HTTP 201 `{id, revision, outcome:"created"}`. |
| `GET /notes/{note_id}` | Full current state. No seen/consumed transition. |
| `PATCH /notes/{note_id}` | Required `expected_revision`, plus at least one of `worker_id`, `job_id`, `phase`, `kind`, `body`, `status`, `status_reason`. Returns HTTP 200 `{id, revision, outcome}`. |
| `GET /notes` | One compact filtered page. |
| `GET /notes/{note_id}/history` | One compact newest-revision-first page with actor attribution. |
| `GET /notes/{note_id}/history/{revision}` | One full immutable historical state with flat current-state fields plus `actor_id`, `actor_worker_id` and `recorded_at`. |

All POST fields are explicit strings; an empty worker or job selector is valid only when the other attachment exists. Patch fields omitted from a request are preserved. Null, unknown and duplicate fields are refused. An explicit transition to pending or consumed clears a previous dismissal reason unless a reason was explicitly supplied, which must be empty. An explicit dismissed status requires a nonblank reason in that request. Body-only corrections to an already dismissed note preserve its reason. An explicit scope change cannot remove the last worker or job attachment. Body/status-only cleanup of a retained phase-only note remains possible. Exact-key replay preserves original successful receipts from before this admission rule. These rules avoid resubmitting large unchanged bodies merely to consume or reopen a note.

Mutations require the existing idempotency key and transaction boundary. Patch guards range from one through `MaxInt64-1`. Stale writes return HTTP 409 `note_revision_conflict` with `details.current_revision`; a missing note returns `note_not_found`. Invalid worker/job targets use the existing missing-target codes. Guard validation precedes no-op detection. A changed patch advances the note revision and atomically records current state, a complete immutable revision, one compact event and its receipt. A no-op returns `outcome:"unchanged"` without another revision, timestamp or event. Exact-key replay returns its original receipt under current authorization, including after later revisions or restart. Changed arguments under the same key conflict. Storage failures roll back every part of the mutation.

Creation also records its first full revision. Compact `note.created` and `note.updated` events identify only the note and revision; they contain no body, phase or dismissal reason. Reads and pagination perform no provider work, durable writes, automatic message acknowledgments or note consumption.

## Selection and output

Lists default to pending notes and accept `worker_id`, `job_id`, `phase`, `kind` and `status` filters; `status=all` explicitly includes every status. An explicit `job_id` selects all notes attached to that exact job, independent of creator, note worker target or current job assignment. Worker and assignment-expansion selectors do not constrain an exact-job selection. Phase, kind and status still combine with AND. Without a job selector, omitted scope filters select the project's notes, and an explicit `include_assigned_jobs=true` requires a nonempty worker filter and broadens just that worker predicate to notes naming the worker OR notes whose job is currently assigned to it. A supplied empty or malformed filter remains invalid even when it would not constrain an exact-job selection. Valid but nonexistent job selectors yield an empty page; nonexistent workers do the same for worker discovery. This is a scoped SQL selection, not a request for job briefs or archives.

Exact-job lists use the same effective selection and signed cursor as the pending-note page in a default job read. Continue that page with CLI `notes list --job JOB_ID --cursor CURSOR` or MCP `note_list` with `job_id` and `cursor`; no worker-scope override is required. Worker selectors do not change an exact-job cursor's scope, while changing the job, phase, kind or effective status does. Project and principal authorization remain required on every page.

Current lists sort by immutable `created_at` and ID, descending. Note writers use nine fractional UTC digits so lexical timestamp sorting preserves timestamp order. Timestamps describe recorded wall time, while revisions define mutation order; clock rollback neither clamps stored times nor invalidates a record. History sorts by descending revision. Both return `{items, cursor?, has_more}`, default 20 and maximum 100, and never paginate automatically. Cursors bind instance, principal, project, route, selected note and effective filters. Cross-filter and cross-resource cursors fail. Pages observe current data rather than promising a transaction spanning multiple requests.

Compact items contain note identity, revision, scope, kind, status, creation/update times, a `body_preview` of at most 240 UTF-8 bytes and `body_truncated`. History items additionally include actor IDs and recorded time. They omit full body and reason. Full current and individual revision reads retain exact text; previews never replace authoritative content. No ordinary job read implicitly expands its note archive.

## Agent interfaces

`notes list --help` (or `help notes list`) explains pending-note scope, filters, selected full reads and pagination locally, without loading profiles or contacting the service. Invalid list arguments point to this help.

The typed client exposes create, patch, current read, filtered list, compact history and individual revision read. Validation of supplied arguments happens before credentials or network access; the normal five-second total client budget and original-key recovery rules apply. Full current/revision responses allow a 128 KiB encoded budget for escaped body/reason text; compact pages have a 512 KiB encoded budget so a requested 100-item page can contain valid escaped phase labels and previews. The default remains 20 items. Invalid UTF-8, malformed state, wrong target/project, mismatched previews and impossible revisions are invalid responses rather than successful partial objects.

CLI commands are `notes add`, `notes update NOTE_ID`, `notes read NOTE_ID`, `notes list`, `notes history NOTE_ID` and `notes revision NOTE_ID REVISION`. Add defaults to the bound profile's worker and `kind:reminder`, with optional job and phase. `--clear-worker` requires an explicit job attachment. A phase label alone does not admit a new note. List with `--job JOB_ID` selects all notes for that exact job. Without a job selector, list defaults to that worker plus its currently assigned jobs; an explicit `--worker ID` selects that worker in the bound project; `--all-workers` explicitly selects project scope, and `--direct-only` suppresses assignment expansion. Project scope cannot be combined with a worker selector or direct-only selection. Phase/kind/status filters narrow either selection. Updates send only supplied fields and require `--expect-revision` and `--key`; explicit clear flags remove worker, job or phase selectors. Bodies accept literal text or a private UTF-8 body file, never both. File input enforces owner-only POSIX mode where supported; Windows uses its native access model rather than treating synthetic POSIX bits as an access-control check. Regular-file, symlink, UTF-8 and 16 KiB bounds apply on both platforms. A status change needs no unchanged body echo.

MCP tools are `note_create`, `note_update`, `note_read`, `note_list`, `note_history` and `note_revision_read`, with equivalent defaults and explicit keys/guards. Creation's optional `worker_id` defaults to the bound worker; an explicit empty string clears that selector. List's `job_id` selects all notes attached to that job; its optional nonempty `worker_id`, `all_workers` and `direct_only` otherwise mirror CLI worker discovery without changing the profile's authenticated actor. Updates preserve omitted fields and allow explicit empty scope strings. MCP arguments have a separate 131072-byte (128 KiB) encoded JSON limit, including field names, escaping and whitespace. Local validation names a body-byte violation separately from an encoded-payload violation without echoing note text; no request was sent. Omit an unchanged body when patching another field. No tool silently consumes a note or interprets note text as authority. Compact list truncation is explicit; one selected full read supplies its complete content.
