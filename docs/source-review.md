# Source-Pass Adjudication

## Method and limits

The initial extraction used two bounded domain inventories. Two additional fresh-context passes independently inspected actual implementation paths and focused test bodies across coordination, review execution/evidence, persistence, and the separate website. The main worker then read disputed source paths and reconciled the design. This is three source-touching review perspectives, not three executions of the legacy suite.

The public source census contains 33 Python modules and 30 test files with 1,601 AST-named test functions at commit `28263335caa23ef0706a8dc79add7eec4d0fcc53`. Hashes and counts were independently verified. Counting a function does not prove its assertions, execution, or relevance. The passes inspected representative scenarios, not every test or source line. Private JSON, live databases, generated pages, and provider state were excluded from extraction.

## Goals supported by the evidence

| High-level goal | Source-backed outcome to retain | Technique that is not a requirement |
| --- | --- | --- |
| Reliable work context | Guarded current briefs, retained checkpoints/history, explicit pauses, visible blockers, one optional resume focus with multiple active jobs | Legacy schema, flag spelling, card layout, status ordering, or filesystem brief authority |
| Trustworthy communication | Durable messages, deterministic conversations, separate seen and handled state, read-only lists and thread views | Global aliases, unrestricted thread reads, model polling, or implied host wakeups |
| Safe project maps and setup | Scoped map edits, source provenance, preview/apply conflicts, idempotent imports, preserved newer work | JSON as an ongoing mutable-state writer or AI summaries treated as historical proof |
| Accurate review execution | Exact target/parent identity, complete evidence, duplicate prevention, retained uncertain posts, explicit finding decisions/fix proof | Per-command whole-queue investigations, arbitrary inherited round numbers, or a giant combined controller object |
| Durable operation | Consistent backup/restore, explicit version compatibility, recovery without data loss or duplicate external actions | Old JSON/SQLite bridges, fixed schema versions, SFTP scripts, or copied repair machinery |
| Low-friction AI use | Compact receipts, deliberate context reads, no provider work for everyday coordination, quiet host-supported completion | Repeated inbox metadata, full archives after writes, mandatory receipt/poll loops, or human-first formatting |
| Live project presentation | Explicit public allowlist, safe rendering, per-project settings and current data | Static private refresh/render/publish cycles or fixed FireMUD theme and labels |

## Adjudicated discrepancies

1. **Primary work:** Both passes found contradictory wording between the inheritance matrix and acceptance. Retain one optional primary as a resume focus because it makes authoritative context selection predictable. It does not restrict the worker to one active job. Preserve this functional outcome, not a unique-index implementation or browser-card order.
2. **Acknowledgment:** The main worker read `InboxStore._mark`: the existing explicit acknowledgment establishes seen and acknowledged atomically. The target preserves that one-action behavior rather than requiring a separate read call. Transport receipt still does not acknowledge anything.
3. **Disk JSON and website side effects:** The main worker verified `_lane_job_plan` and `_site_manifest` consume retained lane/task/next-step/blocker/brief-provenance data. Current site documentation assigns runtime/editorial roles to status/progress files, but historical inputs can contain application state. The main worker also verified the refresh path invokes `sync_hosted_reviews`. The target deliberately separates browsing from provider work and requires an actual migration inventory before cutover.
4. **Map editing:** Add W05 for ordinary scoped map/phase/return-point edits, stale-revision conflicts, retained history, and another project's unchanged state. Import proof alone does not establish daily map usability.
5. **Policy complexity:** Keep exact attribution, finding obligations, duplicate suppression, stops, provider constraints, and recoverability in the native engine. Preserve advanced taper, allocations, and review periods in the inventory as optional later policy capabilities. This avoids losing the source behavior while preventing it from blocking the first reliable engine.
6. **Numerical assumptions:** Page-size and concurrency/latency numbers are calibration candidates, not inherited rules or release gates. Provider ceilings remain observed/configured facts; this project's planning around a discussed 100-file review ceiling is not a product-wide cap.
7. **Asynchronous experience:** Durable operation IDs are service recovery mechanisms. A capable adapter delivers a final async result without requiring the model to track IDs or poll. Host behavior and idle-chat wakeup remain separate proof boundaries. Do not mistake the legacy synchronous hosted waiter for an agent-facing async integration.
8. **Required CI and mergeability:** Pass A found that vague required-CI wording omitted the source's authority and app-identity checks. The main worker inspected `fetch_required_status_checks`, `_required_authority`, and `_required_results`: provider rules and exact applicable results must agree. Add R13 and R14, separate review completion from merge readiness, and hold unknown mergeability without copying the legacy Git fallback implementation.
9. **Final acceptance gaps:** Pass B's final reread identified private-by-default onboarding imports and the platform footer as untested outcomes. Add P05 and W06, and qualify R08/R09 so deferred advanced policy is not a hidden first-engine prerequisite.

## Remaining review boundaries

The design PR is the next defect and human decision review, not a statement that every inherited feature is implemented. Historical repair/import internals and compatibility branches are consciously deferred; native recovery outcomes are retained in [acceptance](acceptance.md). The private website's actual selected JSON contents, full runtime-file inventory, deployment selectors, content rights, and live migration remain later work.

Each implementation slice must trace its public behavior to the selected goal and relevant scenario, then provide fresh proof. No source-test count, independent-agent agreement, or CodeRabbit result replaces those tests. An omitted behavior must be classified explicitly rather than silently lost during rewriting.
