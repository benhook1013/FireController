# Remote MCP

## Status and owner

This document owns the Streamable HTTP and worker-bound credential contract. The daemon implements the opt-in transport and native credential provisioning alongside the [local stdio adapter](mcp.md). Installed hosting and Claude.ai connector discovery and safe read require separate qualification.

## Resource and connector

Mount `/mcp` on the existing FireController daemon and publish it on the installation's canonical HTTPS origin. Keep the daemon loopback-only behind the existing proxy. Enable the route explicitly and keep it disabled on installations that have not selected it. On the hosted installation the connector URL is `https://controller.firedevops.net/mcp`.

Use a dedicated worker-bound bearer credential in the standard `Authorization` header. A custom connector that offers Request headers selects No sign-in for OAuth and adds a required `Authorization` value of `Bearer <connector token>`. FireController authenticates each request. A connector can have one project binding or an explicitly granted set of projects, with one acting worker in each. Use the same connector URL in both cases. Share a connector only with people intended to exercise its grants. Verify fixed header availability and connector enrollment on the intended account. [Claude custom connector documentation](https://claude.com/docs/connectors/custom/add-unlisted#authenticate-with-request-headers).

If the target account lacks fixed request headers, report that compatibility dependency on the implementation job. A generic remote HTTP client can still qualify transport, but Claude.ai acceptance requires a working connector in the target account. The OAuth path, if required for that account, uses an operator-selected authorization server, MCP protected resource discovery, and an operator-controlled mapping from issuer and subject to the same FireController project, worker, and grant boundary. FireController validates resource audience and current authorization on each call. Identity claims from a caller do not create a worker binding. Resolve issuer and account availability before implementing that extension. [MCP authorization specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization).

### Operator setup

1. Generate a fresh, high-entropy secret in a private credential file. Use the same owner-private file handling as the [native client setup](onboarding.md#private-agent-setup-commands).
2. For one project, use its manager binding to register the credential with `fc credentials grant --credential-file /private/connector.token --connector-worker WORKER_ID --permission read --key KEY`. Select `write` or `manage` only when needed. For multiple projects, use the native instance administrator to call `POST /api/v1/operator/connector-credentials` with an idempotency key, the lowercase `token_sha256`, and a `projects` array. Each entry contains an opaque `project_id`, the active `worker_id` in that project, and `permissions` of `["read"]` or `["read","write"]`. Supply two to sixteen distinct projects. One transaction issues the credential and all its bindings, with a scoped audit event for each project. The receipt lists the credential and applied bindings.
3. Stage and verify the [opt-in proxy route](hosting.md#remote-mcp-route) while the daemon route is disabled. Then enable remote MCP through the guarded rollout for the canonical HTTPS origin. Share the token privately with the intended connector owner.
4. Create a custom connector pointing to the canonical HTTPS URL ending in `/mcp`. On an account with Request headers, select No sign-in, add a required `Authorization` header, and supply `Bearer <connector token>`. For multiple bindings, use one connector entry and discover its projects with `connector_projects`.

Rotate by creating a fresh dedicated credential for the desired grants and replacing the connector's private credential. Revoke the prior grant for each selected project by its receipt ID using `fc credentials revoke CREDENTIAL_ID --key KEY` from that project's manager binding. Use `fc credentials update --help` for guarded project permission changes under the same binding. Withdrawing one grant preserves the others. A multi-project connector still requires an explicit project when only one grant remains active.

## Worker-bound credentials

Each binding associates one non-admin credential with a grant and a nonretired worker in the same project. Bindings are immutable. Existing project grants, one-project connectors, and direct API tokens retain their behavior. Mint connector credentials separately so rotation or revocation can target one connection. Retain the ordinary credential digest and binding metadata. Use the existing guarded grant update and revoke operations. A project manager can delegate only the authority the native grant rules allow.

Resolve the bearer and active bindings on every `/mcp` request, including initialization and discovery. One-project connectors retain the original tool arguments. A multi-project connector exposes one extra read-only tool, `connector_projects`, and its other tools require a `project` argument on every call. Use a canonical handle or opaque project ID from that credential's active bindings. The server derives the principal and selected project's acting worker from the credential. There is no shared project selection. Reject missing or ungranted selectors before the tool runs, and reject client-supplied FireController identity headers on this route. Existing resource selectors retain their authorization semantics. Reject missing, invalid, revoked, or unbound credentials before MCP dispatch. Browser sessions and instance-administrator credentials are unavailable on this surface.

Enforce the same immutable binding when a connector bearer reaches the native API directly. A project route must resolve to the bound project and its acting worker must equal the bound worker. Check both in the common scope and transaction authorization path, including authenticated reads, guarded mutations, streams, and credential use by automation. Require an active grant and a nonretired worker. Refuse browser-session issuance for connector credentials so a cookie cannot drop the worker binding. Non-project instance identification remains a read without an acting worker. Return an HTTP authentication challenge for missing or unusable credentials and reject authenticated scope or authorization denials without disclosing foreign resource identities. This prevents REST replay of a connector token as another worker.

## Transport and execution

Reuse the [stdio tool catalog and adapter](mcp.md) for schemas, handlers, annotations, output shaping, cancellation, and typed-client requests. Supply a request-scoped binding and credential source in memory. The typed client calls the existing native handlers through a fixed internal transport to the same daemon. Use the normal service authentication and authorization paths and obtain the internal destination from trusted server configuration. Avoid per-worker subprocesses, persistent copies of raw bearer strings, credential-bearing service URLs, and a second service storage layer. Keep current authorization checks authoritative at dispatch and commit.

Use the pinned [Go SDK Streamable HTTP handler](https://pkg.go.dev/github.com/modelcontextprotocol/go-sdk@v1.8.0/mcp#StreamableHTTPOptions) in stateless mode. Support initialization, paginated discovery, and tool invocation over `POST /mcp`. Stream replies over the originating POST where needed for bounded waits. Authenticated standalone GET and DELETE return 405 in this mode. There are no resumable MCP sessions or idle chat wakeups. Clients recover waits by replaying the existing cursor or reading the original operation. They recover uncertain writes with the original binding, arguments, and idempotency key. A dropped connection never proves rollback or cancels already accepted provider work. Keep supported protocol versions and host behavior in the compatibility record. [MCP transport specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

Validate the canonical Host at the trusted proxy and application boundary, and validate any supplied Origin against an explicit allowlist. Allow clients that omit Origin. Apply body limits consistent with documented tool envelopes and bounded concurrent request and wait admission before allocating expensive work. Set proxy response buffering and upstream timeouts for this route using the existing [hosting rules](hosting.md), and prove actual streaming against the installed proxy. Recheck authorization before delivering sensitive results from long waits and release waiter capacity on completion or cancellation. Keep secrets, headers, private tool inputs and payloads out of logs, traces, metrics, URLs, and error responses. The standard job, review, and pause controls continue to govern tool work.

### Local transport limits

The endpoint admits 32 concurrent HTTP requests and eight concurrent tool calls with extended wait budgets. Each POST accepts one JSON-RPC object up to 2 MiB plus 16 KiB. The application accepts its canonical Origin and additional exact HTTPS origins configured by repeated `--remote-mcp-allowed-origin` flags. Clients that omit Origin remain eligible. The pinned SDK advertises 2026-07-28, 2025-11-25, 2025-06-18, and 2025-03-26; discovery and tool execution are qualified locally with 2026-07-28 and 2025-11-25.

Base schema v5 upgrades the one-project bindings introduced in v4 to support multiple project bindings per credential. Startup preserves existing bindings and credentials. Earlier binaries refuse new schema versions. Backup inspection accepts supported predecessors. Inactive restore retains binding metadata and revokes copied credentials, including connector credentials. An activated restore requires newly provisioned connectors.
