# Remote MCP

## Status and owner

This is the target contract for serving FireController tools over Streamable HTTP. The [local stdio adapter](mcp.md) is implemented. Remote transport, bound credentials, installed hosting, and Claude.ai acceptance have separate implementation and proof milestones.

## Resource and connector

Mount `/mcp` on the existing FireController daemon and publish it on the installation's canonical HTTPS origin. Keep the daemon loopback-only behind the existing proxy. Enable the route explicitly and keep it disabled on installations that have not selected it. On the hosted installation the connector URL is `https://controller.firedevops.net/mcp`.

The first release uses a dedicated worker-bound bearer credential in the standard `Authorization` header. A custom connector that offers Request headers selects No sign-in for OAuth and adds a required `Authorization` value of `Bearer <connector token>`. The FireController server still authenticates every request. Register a separate connector entry for each project and worker binding. Share a connector only with people intended to exercise that worker's access. Anthropic limits availability of fixed request headers, and some plans limit the number of connectors. Verify the intended account's actual setup. [Claude custom connector documentation](https://claude.com/docs/connectors/custom/add-unlisted#authenticate-with-request-headers).

If the target account lacks fixed request headers, report that compatibility dependency on the implementation job. A generic remote HTTP client can still qualify transport, but Claude.ai acceptance requires a working connector in the target account. The OAuth path, if required for that account, uses an operator-selected authorization server, MCP protected resource discovery, and an operator-controlled mapping from issuer and subject to the same FireController project, worker, and grant boundary. FireController validates resource audience and current authorization on each call. Identity claims from a caller do not create a worker binding. Resolve issuer and account availability before implementing that extension. [MCP authorization specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization).

## Worker-bound credentials

Extend native project credential provisioning with an explicit connector worker selection. A project manager selects one existing nonretired worker in the same project, a supported permission set, a digest of a newly generated secret, and an idempotency key. In one transaction, register the native non-admin credential and grant and retain its immutable connector project and worker binding. Existing project grants and direct API tokens remain compatible. Mint connector credentials separately so rotation or revocation can target one connection. Retain only the ordinary credential digest and binding metadata. Use the existing guarded grant update and revoke operations. A project manager can delegate only the authority the native grant rules allow.

Resolve the binding from the bearer on every `/mcp` request, including initialization and discovery. Derive the instance, project, worker, and principal from server state. The bearer is the only caller-supplied identity input. Reject client-supplied FireController identity headers on this route. Tool arguments that select a job, recipient, or other resource keep their existing authorization semantics and never select the acting worker. Reject missing, invalid, revoked, or unbound credentials before MCP dispatch. Browser sessions and instance-administrator credentials are unavailable on this surface.

Enforce the same immutable binding when a connector bearer reaches the native API directly. A project route must resolve to the bound project and its acting worker must equal the bound worker. Check both in the common scope and transaction authorization path, including authenticated reads, guarded mutations, streams, and credential use by automation. Require an active grant and a nonretired worker. Refuse browser-session issuance for connector credentials so a cookie cannot drop the worker binding. Non-project instance identification remains a read without an acting worker. Return an HTTP authentication challenge for missing or unusable credentials and reject authenticated scope or authorization denials without disclosing foreign resource identities. This prevents REST replay of a connector token as another worker.

## Transport and execution

Reuse the [stdio tool catalog and adapter](mcp.md) for schemas, handlers, annotations, output shaping, cancellation, and typed-client requests. Supply a request-scoped binding and credential source in memory. The typed client calls the existing native handlers through a fixed internal transport to the same daemon. Use the normal service authentication and authorization paths and obtain the internal destination from trusted server configuration. Avoid per-worker subprocesses, persistent copies of raw bearer strings, credential-bearing service URLs, and a second service storage layer. Keep current authorization checks authoritative at dispatch and commit.

Use the pinned [Go SDK Streamable HTTP handler](https://pkg.go.dev/github.com/modelcontextprotocol/go-sdk@v1.8.0/mcp#StreamableHTTPOptions) in stateless mode. Support initialization, paginated discovery, and tool invocation over `POST /mcp`. Stream replies over the originating POST where needed for bounded waits. Authenticated standalone GET and DELETE return 405 in this mode. There are no resumable MCP sessions or idle chat wakeups. Clients recover waits by replaying the existing cursor or reading the original operation. They recover uncertain writes with the original binding, arguments, and idempotency key. A dropped connection never proves rollback or cancels already accepted provider work. Keep supported protocol versions and host behavior in the compatibility record. [MCP transport specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

Validate the canonical Host at the trusted proxy and application boundary, and validate any supplied Origin against an explicit allowlist. Allow clients that omit Origin. Apply body limits consistent with documented tool envelopes and bounded concurrent request and wait admission before allocating expensive work. Set proxy response buffering and upstream timeouts for this route using the existing [hosting rules](hosting.md), and prove actual streaming against the installed proxy. Recheck authorization before delivering sensitive results from long waits and release waiter capacity on completion or cancellation. Keep secrets, headers, private tool inputs and payloads out of logs, traces, metrics, URLs, and error responses. The standard job, review, and pause controls continue to govern tool work.

## Build, deployment, and completion proof

- Build on the current integration branch and use its standard validation. Exercise the pinned SDK over the actual HTTP stack and compare schemas and outcomes with stdio. Cover wrong Origin and Host, missing or duplicate bearer, revoked worker credential, a retired worker, cross-project and cross-worker replay on both transports, and a rejected write under read-only access. Verify revocation or grant changes between requests and while a sensitive wait is open. Exercise guarded write replay and loss of the original response without duplicate effects.
- Before enabling the public route, qualify the shipped daemon and proxy with an allowed read and a bounded wait. Use the existing [development release procedure](releases.md#fast-pre-v1-development). Verify the exact serving image or source revision, trusted TLS, and route behavior. Disable the route as the first rollback for a transport-only failure. Use the existing migration and recovery procedure if database state is involved.
- From a client outside the deployment host, paginate tool discovery and exercise one read and one guarded write on a designated test record. Read the result back, confirm worker attribution, replay the original key, and verify project isolation with a second binding. Preserve safe evidence with the deployed revision and protocol version. Use the actual Claude.ai custom connector to discover tools and perform a safe read in the intended account. A passing generic SDK run alone qualifies the generic client.
- Give Claude the exact URL, which project binding to select, how to obtain its credential privately, and the verified client setup. Record the remote and Claude.ai proof separately before completing the implementation job.
