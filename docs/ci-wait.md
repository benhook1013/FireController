# Waiting for CI

The service exposes `POST /api/v1/projects/{project_id}/reviews/ci/watch` for bounded, read-only CI observation. Client, CLI and MCP watch entrypoints are a separate implementation checkpoint and are not included in this service checkpoint. The API requires bearer-based project read access and a configured GitHub observation capability. A read-only browser session is insufficient: its project read grant does not permit this POST route; despite using POST for its bounded target list, it has no idempotency key or durable mutation. Targets do not need Delivery queue enrollment. A watch never requests reviews, spends review allowance, reruns CI or changes branches, jobs, notes or queue membership.

## Request and comparison

The body is `{"targets":[{"pull_number":42,"head_sha":"FULL_HEAD_SHA"}]}`. Supply one to twenty targets, each with its PR number and full expected head SHA. An optional full `base_sha` pins the comparison immediately; otherwise the subscription pins its first freshly observed base. A later observed head/base change returns `superseded`, never CI credit for different code. Fresh supersession is retained for that subscriber until delivery, even if a later refresh fails or observes the original source again. Once a subscription has fresh source-supersession proof, a newer CI-only refresh hint does not hold that result pending. Older cached observations cannot establish a new subscriber's comparison.

`Prefer: wait=N` selects 0–900 seconds, defaulting to 300. Positive waits start at handler entry: scoped authorization and body parsing consume the same selected duration. Zero does not await collection or use cached observations to settle a new subscription. A quiet expiry returns `timed_out:true` with the real target states; it does not create a durable operation. The final fresh authorization read retains its bounded response allowance. Caller cancellation and response-write deadlines remain authoritative. Return or cancellation releases the subscription.

The default gate comes from GitHub's repository default branch. For a stacked PR targeting an unprotected feature branch, it selects that final branch's required contexts while checking the PR's actual head/base or verified test merge. It does not claim testing against the final branch. The result identifies the distinct `gate_ref`; the ordinary stored [CI assessment](review-ci.md) still describes its selected PR base.

## Results and quiet rearming

By default, a call returns when any target passes, fails, closes, is superseded, or has a verified empty gate (`unconfigured`). Unknown requirements and missing results remain pending, never passing. A proven applicable required-check failure ends the watch even if another required check is missing; failure and unproven counts remain distinct. A changed or otherwise unproven comparison cannot establish failure. The exception is positively bound head CI under non-strict required-check authority: a proven merge-base mismatch can keep its merge state `unproven` while an independently proven failed required check still produces `failed`, even when another required check is missing. This grants no failure credit to other unproven comparisons. Results preserve observed source, gate, CI commit, counts and bounded check identities under the existing [CI proof rules](review-ci.md#current-workflow-identity). Outer `state` is a wake reason, not an assertion that every target passed. Passing CI does not authorize merging or imply review completion.

For passed and failed rearming, send exactly one `X-FC-CI-Watch: change-v3` header and copy a returned `observation_key` into that target's optional `after_observation_key`, preserving head/base pins. If the initial request omitted `base_sha`, send the returned `observed_base_sha` as `base_sha` on the next watch alongside the observation key; copying only the original target would allow the new subscription to pin a newer base. An identical fresh terminal result retains its target state, proof, time and key, adds `waiting_for_change:true`, and does not wake the call. Changed terminal proof or selected workflow attention wakes normally. Closure, source supersession and an unconfigured gate always wake. A CI-only hint does not erase fresh closure; a PR metadata hint can represent reopening and requires new source observation.

This is a bounded terminal wait, not a continuous readiness subscription. A newly pending check neither wakes the call nor preserves a passing target state. A pending-then-pass cycle with identical final relevant proof stays quiet; no transition history is retained. Relevant run/check/attempt changes alter observation keys, while observation timestamps and refresh generations do not. Return, timeout or cancellation ends the subscription; later metadata edits need fresh assessment.

`change-v1` and `change-v2` retain failure/attention-only baselines: an unchanged pass wakes them. `change-v2` and `change-v3` opt into exact optional `merge_base_mismatch` identities. Successful `change-v3` responses acknowledge that capability in the same header. Capability negotiation does not grant CI success or alter source pins.

## Selected workflow attention

Send exactly one recognized `X-FC-CI-Watch` header, such as `X-FC-CI-Watch: change-v3`, when selecting workflows; requests containing `failure_workflow_ids` without it are rejected. An optional `failure_workflow_ids` array selects one to sixteen unique positive workflow IDs per target. It adds early attention, not required-gate membership or dependency-graph assertions. A proven failed job supplies an eligible `attention` wake result; the target remains pending with its original gate counts/checks. In a batch, the first target in request order with an eligible wake result determines the outer `state`. A prior target may therefore produce outer `passed` even when a later target has workflow failures; inspect every target. Up to sixteen `workflow_failures` rows identify exact workflow, run, current numbered attempt, job and check-run IDs, name and conclusion. No job bodies or logs are fetched. Terminal gates, closure and supersession retain their normal results without extra attention.

A newer completed run explicitly skipping the same uniquely named job does not prove an earlier failure repaired. Earlier failure attention needs a complete same-workflow/event/commit chain of such skips and a final run-inventory recheck. Missing jobs, ambiguous duplicate names, pending or cancelled execution block that fallback. New substantive results supersede old results; a rerun uses only its current attempt. A successful final recheck validates every retained row, including direct failures. Failed rechecks discard fallback rows while retaining independently proven direct applicable-comparison evidence and the provider warning. Old success never supplies required-gate credit.

A stable, positively bound `ci_merge_base_mismatch` can expose selected same-head repair attention with `workflow_attention_basis: head_only_current_comparison_unproven`. The gate retains mismatch, zero counts, no selected CI commit and empty checks. These are real same-head failed jobs with unknown run base/merge comparison, not current-comparison failure or success credit. Other unproven comparisons and non-opted-in subscriptions perform no same-head collection.

Send exactly one `X-FC-CI-Workflow-Details: 3` header with `X-FC-CI-Watch: change-v3` to enable both same-head and labelled historical attention. Workflow-details version `2` allows proven same-head attention but no historical rows; version `1` retains applicable latest-run details without head-only failures or wakeups. A selected advanced-attention mode requires provider support at admission; an adapter cannot silently downgrade head-only or historical selectors to ordinary workflow observation. Unsupported modes are rejected before registering a watcher or consuming shared watch capacity. Projection occurs per subscriber before choosing attention and change keys. Newly capable subscribers require fresh proof even when their workflow IDs are already selected.

Historical rows use `basis: historical_same_head_failure_supersession_unproven`: a real earlier failed job on the pinned head whose latest-job coverage/supersession is not proven. They use only current numbered attempts already reached by the bounded skipped-job walk, without extra history requests or altered stopping conditions. Matrix templates do not imply identity with expanded jobs. A newer exact-name substantive result suppresses the candidate; duplicate names, malformed/missing attempts and unread history provide no association. A final same-head inventory recheck is mandatory and failed/moved rechecks discard history. This never proves the latest comparison failed or credits metadata-only success as repair.

Pending applicable targets may expose up to sixteen selected `workflow_observations` with `basis: latest_run_only`, using collected inventory without extra reads. These fields do not change wake behavior, observation keys or gate proof. Earlier-run failure attention omits the whole optional observations group to avoid conflicting run identities. Missing details and absent failure rows do not certify successful jobs, repaired earlier failures or full coverage.

Known attention also accepts `after_observation_key`: retain source pins and workflow selection. Identical attention stays quiet with its failure rows and `waiting_for_change:true`; changed proof wakes normally. Collection failures never upgrade or erase required-gate facts. Required and optional work share the forty-second provider budget and thirty-two-attempt bound. Selected workflows receive their latest-run attempt reads before older skipped-run history uses the remaining budget. Required attempts are reused; optional failures stop fanout and retain normal account backoff. This proof is local to an observation, with no new persisted schema or per-job polling.

## Scheduling and isolation

Overlapping watches share observation workers and provider-account limits, with at most sixteen selected workflow IDs per PR across subscribers. A new subscriber needs a collection started after registration without withholding another subscriber's fresh result. Departed subscribers leave no freshness demand. In-flight collection stops when remaining subscribers, CI hints and fallback demand no longer need it, without replacing completed facts.

Trusted GitHub hints use five-second event coalescing. Same-repository branch pushes received before the initial base ref is published retain refresh demand through completion; known base/gate refs subsequently restore narrow matching. SHA-only CI hints received during a collection are reconciled with its selected CI commit before publishing the verdict. This holds at most thirty-two distinct unmatched commit hints per active collection; overflow conservatively requires a refresh, and completion or cancellation releases those hints. This checkpoint does not register a signed webhook endpoint, so active watches also use the shared sixty-second fallback. These are scheduling intervals, not completion deadlines; provider time, capacity and account backoff still apply. No per-wait provider polling loop is started.

Subscriptions are bounded and process-local. Service restart ends the HTTP subscription, and a replacement observer cannot supply results to subscriptions owned by its stopped predecessor. A caller starting a replacement watch must retain explicit source pins; an implicit base from a lost server subscription cannot be recovered by silently creating another subscription. Local refusal reasons distinguish scope/binding reads, capacity, observer availability and cancellation without claiming provider, SQLite or deployment causes.
