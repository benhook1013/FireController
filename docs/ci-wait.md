# Waiting for CI

Use `reviews ci-wait` or MCP `wait_for_ci` to wait quietly for required CI on up to twenty PRs in the bound project. Every target supplies its PR number and full expected head SHA; an optional full base SHA pins the base immediately. Otherwise the watch pins the first freshly observed base. A later comparison change returns `superseded`, rather than crediting results for different code. Once this subscription has a fresh observed head/base mismatch, a newer CI refresh request does not keep that superseded comparison waiting; older cached observations cannot supply this decision.

```sh
fc reviews ci-wait --target 42:FULL_HEAD_SHA --target 43:FULL_HEAD_SHA:FULL_BASE_SHA --wait-seconds 300
```

The default gate comes from the repository's final merge branch, represented by GitHub's default branch. For a stacked PR targeting an unprotected feature branch, this selects the final branch's required contexts while checking the PR's actual head/base or verified test merge. It does not claim the PR was tested against the final branch. Optional preview and deploy workflows do not participate unless that gate requires them. The ordinary stored [CI assessment](review-ci.md) continues to describe its selected PR base; the watch reports its distinct `gate_ref` explicitly.

One call returns when any target passes, fails, closes or is superseded, or when a verified empty gate returns `unconfigured`. Missing results and unknown requirements remain pending with an explicit reason; neither becomes a pass. Results include actual observed comparison, gate, CI commit, counts and bounded required-check details. Current workflow, attempt and check identities follow the existing [CI proof rules](review-ci.md#current-workflow-identity). The outer `state` identifies the wake condition and can be `passed` while other targets remain pending. CLI/MCP add `all_targets_passed`, which is true only for a nonempty batch where every target passed; inspect `targets` for individual outcomes. Passing CI does not authorize merging or imply review completion.

CLI and MCP pending targets add a plain diagnostic and `phase`: `not_observed` means the controller has not finished a fresh observation for this watch; `refreshing` means newer facts are requested and older counts are informational; `checks_pending` and `checks_unproven` describe collected GitHub check facts. `observation_unproven` covers a collection whose CI result could not be established. Zero counts before observation do not establish an empty gate. The original `observed_at` dates collected facts when present. A returned response ends this call's subscriptions, so it does not promise a next scheduled check or completion ETA. Known test-merge refusals reuse the existing CI comparison recovery guidance; requested and observed PR base SHAs are not relabeled as the stale merge parent or live branch tip. The raw API facts and wait behavior are unchanged.

Pass only the remaining targets into a subsequent wait. Waits default to 300 seconds and support 0–900 seconds. Zero returns the currently available result immediately. A quiet expiry returns `timed_out:true` and the real pending states; it does not create a durable operation to poll. Cancellation or return releases this call's temporary subscriptions. Configure a capable MCP host using the [long-wait guidance](agent-client.md#quiet-asynchronous-waiting); a service wait does not itself promise idle-chat wakeup.

When the service explicitly identifies shutdown as the reason a temporary wait ended, CLI and MCP retain that safe reason and explain reattachment using the same pins. The interruption does not establish failed GitHub CI. Generic overloads remain unclassified rather than being described as a known restart. The service can absorb refused local read admission within the original [result-wait budget](agent-client.md#quiet-asynchronous-waiting); the client does not resubmit the call or request a review.

The API is `POST /api/v1/projects/{project_id}/reviews/ci/watch` with body `{"targets":[{"pull_number":42,"head_sha":"FULL_HEAD_SHA"}]}` and optional `Prefer: wait=N`. Despite using POST for the bounded target list, this requires project read access and has no idempotency key or durable mutation. PRs need not be enrolled in the Delivery queue. The project must have a configured GitHub observation capability. A watch never requests reviews, spends review allowance, reruns CI or changes branches, jobs, notes or queue membership.

Overlapping watches share the existing observation workers and provider-account limits. Signed [GitHub webhooks](github-observation.md) prompt observation, with five-second event coalescing; an active-only sixty-second fallback recovers missed events. These are scheduling intervals, not completion deadlines: provider time, account backoff and worker capacity still apply. No per-wait provider polling loop is started. Subscriptions are process-local and bounded; a service restart ends the call, and a new read can watch the same pins.
