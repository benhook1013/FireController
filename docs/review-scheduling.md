# Review scheduling

Projects can independently opt in to automatic new Hosted or CLI requests. Both default to off. Explicit CLI requests continue to work without enabling automatic selection; a proven quota refusal retains any accepted request through [durable CLI waiting](review-execution.md#durable-cli-quota-waiting), without replacing that operation. Automatic GitHub observation and automatic retry of an already authorized timer-backed request are independent of this setting; see [observation](github-observation.md) and [timer-backed waiting](review-execution.md#timer-backed-hosted-waiting).

## Automatic Hosted requests

A project manager enables scheduling through the queue's **Automatic Hosted** control, CLI or MCP. Enabling binds authorization to that manager's exact credential and an active project worker. A browser manager explicitly selects the authorizing worker while retaining the human session identity. The controller rechecks that authorization before selection and dispatch. New selections use the current configured authorizer. An already selected automatic operation retains its original principal, worker and credential when a later manager changes settings. Any later scheduling revision requires complete durable history proving that the intent's own channel stayed enabled in every intervening revision, including when the authorizer is unchanged. Missing history or any disable/re-enable blocks continuation. An unchanged authorizer can finish a queued or selecting intent across a continuously enabled history, including unrelated-channel changes. Across an authorizer change, only an already selected operation can continue, and both authorizers must remain valid. This preserves the existing operation and any quota timer rather than creating a replacement. A blocked queued operation reports `automation_authorization_changed` as a current diagnostic for manager investigation. Revoked credentials, lost management access, retired workers and restored-provider holds cannot authorize new work.

The scheduler uses the configured queue membership and the same derived open order as [Delivery and Reviews](review-workspace.md). New selections take that order into account while existing operations retain their original queue bindings. At the scheduling ceiling, a normal add can make room using a verified merged entry outside pending operation and refresh prefixes, keeping its Delivery history and review records. It checks eligible work at most once per five-second coordinator interval; this is not a promised start time or another GitHub polling loop. Source, publication, the selected PR’s own findings, routes and imported obligations, round limits, taper and provider guards still apply. Either channel can review a stacked child while ancestors await findings, fixes or further rounds, using the full freshly verified enrolled named-parent source chain. Ancestor obligations remain unresolved and keep their normal readiness requirements. Retained scheduling, channel-front and source-retry selection validation failures, a retained parent cycle, or a planning basis above its row limit prevent planning only for the affected project and channel. The same isolation applies when queued selection workers claim, choose, or finish a target: a validated project-local refusal retains a held selection, rolls back partial source and child writes, and preserves its accepted automatic basis. Explicit selections keep local-read attribution. Independent projects and the other channel continue. Shared storage and transaction failures remain errors rather than being suppressed; arbitrary SQL failures are not classified as project-local corruption. Automatic selection authorization rejects a malformed or nonpositive retained scheduling revision as `storage_unavailable`; its typed local refusal does not turn actual query failures into corruption. Automatic requests never inherit out-of-order or file-limit overrides. Each project first plans in a bounded read-only snapshot. Only a candidate for a new intent or due source recovery enters the writer, which repeats authorization, configuration, policy, pause, busy and basis checks before ordinary atomic acceptance or retry. A changed plan waits for a later pass.

Meaningful source, review or control changes can create another automatic intent. A waiting later PR does not prevent reconsideration of an earlier PR that becomes eligible; the earlier request can take priority while the later request retains its identity and cooldown. Existing queued work on a PR prevents a duplicate intent for that PR, and active provider work is not interrupted. Timer-backed requests retain their original operation and retry deadline. Ticks, restarts, observation timestamps and failed/cancelled operation transitions cannot recreate the same request. A clean CLI completion alone cannot restart a cancelled Hosted request. A dependent in either channel can already be eligible while its actual predecessor awaits finding work; later parent source or obligation changes still participate in the existing semantic intent identity. Cancellation stops that intent; use a PR pause to hold new reviews persistently.

A pre-child automatic Hosted or CLI selection held only by `source_budget_exhausted`, `source_fetch_timeout` or `source_provider_unavailable` can retry its source selection after at least thirty seconds. It reuses the original selection and accepted configuration, policy, capability and authorizer, with the exact scheduling revision still current. At most two such delayed retries are permitted by a conservative durable transition budget; interrupted-selection recovery consumes that budget rather than resetting it. Existing recovery of an interrupted read remains separate from this bound on completed source holds. Restart and backup restore retain the budget and last-transition time. Restore/provider holds still prevent work.

A later selection or direct operation in the same channel fences off this recovery, including a cancelled, failed or uncertain request. Explicit held selections, linked children, exhausted budgets, refusals, rate limits and invalid source responses are never reopened by it. The retry performs ordinary fresh source selection and normal admission; success may link at most one ordinary child operation under the original authority. It neither grants rounds nor bypasses any dispatch guard. A meaningful source or control change can still authorize a new automatic intent through the normal scheduler.

Results still require normal adjudication, finalization and fix evidence. Automation does not infer fixes or grant more reviews. Enabling it can spend existing authorized Hosted allowance; it is a deliberate project control, not a prerequisite for routine review use.

## Automatic CLI requests

A project manager can explicitly enable `automatic_cli` through CLI, MCP or the project scheduling API. The browser shows its current state; its Hosted editor preserves the CLI setting. Both settings use the retained manager credential and active worker, with the same authorization rechecks before selection and dispatch. Changing either setting uses the shared scheduling revision for authorization. Each channel retains its own intent-basis revision in the scheduling event, so changing only the other channel does not recreate a cancelled or failed intent. Legacy events retain their shared basis without rewriting old digests. Reasserting unchanged settings rearms the supplied channels; a Hosted-only write preserves the omitted CLI basis. Older Hosted-only writes omit `automatic_cli` and preserve its current value; explicit `false` disables new CLI automation.

Automatic CLI uses the ordinary durable channel-front selection and execution path, without out-of-order or file-limit overrides. Existing grants, maxima, taper, channel closure, exact current-head checks, source-owned predecessor identities, and the selected target's publication and adjudication requirements remain in force. No setting increases grants or adjudicates findings. A meaningful completed result or source/control change can authorize another selection; ticks, restart, failed attempts and cancellation alone cannot. CLI and Hosted results have separate intent digests, so a clean completion in the other channel does not recreate a cancelled request.

The current server policy fixes one repository preference in code; it is not a per-project setting. For competing CLI work on the same installed provider account, the repository `benhook1013/FireMUD` takes priority over other projects. The repository identity is case-insensitive; a project display name does not grant priority. Selection considers that repository first, and the serialized attempt claim also yields to its eligible queued requests. Paused, invalid, draft-waiting or not-yet-due requests do not reserve the account. Other accounts remain independent and active reviews are never preempted. This preference does not relax dependencies or change retained quota deadlines. It has no fairness or maximum-deferral guarantee: other projects on that account may wait indefinitely while the preferred repository continues to have eligible work.

An automatically selected CLI request can recover once, after at least thirty seconds, from a transient GitHub source read that stopped preparation before allowance or dispatch. It retains the same operation, keeps the stopped attempt in history, and re-enters ordinary queue order when its comparison and authorization still qualify. A previously retained generic source-read failure requires a later successful refresh of the matching comparison. Every retry still verifies fresh source and allowance before dispatch.

An automatically selected Hosted or CLI preparation cancelled by supervisor shutdown can also recover once after thirty seconds, preserving its operation and selection. This requires the complete two-transition pre-admission history with no anchor, intent, external identity, allowance/preflight/query/observation, retained evidence or reservation. Current source, queue, authorization, pause and round gates still apply. Explicit operator cancellations, incomplete provider runs and unknown effects do not qualify; they remain visible for owner investigation rather than being automatically reposted. The one-retry budget is shared with the transient CLI source-preparation retry and survives restart.

Retained undecided CLI findings and accepted findings awaiting fix proof hold new CLI reviews on that PR, including after a partial attempt releases its reservation. Once those findings are handled, automatic CLI skips the comparison that produced the partial result and can advance on a qualified changed comparison. A provider warning that reports unreviewed files also prevents automatic repetition on the same comparison when it contains zero findings. A deliberate explicit CLI request can retry the same comparison after those obligations clear. Partial runs earn no completed round or taper credit.

An already queued explicit or automatic CLI operation prevents a duplicate request for its PR. Proven quota exhaustion keeps that operation and its original comparison through the existing shared-account backoff. Disable automatic CLI to stop new automatic selection and authorization of its undispatched children; explicit pending requests retain their original authorization. Use an operation cancellation or PR pause when the intent itself must stop. Results and merge decisions remain operator work.

## Pause a PR

An ordinary project writer can pause new reviews for a PR, even before its first review intent. Queue entries expose **Pause reviews** and **Resume reviews**. The pause covers undispatched work in both channels, preserves queued identities and cooldown deadlines, and permits collection of an already issued review. An optional short reason explains the pause; resume clears it. If a pause or authorization change is discovered during unused preparation, the same operation returns to the queue with its original attribution and any cooldown deadline; an admitted or possibly issued attempt is never silently requeued. Operation and project pauses take precedence over a PR pause in current queued diagnostics, and a PR pause takes precedence over draft, quota and queue-order waits.

Draft PRs are separately ineligible for dispatch. [Explicit CLI requests can wait for readiness](review-execution.md#cli-requests-while-draft). A PR pause does not change GitHub Draft state, round settings, earned taper, channel closure, worker coordination pause, project execution pause or an individual operation's pause. Resuming a PR does not resume an explicitly paused operation or reopen a closed channel. See [operation controls](review-execution.md#timer-backed-hosted-waiting) and [round controls](review-round-controls.md).

## CLI and MCP

The provider-free [lane diagnostic](review-lane-diagnostics.md) explains each configured PR against retained source and local target obligations, with explicit unknowns and parent source blockers. It does not establish fresh admission or trigger work.

Read the current scheduling revision before changing settings. Keep the exact request and key after an uncertain mutation outcome; replaying the same key cannot enable or pause twice.

```sh
fc reviews scheduling
fc reviews scheduling configure --automatic-hosted true --automatic-cli true --expect-revision 0 --key retained-enable-key
fc reviews scheduling read --pr 123
fc reviews scheduling pause --pr 123 --reason 'Preparing fixes' --expect-revision 0 --key retained-pause-key
fc reviews scheduling resume --pr 123 --expect-revision 1 --key retained-resume-key
```

Normal `reviews execution` / `review_execution_read` output composes execution with this scheduling read, including its independent revision, automatic setting and authorizing worker. The authorizer is permission attribution, not lane ownership. Use [quiet review activity watch](review-operations.md#quiet-review-activity-watch) to discover automatic requests and subsequent native operation changes without manufacturing inbox messages.

MCP equivalents are `review_scheduling_read`, `review_scheduling_configure`, `review_pull_scheduling_read` and `review_pull_scheduling_update`. The update takes explicit PR number, `paused`, expected revision and idempotency key; project configuration takes explicit `automatic_hosted`, optional `automatic_cli`, expected revision and key. Use tools advertised by the running client. Neither read starts work. Project reads include only currently queued paused PRs; explicit PR reads can inspect pauses outside the queue.

## HTTP and retention

`GET`/`POST /api/v1/projects/{project_id}/reviews/scheduling` read/configure project scheduling. The write body is `{expected_revision, automatic_hosted, automatic_cli?}` and requires project management. `GET`/`POST /api/v1/projects/{project_id}/reviews/pulls/{number}/scheduling` read/update a PR pause. The write body is `{expected_revision, paused, reason?}` and requires project write access. Writes require the normal explicit idempotency key. Unconfigured records read as revision zero and off/unpaused; writes return a new revision. Project reads report unavailable authorization or provider holds without exposing credential identifiers or tokens.

Backups retain scheduling, PR pauses and automatic-intent attribution. Older bundles without this optional domain remain off; version-one Hosted-only records migrate with automatic CLI off. Restore remains inactive with provider execution held. Historical authorizers remain valid historical evidence after revocation or retirement.

## Validation

Focused tests cover default-off behavior, authorization withdrawal, browser/writer/manager boundaries, pause before intent and dispatch, timer identity, cancellation suppression, independent progression and same-head dependency release, ordinary supervisor dispatch, typed CLI/MCP/browser contracts, exact-key recovery and backup/inactive restore. Controlled providers spend no live review allowance. Actual Chromium interaction proof covers desktop and mobile width. Installed release verification is recorded with deployment evidence rather than inferred from component tests.

## Hosted queue-priority display

Version `5` of `X-FC-Operation-Wait` extends version `3` with optional `queue_ahead_pull_number` in staged round progress. The browser shows **Behind #PR** for an earlier accepted Hosted request without a visible or hidden countdown. Older versions omit this hint and retained deadlines are unchanged. Version `4` remains the separate source-retry projection, without quota estimates; version `5` does not include source-retry evidence. The bound client uses [version `6`](source-preparation-retry-design.md#compatibility-and-backup-gates) to combine source-retry evidence and retained CLI allowance estimates without queue-priority hints. This display does not promise dispatch or change review accounting.


## Bounded scheduler decision history

The read-only decision history records actual automatic planning passes and completed source-selection settlements separately for each project and channel. It is not reconstructed from live diagnostics. Selection records contain each actually considered PR, the head known during that selection (absent when source acquisition failed or a pause avoided it), candidate outcome and reason, an identified blocking PR where available, the settlement outcome, and the selected PR. An unvisited suffix is not presented as considered. Automatic planning records explain control/intent filtering before source selection; their heads, when available, are retained-source facts and never fresh admission proof. An empty head means unknown, not no prior source.

Adjacent identical records are condensed into first/last observed timestamps and an occurrence count. Distinct selection identities remain distinguishable. Storage retains at most 256 records per project/channel and seven days of activity; new writes prune that lane, and reads exclude expired rows even for idle lanes. History begins with this feature, has no backfill, and is bounded operational telemetry rather than review evidence, allowance accounting, a scheduling authority, or an exhaustive audit journal. It is included as an optional validated backup domain; older bundles without it restore with empty history. The matching backup helper must understand this new domain before rollout. Live lane diagnostics remain available unchanged.

Use `fc reviews scheduling history --channel hosted --limit 20` or `review_selection_decision_history`. HTTP reads use `GET /api/v1/projects/{project_id}/reviews/lanes/{channel}/decisions?limit=20`. CLI/HTTP accept an exclusive `before` sequence cursor for older retained entries. Each page is newest first, defaults to 50, and is limited to 100. Read permission and project isolation are identical to the live diagnostic. Reads never contact providers, start work, acknowledge messages, or mutate review state. Missing or pruned history is not proof that no decisions occurred.

Recording automatic-plan telemetry does not manufacture intent or convert a no-op into scheduler progress; a recording failure is logged separately without cancelling authorized work. Automatic-pass recording has a ten-millisecond admission/transaction budget; contention can omit a pass rather than delay review scheduling, so this history is not an exhaustive audit journal. Selection settlement history is recorded only after the real selection commits, using a separate bounded best-effort write; recording failures cannot roll back admission or child work. A process interruption can omit the record but cannot claim an uncommitted child.

The query response also includes `omitted_recent_passes`: a project/channel-scoped lower bound from the last 256 omitted telemetry writes across this Engine process. This fixed-size in-memory gap ring does not wait for the database writer; counts reset on restart and fall as old entries are evicted. Zero is not proof of exhaustive history. Durable records and server warning logs remain separate evidence.
