# Terminal deployment duplicate retention

`deployment_duplicates.py` is a bounded prototype for recurring removal of exact duplicate deployment files. It is not installed or scheduled by this source change. Production adoption requires independent review of the installation's complete dependency graph and producer/consumer custody, not only passing local tests.

The private configuration explicitly enrolls terminal operation directories under one canonical root. Each entry pins its terminal marker SHA-256. Current and rollback directories are protected and cannot overlap enrolled roots. Enrollment is an operator decision: a directory name, timestamp or successful test does not establish that an operation is terminal. Failed and pending operations remain outside enrollment.

Within enrolled roots the collector discovers only standalone `fcd`, `canonical.sqlite` and `firecontroller.sqlite` files. It preserves unique bytes and a shallowest-path surviving copy for each exact SHA-256 group, refuses symlinks and changed content, skips SQLite files with journal/WAL sidecars and excludes live process references. It hashes both the candidate and surviving copy immediately before removal. It never recursively deletes directories, archives copies elsewhere or touches arbitrary database/capture/backup trees.

Every run acquires the same nonblocking deployment lease used by producers and consumers. All later uses of terminal artifacts must participate in that lease. The initial runtime integration must verify this, including descendant processes and rollback paths; the utility cannot establish that guarantee by scanning `/proc` alone.

`dependency_configs` must name the selected private JSON entrypoints. The collector follows absolute local paths recursively into JSON dependencies, checks every referenced local path exists and protects those paths. Missing dependencies refuse cleanup before deletion. This includes indirection such as batch configuration to provider configuration to an external transfer executable. Config values and credentials never enter result reports. This conservative traversal may refuse configurations containing absolute non-local identifiers; such configurations require explicit schema-aware integration rather than bypassing the check. Configuration references are not the entire dependency graph: unit/drop-in paths, command arguments and manually selected rollback scripts require installation-owner protection too.

Bounds are 128 terminal roots, 10,000 directory entries, 128 configuration files, one MiB per configuration and up to four GiB verification per invocation. Default verification is one GiB. Insufficient budget leaves files untouched for a later run; it does not expand scope. Results use the existing fixed latest/previous receipt writer. No timer template or live installation is included until independent qualification establishes complete custody. Future producer enrollment and unique rebuildable-build retention are separate obligations.

Run `python3 -m unittest discover -s tools/deploy -p 'test_deployment_duplicates.py'` for local duplicate, retry, uniqueness, reference, sidecar, protected-root, marker, symlink, budget and indirect-config regression tests. These local tests do not constitute production qualification.

## Producer receipt binding (isolated, not installed)

The command entrypoint now requires each terminal entry to name its private `producer_manifest` inside the enrolled operation. It verifies the existing `artifact_operation` terminal receipt: the exact manifest hash, top-level receipt filename, operation root, terminal state, and the device/inode of the collector's acquired deployment lease must all agree. An arbitrary marker hash, `producer_finished_unenrolled`, replaced lease, or changed enrollment is refused. Six integration tests invoke the real producer wrapper and exercise these refusal boundaries; the original seventeen collector tests remain low-level tests, not proof of command installation safety.

This does not yet establish authoritative current/rollback/pending selection. That requires the installer owner's finalized manifest contract and live custody adapter. No timer or production enrollment has been created, and this component must not be installed on its own. Existing successful-but-unenrolled historical operations are not retroactively enrolled by this change.

## Proposed custody pointer interface

`release_custody.py` is a pure contract prototype, not an authoritative emitter. It binds a node identity, versioned producer identity, generation and distinct predecessor, existing rollout lease identity, exact current/rollback manifests and explicit pending pin (or null). Pending is protected alongside current and rollback. Each release names exact source/image, existing operation roots and role-qualified executable/config/recovery-reader dependencies. The local fixture checks reject missing external tools, changed manifests, live pointer disagreement and replaced leases. Results always state `cleanup_authorized=false`.

The guarded installer must implement predecessor compare-and-swap and atomic fsynced publication under the lease. It must publish pending before mutation and clear it only after verified terminal success; crash/unknown states preserve the union. A future live adapter must independently verify actual node, unit/drop-in/argv/environment/mount references, executable bytes, credential *references* without reading/emitting their contents, and recovery readers needed by retained backup formats. It must close the graph and refresh observations under the same lease. This prototype does not yet model credential-reference edges or prove recovery closure, and therefore deliberately cannot authorize a collector. Node/current/rollback declarations cannot attest their own truth. Existing live deployment receipts are not retroactively authoritative state pointers.

### Review-driven refinement

A pending release may now explicitly use `phase=prepared` and `image_digest=null`, preserving existing source/operation inputs before any image is built. Current and rollback must remain `phase=built` with exact digests. Dependency executable/config/recovery-reader hashes are checked with bounded regular-file reads and identity checks; private JSON configuration closure rejects missing or undeclared indirect files. This remains a partial graph contract, not a claim to parse systemd/environment/credential-reference or all recovery requirements. Tests cover tampered executable bytes and missing indirect dependencies.

The collector command now **hard-refuses `apply=true`**, independent of configuration and marker receipts, until an independently qualified live custody adapter is wired. Low-level disposal functions remain testable only for exact-survivor algorithm qualification. Matching a caller-supplied `observed` dictionary is still not independent authority, and the state validator always returns `cleanup_authorized=false`. No production state publisher or CAS transition is implemented by these refinements.

### Guarded prepared-state publisher prototype

`publish_prepared` now performs a real private-file compare-and-swap under the existing exclusive rollout lease. It requires an existing validated pointer and exact predecessor digest, preserves active current/rollback pins, refuses unresolved pending work, and publishes only a new pre-image pending generation. It validates dependency bytes before publication, rechecks the live observation and pointer identity/content, fsyncs the temporary file, atomically replaces the pointer, then fsyncs its directory. Tests exercise publication, stale CAS, changed observation, held lease, active-pin changes, pending clear and unresolved pending refusal.

This publisher deliberately cannot bootstrap an installation, promote current/rollback, clear pending or authorize deletion. Its live observation callback still needs a deployment-owner implementation; fixture callbacks are not production authority. No production pointer has been emitted. A failure after atomic replacement but before directory fsync can leave an uncertain published pointer, so callers must inspect the exact generation rather than blindly retry or clear pending. Shared-lease compliance remains necessary for dependency stability, and the final destructive boundary must independently revalidate dependencies. The collector command stays hard-disabled for apply.
