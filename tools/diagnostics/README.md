# Offline SQLite storage inventory

`python3 tools/diagnostics/sqlite_storage.py --offline-snapshot /absolute/path/snapshot.sqlite` reports per-table/index page allocation, payload and unused bytes, plus database page/freelist totals. Use only an existing quiescent offline snapshot. This command does not create a backup or copy the database; do not point it at the live service database. No production inventory is established by the synthetic tests.

The immutable read-only connection creates no journals or shared-memory files. Existing WAL, SHM or journal sidecars refuse inspection rather than silently ignoring changes; symlinks and observed source changes also refuse. Keep the snapshot immutable for the whole invocation: stat checks do not replace custody against concurrent writers. Object names are included; row values and SQL definitions are not. Treat output as private operator data.

Inspection has a five-second default SQLite progress deadline, at most thirty seconds, and at most 1,024 reported objects. This output limit does not bound the preceding aggregate scan or impose a hard memory cap; use external memory/process limits for large or untrusted snapshots. Unsupported `dbstat`, interruption, corrupt input or incomplete evidence reports unavailable and exits nonzero, never partial success. The SQLite progress deadline cannot interrupt an operating-system disk read; use normal external process limits for an unresponsive filesystem. No checkpoints, VACUUM, row deletion, retention changes, deployment or background schedule are performed. Free pages and unused bytes are measurements, not authority or advice to delete data. Filesystem allocation, live WAL growth and semantic retention remain separate parts of the broad disk/database investigation.

Run `python3 -m unittest discover -s tools/diagnostics` for synthetic accounting, read-only conservation, sidecar refusal, deadline, object-budget and changed-source tests.

## Capture staging inventory

`python3 tools/diagnostics/capture_staging.py --capture-root /absolute/private/capture/root` inspects one existing local capture directory without reading capture contents, recursing, following staging symlinks or deleting anything. It reports counts, logical size and summed allocated bytes for `.capture-`, `.hosted-capture-` and `.exhaustion-` staging entries. Names and contents are not emitted. Shared hard links can count the same allocation twice; these totals are not reclaimable-space estimates.

The capture stores remove their random staging names on normal return using deferred cleanup. Abrupt process death can leave those names behind. This diagnostic measures that previously unaccounted category; it does not claim entries are abandoned, fix crash cleanup, or establish current live disk usage. Active writers and retained recovery evidence must be distinguished before a separate cleanup design. An OS-process test demonstrates staging survival after abrupt exit, not a fault-injected Controller capture run.

The scan is limited to 4,096 total directory entries and a five-second cooperative deadline, including unrelated entries. Detected directory changes, failures or exceeded limits report unavailable rather than partial success. File sizes may change during an active write; `observed` is approximate metadata, not a consistent snapshot or custody proof. External process limits are needed for blocked filesystem reads. Nothing is installed, scheduled or enabled by shipping this tool.

### Staging lifecycle and handling boundary

Inventory separates regular staging files with an observed same-device/same-inode private hard link under a published capture-shaped name from those without one. An independent file with equal bytes does not count. This identifies duplicate *names*, not validated captures or abandoned files. A hard-linked staging name generally adds no second data allocation, so removing it would not reclaim the payload. Contents and ownership are deliberately not inferred from filename patterns. Both groups remain protected.

Current writers close the staging descriptor **before** linking the final name. Therefore no open descriptor, process absence in a partial scan, or an old timestamp cannot establish safety to unlink: a writer can still be between close and publication. Files without a published link may be the only recoverable capture bytes after interruption. Do not add an age-based sweep or delete every matching prefix. Unknown legacy files stay untouched.

Any future automatic cleanup needs coordinated custody across **all** writers and the collector, covering creation through final link and directory sync, with crash release and bounded nonblocking collection. Merely locking a staging inode after creation leaves a creation-to-lock race. Admission of an old installation also needs verified quiescence because old writers do not participate. Only after such custody exists should deletion distinguish verified published duplicates from explicitly disposable new-generation scratch. Writer-side custody and an uninstalled duplicate-name collector are implemented on Linux as described below; production collector wiring and legacy adoption are not. Measure actual impact before adding a cleanup subsystem.

### Capture publication custody

`internal/capturecustody` supplies Linux-only shared-writer/exclusive-collector leases. All three capture-store Save paths acquire shared custody before creating a new staging file and retain it through their staging cleanup. No collector is wired. Writers require a deadline and hold an independently opened shared OS lock across the whole publication lifetime, including the closed-staging-descriptor gap. Maintenance acquisition is nonblocking. Separate opens preserve exclusion between goroutines in one process as well as between processes. Root and persistent lock identity/permissions are revalidated; a changed lock or root refuses. The lock file is never replaced or removed. Unsupported platforms cannot acquire custody. As with the capture stores, hostile same-user path replacement is outside this prototype's threat boundary.

Process tests hold custody across close-before-publication, kill the writer, then verify the lease releases and both sole-copy staging and published hard links remain unchanged. Separate actual-store tests exercise blocked admission, cancellation without files, successful publication and replay for CLI, Hosted and exhaustion stores. Acquisition waits at most five seconds or the earlier caller deadline; it does not extend the caller context or refresh any execution permission. Existing published-result reconciliation remains unchanged and needs no staging lease. Linux new staging names use `.capture-stage-v1-` with a type suffix; non-Linux stores retain legacy staging and behavior, without claiming maintenance custody. No automatic cleanup is enabled, and neither these tests nor source changes prove a live lease-aware rollout. Legacy files remain unenrolled. Run `go test -race ./internal/capturecustody` on Linux for the prototype tests.

### Uninstalled duplicate-name collector

Linux `CollectPublishedCaptureStaging` has no production caller, timer or CLI command. It requires explicit retained attempt/reference bindings and defaults to dry-run when `apply` is false. Under nonblocking exclusive writer custody, it strictly revalidates each final through the corresponding CLI, Hosted or exhaustion reader. Only matching-type `.capture-stage-v1-` names sharing that exact final inode can enter the plan. Independent byte-equal files, sole-copy staging, legacy names, symlinks and unbound files remain untouched. Names alone never establish valid retained captures.

The complete scan and plan are bounded before mutation: 128 bindings, 64 MiB of validated final files, 4,096 directory entries, 128 duplicate names and a five-second cooperative deadline. Apply rechecks root/lease and both identities before each unlink, then syncs the directory. Later interruption or a sync error can follow a partial apply; the returned removed count records successful unlinks and retry preserves final captures. This is removal of redundant names, not payload-space recovery. Filesystem operations can still block beyond a cooperative deadline.

Source tests exercise all three real stores, dry-run, apply, replay, active-writer refusal, conflicting/invalid references, symlink/legacy/sole-copy preservation and plan-overflow refusal before any deletion. These tests are not installation approval. Actual writer-generation adoption, live root ownership, exact-source runtime qualification and the operator's explicit apply scope must be established before wiring any production caller. No legacy cleanup, sole-copy recovery or automatic deletion is enabled.
