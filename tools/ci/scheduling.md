# Shared CI scheduling

## Contract

The CI workflow runs for pull requests and pushes to `main` and `develop`. It retains twenty-two Go race shards, source/browser checks, packaged qualification, two native smoke jobs and the final `validate` job: twenty-seven jobs per run. Job names, event-bound checkout behavior, race coverage and the executable validation gate remain unchanged. The gate depends on every family and runs with `always()`; only success from every family passes. Scheduling does not give failed, skipped or cancelled work CI credit.

Every job acquires exactly one repository-wide `firecontroller-ci-slot-N` concurrency group, where N is in 0 through 19. Each group uses `queue: max` and `cancel-in-progress: false`. Once the rollout gate is activated, no shared workflow-wide lock or per-run matrix parallel limit prevents independent runs from using different slots. Before activation the legacy workflow-wide lock remains in force. Admission happens through native Actions concurrency before runner execution, not a polling step that consumes a runner while waiting. The twenty groups bound concurrent admitted jobs, including the gate, to twenty across participating workflow revisions.

The race matrix explicitly associates its existing ordered shard inventory with slots 0 through 19, followed by slots 0 and 1 for the final two shards. Source checks use slot 2, qualification uses slot 3, Windows uses slot 4 and macOS uses slot 5. Validation reuses slot 2 after its own families finish. These keys never include a PR number, branch, commit, workflow run or attempt. They therefore coordinate all participating runs rather than granting each run a separate budget. No new credentials, services, installed dependencies or privileged workflow are needed.

## Throughput and queue limits

A lone run with enough runnable jobs can occupy all twenty slots. Other PRs and branch runs can start jobs on released slots while an earlier run still has a slow tail. This is a workload-specific opportunity, not a fully work-conserving scheduler: a runnable job cannot borrow another lane when its assigned lane is occupied. One long job and queued jobs on the same lane can leave nineteen lanes idle. No guaranteed utilization, fairness across lanes or elapsed-time bound is claimed. Available Linux, Windows and macOS runners and the account capacity shared with FireMUD can further reduce throughput. Repository-local concurrency does not impose a combined FireMUD/FireController cap or reserve runners for either project.

GitHub admits one active member and up to one hundred pending jobs per group with `queue: max`; new arrivals are cancelled once that queue is full. FIFO is based on when a job starts waiting on its group, not workflow dispatch order. A run can contribute multiple jobs to the same group, so the limit is not one hundred workflow runs. Existing queued jobs are not displaced, but a latest live PR or develop revision can lose a required job on overflow and cannot pass validation. After capacity drains, an operator must rerun that current revision as appropriate; there is no automatic overflow recovery or promise that every latest revision is always admitted.

This workflow deliberately does not cancel superseded runs. New revisions stay eligible at ordinary load, alongside independent PRs and branch pushes. A future per-PR/ref supersession policy must use a separate workflow-level group, not change the shared job lanes to cancellation mode. `queue: max` and `cancel-in-progress: true` cannot be combined in the same group. Supersession alone cannot eliminate saturation across many distinct PRs.

True dynamic allocation of any free slot and durable latest-revision admission beyond provider queue limits would require a larger admission/runner scheduling service, including mixed-platform capacity, recovery and check-identity handling. That infrastructure is outside this bounded native implementation.

Provider semantics: [GitHub concurrency documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) and [larger queue announcement](https://github.blog/changelog/2026-05-07-github-actions-concurrency-groups-now-allow-larger-queues/).

## Rollout and recovery

The repository variable `FIRECONTROLLER_CI_INTERLEAVE` controls the workflow-level rollout gate. An unset value or any value other than `true` keeps the original `firecontroller-ci` workflow group, with `queue: max` and `cancel-in-progress: false`. GitHub compares strings case-insensitively, so `TRUE` and `True` also enable interleaving; use the documented lowercase value for administration. The default therefore serializes new gated workflows with legacy workflows while this change is reviewed and adopted. All new jobs acquire lanes even while serialized.

After legacy runs are drained and all eligible workflow revisions are aligned, the repository owner can set the variable to `true`. Future group selections then use `firecontroller-ci-run-{run_id}`, allowing independent workflows to interleave while their jobs share the same twenty lanes. Changing this variable is a separate owner-operated repository setting action; the workflow and tests do not modify it.

Group selection for an existing or queued workflow uses its captured configuration and evaluated admission context. A later variable update is not a migration of those already selected groups. Default-gated runs may remain queued on the old group after activation; they are still safe alongside activated gated runs because both acquire job lanes. Do not assume a variable update drains, cancels, restarts or reassigns existing runs. Exact variable visibility and provider admission timing require operational verification.

To roll back interleaving for future group selections, unset the variable or give it a value other than `true`. Existing interleaving runs can continue on their previously selected groups alongside the first newly serialized run. Their shared job lanes still enforce twenty, but rollback does not immediately serialize every already admitted run. Do not reintroduce an ungated legacy revision until all interleaving runs are drained.

The hard twenty-job bound after activation applies only to jobs participating in these twenty keys. An older workflow using the previous workflow-wide group does not acquire these slots. An old twenty-job run alongside a new twenty-job run can therefore reach forty. Before activating interleaving and claiming the repository-wide cap, drain older in-flight and queued runs and align all eligible PR and push workflow revisions with this contract. An old workflow queued before activation is still an old workflow and must be included in the drain. Do not rerun historical workflows outside the slot scheme while relying on the cap. Publication alone does not perform this operational drain or alignment. Keep lane names stable during future changes, and count every newly added job, including administrative or finalization jobs.

A saturated queue is a failed validation outcome, not permission to omit a check. Recovery must retain the correct event revision and current-attempt evidence. Deploying additional schedulers, generating synthetic passing checks or changing required-check policy is not part of this change.

## Proof and limits

`make ci-selection-check` checks the actual workflow inventory, slot range, all six concurrency declarations including the exact safe-default rollout expression, matrix expansion, job names, triggers and absence of checkout revision overrides. It retains the package/test coverage checks and executes the real validation shell against success and non-success family results. Mutations demonstrate refusal of missing or out-of-range lanes, extra jobs/dimensions, cancellation, incorrect queue mode, changed names or revision overrides.

The bounded event-driven model derives all twenty-seven jobs and their slots from the workflow. It assumes immediate runner availability and FIFO lane admission, and demonstrates full twenty-slot use by a lone run, independent PR/develop overlap, progress on nineteen lanes during a slow tail, overlap of one run's gate with another run's work, and a peak no greater than twenty including non-matrix jobs. Workflow-admission model checks demonstrate default serialization with old workflows, immutable already-selected groups across activation, and rollback affecting future group selections while existing lane-bound runs remain safe. Separate counterexamples demonstrate idle capacity from fixed affinity, cancellation of a latest arrival at the hundred-pending-job boundary and failure of the global bound during mixed legacy/new rollout.

These are local configuration/model checks, not observed GitHub runner timing or completed operational rollout. Actual hosted overlap, native queue behavior under account contention, exact-revision required-check results and legacy drain/alignment must be verified by the repository owner during rollout. No CI runs are triggered by the model.
