# Shared CI scheduling

## Default-closed interleaving gate

The CI workflow runs for pull requests and pushes to `main` and `develop`. It retains twenty-two Go race shards, source/browser checks, packaged qualification, two native smoke jobs and the final `validate` job: twenty-seven jobs per run. Job names, event-bound checkout behavior, race coverage and the executable validation gate remain unchanged. The gate depends on every family and runs with `always()`; only success from every family passes. Scheduling does not give failed, skipped or cancelled work CI credit.

Every job acquires exactly one repository-wide `firecontroller-ci-slot-N` concurrency group, where N is in 0 through 19. Each group uses `queue: max` and `cancel-in-progress: false`. The workflow reads `FIRECONTROLLER_CI_INTERLEAVE`: unset or non-`true` retains the literal `firecontroller-ci` lock; `true` selects `firecontroller-ci-run-{run_id}`. GitHub string equality is case-insensitive, so `TRUE` and `True` also enable overlap, while whitespace, `1` and `yes` do not. Both workflow modes retain `queue: max` and disabled cancellation. Admission happens through native Actions concurrency before runner execution, not a polling step that consumes a runner while waiting. The unchanged twenty groups bound concurrent admitted jobs, including the gate, to twenty across participating workflow revisions.

The gate carries the existing development implementation without replacing this branch's smaller job inventory. It cannot inspect other workflows, prove a drain or change repository settings. Its safe default does not establish the effective setting: verify that the variable is disabled before publishing gate-bearing source, and complete the alignment and drain below before activation. A pre-existing `true` value could activate a newly published PR workflow immediately.

The race matrix explicitly associates its existing ordered shard inventory with slots 0 through 19, followed by slots 0 and 1 for the final two shards. Source checks use slot 2, qualification uses slot 3, Windows uses slot 4 and macOS uses slot 5. Validation reuses slot 2 after its own families finish. These keys never include a PR number, branch, commit, workflow run or attempt. They therefore coordinate all participating runs rather than granting each run a separate budget. No new credentials, services, installed dependencies or privileged workflow are needed.

## Throughput and queue limits

A lone run with enough runnable jobs can occupy all twenty slots. With the gate enabled, other PRs and branch runs can start jobs on released slots while an earlier run still has a slow tail. The disabled gate retains whole-workflow serialization. This is a workload-specific opportunity, not a fully work-conserving scheduler: a runnable job cannot borrow another lane when its assigned lane is occupied. One long job and queued jobs on the same lane can leave nineteen lanes idle. No guaranteed utilization, fairness across lanes or elapsed-time bound is claimed. Available Linux, Windows and macOS runners and the account capacity shared with FireMUD can further reduce throughput. Repository-local concurrency does not impose a combined FireMUD/FireController cap or reserve runners for either project.

GitHub admits one active member and up to one hundred pending members per group with `queue: max`; new arrivals are cancelled once that queue is full. With the gate disabled, the workflow-level group queues up to one hundred runs and rejects additional runs; individual job groups also retain the provider queue bound. FIFO is based on when a job starts waiting on its group, not workflow dispatch order. When the gate permits concurrent workflows, a run can contribute multiple jobs to the same job group, so each lane limit must not be interpreted as one hundred workflow runs. Existing queued jobs are not displaced, but a latest live PR or develop revision can lose a required job on overflow and cannot pass validation. After capacity drains, an operator must rerun that current revision as appropriate; there is no automatic overflow recovery or promise that every latest revision is always admitted.

This workflow deliberately does not cancel superseded runs. New revisions stay eligible at ordinary load, alongside independent PRs and branch pushes. A future per-PR/ref supersession policy must use a separate workflow-level group, not change the shared job lanes to cancellation mode. `queue: max` and `cancel-in-progress: true` cannot be combined in the same group. Supersession alone cannot eliminate saturation across many distinct PRs.

True dynamic allocation of any free slot and durable latest-revision admission beyond provider queue limits would require a larger admission/runner scheduling service, including mixed-platform capacity, recovery and check-identity handling. That infrastructure is outside this bounded native implementation.

Provider semantics: [GitHub concurrency documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) and [larger queue announcement](https://github.blog/changelog/2026-05-07-github-actions-concurrency-groups-now-allow-larger-queues/).

## Alignment, activation and recovery

The repository operator, Ben Hook, owns verification and any setting change. Record exact observations and timestamps with the rollout work, rather than treating source tests as operational proof.

1. Before publishing a gate-bearing revision, verify and record the effective `FIRECONTROLLER_CI_INTERLEAVE` value or verified absence. Account for repository and organization-level visibility and precedence where applicable; environment-level variables are unavailable during workflow group selection. Unknown state is a stop. Keep the setting disabled during source review and alignment.
2. Obtain human merges for required source changes. Inventory every eligible `main` and `develop` push and open PR's event-selected workflow, including dependency/fork branches and other workflows consuming the intended budget. Every job must use the unchanged twenty-slot namespace. PR head source or a mutable current merge ref cannot certify an older run's event-selected source. Preserve this branch's twenty-seven-job inventory and the separate development workflow's selector, twenty-third race shard, container, publisher, website-only conditions and required gates.
3. Enumerate every nonterminal CI run, attempt and page of jobs, including `pending`, `queued`, `requested`, `waiting` and `in_progress`. Record run identity, event, immutable source and lane capability. Drain every legacy no-slot or unverified run. Branch updates do not modify queued workflows or historical reruns. Do not cancel, rerun or replace checks as a side effect of an audit.
4. Prevent fresh legacy arrivals during the final audit and activation. Coordinate source publication and historical reruns with contributors and automation. A necessary legacy rerun after activation requires disabling the gate and waiting for all already independently admitted runs to finish first. Disabling alone does not make an immediate legacy rerun safe.
5. Verify exact-revision required checks and app identities on each target branch. Retain `validate` and its real executable prerequisites; do not manufacture a passing result or reduce branch protection. Verify account and OS runner capacity, including FireMUD contention. These lanes are a repository-local upper bound, not a combined-project cap or runner reservation.
6. Only after review, alignment and a fresh legacy-free audit may the operator explicitly enable the setting. Observe independently admitted lane-capable runs, exact-revision checks, peak occupancy including non-matrix jobs, platform waits and queue overflow. Verify both this smaller workflow and the existing full PR/development and selected website-only development paths without substituting one inventory for the other.

Already selected workflow groups are not migrated by a later setting change. Lane-bound queued compatibility workflows remain safe alongside activated lane-bound workflows because they share the same slots; they need not be cancelled or moved. Enabling the setting does not release those previously queued workflows. Rollback disables the setting for future group selections, retains all twenty job lanes, and waits for already admitted work to finish. It does not immediately serialize existing runs. Exact variable visibility and provider admission timing require operational verification.

A legacy workflow that lacks lanes is safe alongside disabled gate workflows because both use the literal workflow lock. It would not be safe alongside an independently admitted interleaving run: the legacy matrix admits up to sixteen Linux shards alongside source checks, qualification and two native jobs, while validation waits for those families. Those twenty runner occupants plus a new twenty-lane run could reach forty. Include old queued workflows in the drain before enabling overlap. Do not rerun historical workflows outside the slot scheme while relying on an activated shared-lane cap, or reintroduce an ungated legacy revision until interleaving runs are drained. Publication alone does not perform this operational drain or alignment. Keep lane names stable during future changes, and count every newly added job, including administrative or finalization jobs.

A saturated queue is a failed or cancelled validation outcome, not permission to omit a check. Recovery must retain the correct event revision and current-attempt evidence. Deploying additional schedulers, generating synthetic passing checks or changing required-check policy is not part of this change.

## Proof and limits

`make ci-selection-check` checks the actual workflow inventory, slot range, all six concurrency declarations including the exact default-closed gate and its single variable reference, exact job-to-slot affinity, matrix expansion, job names, triggers and absence of checkout revision overrides. It retains the package/test coverage checks and executes the real validation shell against success and non-success family results. Mutations demonstrate refusal of missing or out-of-range lanes, extra jobs/dimensions, cancellation, incorrect queue mode, changed names or revision overrides.

The bounded event-driven model derives all twenty-seven jobs and their slots from the workflow. It assumes immediate runner availability and FIFO lane admission, and demonstrates single-run twenty-slot use. Enabled-gate scenarios cover independent PR/develop overlap, progress on nineteen lanes during a slow tail, overlap of one run's validation with another's work and a peak no greater than twenty including non-matrix jobs. Admission checks cover disabled serialization with legacy workflows, case-insensitive activation, immutable already-selected groups, rollback affecting future group selections, and finite workflow/job queues. Separate counterexamples demonstrate fixed-affinity idle capacity, cancellation of a latest arrival at the hundred-pending boundary and failure of the bound during mixed legacy/new rollout. The model handles successful DAG completion, not rejected-job termination or failure propagation and workflow-group release. Separate checks execute the real validation shell against successful and failed, skipped, cancelled or unknown family results under both setting modes. GitHub expression execution, variable propagation and admission timing are not simulated provider proof.

The mixed-rollout counterexample admits actual modeled jobs for both runs. Its legacy model preserves the sixteen-shard matrix cap, independent source/qualification/native occupancy, queued-shard refill and validation dependencies, rather than adding a constant runner count.

These are local configuration/model checks, not observed GitHub runner timing or completed operational rollout. Actual hosted overlap, native queue behavior under account contention, exact-revision required-check results and legacy drain/alignment must be verified by the repository owner during rollout. No CI runs are triggered by the model. While the gate is disabled, shared lanes cannot improve cross-run overlap and their collisions can lengthen a single run. Before changing lane assignments, compare job start/end intervals and lane occupancy over representative runs; differing revisions and runner availability do not establish a causal speedup or regression. The lane-bound proof is not an elapsed-time optimization result.
