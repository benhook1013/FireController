# Shared CI scheduling

CI keeps the latest workflow arrival for each pull request and each push branch. GitHub groups runs by event and full ref. A new pull-request run replaces queued or running CI for that PR. A push to `main` replaces earlier push CI for `main`; `develop` has its own group. The `develop` push and PR #45 can both run because they validate different events. GitHub chooses by concurrency admission order. When recovering CI, trigger a fresh run for the current comparison. Rerunning a historical event can displace newer CI in the same group.

## Shared job limit

Every job in this CI workflow uses one of twenty repository-wide groups, `firecontroller-ci-slot-0` through `firecontroller-ci-slot-19`. The job groups retain `queue: max` and finish running jobs without cancelling them for unrelated work. The workflow groups use GitHub's single pending slot and cancel superseded runs. This separates revision supersession from the shared runner budget. Different PRs and push branches can make progress when lanes free up. Fixed lane assignments and Linux, Windows or macOS runner availability can still leave capacity idle. GitHub caps each job queue at one hundred pending jobs, so a sufficiently large burst of distinct PRs can still overflow. An overflowed required job needs a fresh current-comparison check. [GitHub concurrency guidance](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)

This workflow runs twenty-seven jobs, including twenty-two Go race shards. Source/browser and validation use slot 2, packaged qualification uses slot 3, and Windows and macOS use slots 4 and 5. The ordered race shards use slots 0–19, then 0–1. The required `validate` check retains its name, exact event revision and success criteria. A cancelled or failed required family cannot satisfy validation.

## Switching from the global queue

1. Before publishing the new policy, inventory FireController CI across all nonterminal states, including pending, queued, requested, waiting and in-progress runs. Match PR runs to their PR and current head and base comparison, and push runs to the current ref tip. Identify event-selected workflow source when checking lane compatibility. A run's head branch or current PR merge ref alone cannot identify a historical run's event source.
2. Cancel only runs proven obsolete by a moved or closed PR comparison, a moved push ref, or a verified replacement for the same comparison. Preserve current evidence and leave ambiguous runs alone until verified or terminal. Before starting independent workflows, drain any running or waiting workflow that could still dispatch jobs outside the shared lanes. Coordinate the cutover with active contributors and avoid historical reruns. Earlier runs keep the group they were admitted into.
3. Verify current PR heads and both branch tips have a successful or live run for their exact comparison. Publish the main-facing change and carry it into the integrated development workflow, preserving each workflow's job inventory. After the human merge, merge the updated base into existing PR branches where needed so future PR events select the new workflow. Where an exact current comparison missed admission, trigger a fresh event after checking there is no suitable run. Retain branch protection and the required Actions check source.
4. Verify on GitHub that new runs supersede older ones for the same PR and push ref, that different refs overlap within the shared lanes, and that current heads receive the required check. If a legacy run resurfaces, stop it before it can exceed the shared budget. FireMUD's workflows and runner limits are independent of these repository-local groups.

## Local verification

`make ci-selection-check` checks the actual job inventory, workflow group, shared lane keys, slot assignments and validation gate. The bounded model exercises same-ref replacement, independent PR and push runs, shared lane occupancy and finite queues. The model assumes available runners and does not measure GitHub dispatch or cancellation timing. The pinned actionlint version predates the job-level `queue` field. The workflow check ignores only that exact diagnostic and the CI-selection checks verify the queue declarations.
