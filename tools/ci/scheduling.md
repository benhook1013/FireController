# Shared development CI scheduling

## Default-closed interleaving gate

The integrated development workflow reads the repository variable `FIRECONTROLLER_CI_INTERLEAVE` when GitHub selects its workflow concurrency group. An unset or non-`true` value retains the repository-wide `firecontroller-ci` group. The string `true` selects `firecontroller-ci-run-{run_id}`, allowing independent runs to reach the same twenty job lanes. GitHub expression string comparison is case-insensitive, so `TRUE` and `True` also enable overlap; whitespace, `1` and `yes` do not. Both modes retain `queue: max` and `cancel-in-progress: false` at workflow and job level.

The gate does not inspect other workflows, prove a drain, reserve runners or write repository settings. Its safe default does not establish the repository's actual setting. Before publishing this source to any PR or eligible push branch, the repository operator must verify the effective variable is disabled. Before enabling it, complete the alignment and drain below. A pre-existing `true` value could otherwise activate a newly published PR workflow immediately.

This workflow is not the smaller main-branch workflow. Its expanded inventory contains thirty-one jobs: twenty-three Go race shards, two native smoke jobs, change selection, source/browser checks, packaged qualification, container runtime, validation and trusted-push publication. A full PR runs thirty jobs because it cannot publish. An explicitly selected website-only development push runs six jobs: selector, source, qualification, container, validation and publication. Only race/native are skipped under that existing selection contract. All job names, permissions, steps, event-revision binding, artifact checks and conditional behavior remain unchanged.

Every job acquires one of `firecontroller-ci-slot-0` through `firecontroller-ci-slot-19` with `queue: max` and cancellation disabled. The twenty-three race shards retain their order and use slots 0 through 19, then 0 through 2. Source and validation use slot 2, qualification 3, Windows 4, macOS 5, selector 6, publication 7 and container 8. Matrix parallel limits no longer reserve a separate per-run budget. A full run can occupy twenty lanes after its selector finishes. Validation still waits for all six prerequisite families and retains its executable website-only exception; publication still waits for successful validation and runs only for trusted branch pushes.

Publication previously used `container-publication-${{ github.ref }}`. It now uses the shared slot 7 because a job cannot acquire two Actions concurrency groups. This preserves mutual exclusion between publishers of the same ref and imposes stronger serialization across all publishers and other slot-7 jobs. It can delay publication but does not broaden publication authority, change the tested artifact, create a deployment or require a new credential. With the gate disabled, the workflow lock already serializes publication across runs. With the gate enabled, the shared lane preserves publisher exclusion across interleaved runs.

## Throughput and finite queues

When the gate is enabled, independent runs can use released lanes during a slow tail. With the gate disabled, whole workflows remain serialized. Fixed lane affinity is not a work-conserving scheduler: jobs waiting on one occupied lane cannot borrow nineteen idle lanes. Runner platform availability and account capacity shared with FireMUD can further reduce throughput. Repository-local groups neither reserve runners nor impose a combined FireMUD/FireController budget.

GitHub permits one active member and up to one hundred pending members per concurrency group with `queue: max`; further arrivals are cancelled. The current workflow lock can reject additional runs at that limit. With the interleaving gate enabled, each lane can reject additional jobs, including a latest live revision. One run can contribute several jobs to a lane, so its capacity is not one hundred runs. FIFO follows when a member begins waiting on its group, not workflow dispatch time. There is no supersession policy or automatic overflow recovery. A rejected required check is not a passing result; an owner must rerun the correct current revision after capacity becomes available.

These semantics are documented by [GitHub concurrency guidance](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency). Strict dynamic allocation to any free slot with durable latest-revision admission beyond those limits requires a larger admission/runner service, outside this bounded implementation.

## Alignment and activation sequence

The main-branch compatibility source and this development source have different inventories and validation contracts. Do not replace the integrated workflow with the smaller main workflow or copy its twenty-two-shard guard. Retain the selector, twenty-third race shard, container and publisher, native artifact handling and website-only qualification rules when resolving merges. Every new job must join a counted lane. The development gate belongs with the integrated development source; a main-branch port must retain that branch's own jobs and checks.

The repository operator, Ben Hook, owns the following rollout checks and any repository setting change. Record observations and timestamps with the rollout work, not as an assertion that the source code enforces them.

1. Before publishing a gate-bearing source revision, inspect the effective `FIRECONTROLLER_CI_INTERLEAVE` variable and record its exact value or verified absence. Verify repository and organization-level availability and precedence; environment-level variables are not available when the workflow group is selected. Unknown state is a stop, not an assumed disabled setting. Keep the setting disabled during source review and compatibility alignment.
2. Obtain human merges for the required compatibility source. Inventory all eligible `main` and `develop` pushes and every open PR's event-selected workflow, including dependency branches and fork PRs. Every job must use the unchanged `firecontroller-ci-slot-0` through `firecontroller-ci-slot-19` namespace before overlap is allowed. A PR head's source is a useful first check, but PR runs use the event's merge revision; a current branch or mutable merge ref is not evidence about an older run. Unverified event-selected source remains a rollout blocker. Other workflows consuming the intended CI budget must also be accounted for.
3. Enumerate all nonterminal CI runs and every page of their jobs. Include `pending`, `queued`, `requested`, `waiting` and `in_progress` runs, not only runner-active jobs. Record run ID, attempt, event, immutable source and lane capability. Drain every legacy no-slot or unverified run. Updating a branch does not update a previously queued workflow or a historical rerun. Do not cancel, rerun or replace an exact-revision check as a side effect of the audit.
4. Prevent a new legacy arrival during the final audit and setting change. Align future event sources and coordinate with contributors and automation so no historical no-slot revision is rerun. If a legacy rerun becomes necessary after activation, disable the gate, let all already independently admitted runs finish, then perform the rerun while the legacy workflow lock is effective. Disabling alone does not make an immediate legacy rerun safe.
5. Verify current required checks, their app identity and source-revision binding on each target branch. Keep the required `validate` name and the real executable prerequisite gate; do not manufacture a green check, reduce required coverage or change branch protection to clear the queue. Confirm account and OS runner capacity, including concurrent FireMUD work. FireController's twenty lanes are a repository-local upper bound, not an account-wide twenty-runner budget or a reservation. Zero active FireController jobs does not prove account headroom.
6. After review, source alignment and a fresh legacy-free audit, the operator may explicitly enable the setting. Observe independently admitted lane-capable runs, exact-revision checks, lane occupancy, native-platform waits and overflow. Verify the thirty-one-job full development push, thirty-job PR and six-job website-only development path under their existing selection conditions. Roll back by disabling the setting if required; retain all twenty job lanes and wait for admitted work to finish. A setting change never migrates workflow groups already selected.

Lane-bound queued compatibility workflows remain safe alongside enabled lane-bound workflows because every job shares the same slot namespace. They need not be cancelled or moved to the new workflow group. Legacy workflows without slots do not share that protection: a legacy twenty-job run plus an enabled twenty-job run can reach forty. Full alignment and a drain are required even if the currently running sample looks lane-capable.

This source does not perform human merges, a drain, settings mutations or hosted acceptance. The activation checks are operational preconditions. Source review and local model success cannot substitute for them.

## Local proof and limits

`make ci-selection-check` verifies the real thirty-one-job inventory, exact names and conditional boundaries, all nine concurrency declarations, the exact default-closed gate, explicit matrix slot mapping and absence of revision overrides. Existing development-selector tests execute the real validation shell, including refusal of skipped race/native checks outside the selected website-only development push. Existing package/test slice tests and release/deployment helper checks remain intact.

The bounded scheduler model derives its jobs and lanes from this workflow and respects selector, validation and publication dependencies. It proves single-run twenty-slot use, full PR publication exclusion and the six-job website-only path. Enabled-interleaving scenarios exercise PR/develop overlap, slow-tail progress on nineteen lanes, selector/validation/publication overlap with another run's tests, and the twenty-job peak including all non-matrix jobs. Tests also cover disabled whole-run serialization, case-insensitive activation, compatibility-queue retention during activation, rollback without migration, publisher mutual exclusion, fixed-affinity idle capacity, latest-arrival workflow/job queue overflow and the legacy/new overlap counterexample. The model does not claim the repository setting is enabled or the operational preconditions are satisfied. Its DAG models successful completion only; rejected-job termination, failure propagation and subsequent workflow-group release are not simulated. Separate tests execute the real validation shell with failed, cancelled, skipped and unknown prerequisite results, and reject every value outside the existing full/website-only success contract. Expression evaluation and group-selection timing are modeled, not executed in GitHub.

The pinned actionlint release predates GitHub's `concurrency.queue` field: only its exact unknown-queue diagnostic is excluded, while the CI-selection checks verify every queue and cancellation declaration. Every other linter diagnostic remains fatal.

These are local source/model checks, not observed hosted concurrency, executed publication, deployment proof or operational rollout. Actual GitHub timing, exact-revision required checks, runner contention and safe drain/alignment require separate owner verification. No model triggers CI or publishes containers.
