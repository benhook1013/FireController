# Shared CI scheduling

## Current compatibility stage

The CI workflow runs for pull requests and pushes to `main` and `develop`. It retains twenty-two Go race shards, source/browser checks, packaged qualification, two native smoke jobs and the final `validate` job: twenty-seven jobs per run. Job names, event-bound checkout behavior, race coverage and the executable validation gate remain unchanged. The gate depends on every family and runs with `always()`; only success from every family passes. Scheduling does not give failed, skipped or cancelled work CI credit.

Every job acquires exactly one repository-wide `firecontroller-ci-slot-N` concurrency group, where N is in 0 through 19. Each group uses `queue: max` and `cancel-in-progress: false`. The workflow also retains the literal `firecontroller-ci` concurrency group with `queue: max` and `cancel-in-progress: false`. Independent runs remain serialized with legacy workflows. This version reads no repository variable and does not enable interleaving; it safely introduces the lanes before a separately reviewed gate change. Admission happens through native Actions concurrency before runner execution, not a polling step that consumes a runner while waiting. The twenty groups bound concurrent admitted jobs, including the gate, to twenty across participating workflow revisions.

The race matrix explicitly associates its existing ordered shard inventory with slots 0 through 19, followed by slots 0 and 1 for the final two shards. Source checks use slot 2, qualification uses slot 3, Windows uses slot 4 and macOS uses slot 5. Validation reuses slot 2 after its own families finish. These keys never include a PR number, branch, commit, workflow run or attempt. They therefore coordinate all participating runs rather than granting each run a separate budget. No new credentials, services, installed dependencies or privileged workflow are needed.

## Throughput and queue limits

A lone run with enough runnable jobs can occupy all twenty slots. Under the proposed future interleaving gate, other PRs and branch runs could start jobs on released slots while an earlier run still has a slow tail. The current literal workflow lock prevents that overlap. This is a workload-specific opportunity, not a fully work-conserving scheduler: a runnable job cannot borrow another lane when its assigned lane is occupied. One long job and queued jobs on the same lane can leave nineteen lanes idle. No guaranteed utilization, fairness across lanes or elapsed-time bound is claimed. Available Linux, Windows and macOS runners and the account capacity shared with FireMUD can further reduce throughput. Repository-local concurrency does not impose a combined FireMUD/FireController cap or reserve runners for either project.

GitHub admits one active member and up to one hundred pending members per group with `queue: max`; new arrivals are cancelled once that queue is full. In the current compatibility stage, the workflow-level group queues up to one hundred runs and rejects additional runs; individual job groups also retain the provider queue bound. FIFO is based on when a job starts waiting on its group, not workflow dispatch order. After a future gate permits concurrent workflows, a run can contribute multiple jobs to the same job group, so each lane limit must not be interpreted as one hundred workflow runs. Existing queued jobs are not displaced, but a latest live PR or develop revision can lose a required job on overflow and cannot pass validation. After capacity drains, an operator must rerun that current revision as appropriate; there is no automatic overflow recovery or promise that every latest revision is always admitted.

This workflow deliberately does not cancel superseded runs. New revisions stay eligible in the serialized workflow queue at ordinary load, alongside independent PRs and branch pushes. A future per-PR/ref supersession policy must use a separate workflow-level group, not change the shared job lanes to cancellation mode. `queue: max` and `cancel-in-progress: true` cannot be combined in the same group. Supersession alone cannot eliminate saturation across many distinct PRs.

True dynamic allocation of any free slot and durable latest-revision admission beyond provider queue limits would require a larger admission/runner scheduling service, including mixed-platform capacity, recovery and check-identity handling. That infrastructure is outside this bounded native implementation.

Provider semantics: [GitHub concurrency documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) and [larger queue announcement](https://github.blog/changelog/2026-05-07-github-actions-concurrency-groups-now-allow-larger-queues/).

## Proposed activation and recovery

Enabling interleaving requires a follow-up reviewed workflow gate change, alignment of all eligible PR and push revisions, and a drain of legacy in-flight and queued runs. This compatibility-stage workflow cannot be activated by a repository variable alone. Publish this literal-lock compatibility stage separately. A later activation PR must name the repository operator responsible for verifying the setting and recording its exact observed state before rollout. Do not assume an unverified variable is unset or disabled.

The proposed follow-up gate would use `FIRECONTROLLER_CI_INTERLEAVE`: unset or non-`true` would retain `firecontroller-ci`; `true` would select `firecontroller-ci-run-{run_id}`. GitHub string equality is case-insensitive, so `TRUE` and `True` would also activate that proposed expression. Both workflow and job groups would retain `queue: max` and disabled cancellation. These are modeled future semantics, not behavior of the current file. No test or workflow changes repository variables.

For that proposed gate, an existing or queued workflow's selected group is not migrated by a later variable change. Runs still captured on the compatibility group would remain safe alongside activated lane-bound runs because both acquire the same job slots. Do not assume a variable update drains, cancels, restarts or reassigns existing runs. Exact variable visibility and provider admission timing would require operational verification. Rolling the proposed gate back to a disabled value would affect future group selections, not immediately serialize all previously admitted runs.

A legacy workflow that lacks lanes is safe alongside this compatibility stage because both use the literal workflow lock. It would not be safe alongside an independently admitted interleaving run: the legacy matrix admits up to sixteen Linux shards alongside source checks, qualification and two native jobs, while validation waits for those families. Those twenty runner occupants plus a new twenty-lane run could reach forty. Include old queued workflows in the drain before enabling overlap. Do not rerun historical workflows outside the slot scheme while relying on an activated shared-lane cap, or reintroduce an ungated legacy revision until interleaving runs are drained. Publication alone does not perform this operational drain or alignment. Keep lane names stable during future changes, and count every newly added job, including administrative or finalization jobs.

A saturated queue is a failed or cancelled validation outcome, not permission to omit a check. Recovery must retain the correct event revision and current-attempt evidence. Deploying additional schedulers, generating synthetic passing checks or changing required-check policy is not part of this change.

## Proof and limits

`make ci-selection-check` checks the actual workflow inventory, slot range, all six concurrency declarations including the literal workflow-level compatibility lock and absence of variable references, matrix expansion, job names, triggers and absence of checkout revision overrides. It retains the package/test coverage checks and executes the real validation shell against success and non-success family results. Mutations demonstrate refusal of missing or out-of-range lanes, extra jobs/dimensions, cancellation, incorrect queue mode, changed names or revision overrides.

The bounded event-driven model derives all twenty-seven jobs and their slots from the workflow. It assumes immediate runner availability and FIFO lane admission, and demonstrates full twenty-slot use by a lone run. Lane-only scenarios explicitly model proposed future interleaving: independent PR/develop overlap, progress on nineteen lanes during a slow tail, overlap of one run's gate with another run's work, and a peak no greater than twenty including non-matrix jobs. Those overlap scenarios are not attributed to the current serialized workflow. Workflow-admission model checks demonstrate literal-lock serialization with old workflows. The separately named proposed-gate model explores immutable already-selected groups across future activation and rollback affecting future group selections while existing lane-bound runs remain safe. Separate counterexamples demonstrate idle capacity from fixed affinity, cancellation of a latest arrival at the hundred-pending-job boundary and failure of the global bound during mixed legacy/new rollout.

The mixed-rollout counterexample admits actual modeled jobs for both runs. Its legacy model preserves the sixteen-shard matrix cap, independent source/qualification/native occupancy, queued-shard refill and validation dependencies, rather than adding a constant runner count.

These are local configuration/model checks, not observed GitHub runner timing or completed operational rollout. Actual hosted overlap, native queue behavior under account contention, exact-revision required-check results and legacy drain/alignment must be verified by the repository owner during rollout. No CI runs are triggered by the model. While the literal workflow lock remains, shared lanes cannot improve cross-run overlap and their collisions can lengthen a single run. Before changing lane assignments, compare job start/end intervals and lane occupancy over representative runs; differing revisions and runner availability do not establish a causal speedup or regression. The lane-bound proof is not an elapsed-time optimization result.
