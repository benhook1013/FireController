# Shared development CI scheduling

## Current compatibility stage

The integrated development workflow retains the literal repository-wide `firecontroller-ci` workflow lock, `queue: max` and `cancel-in-progress: false`. Independent runs remain serialized with existing workflows. This change adds twenty shared job lanes but does not enable interleaving or read a repository activation variable. Enabling overlap requires a reviewed follow-up gate change and operational alignment/drain; changing a variable alone cannot activate this version.

This workflow is not the smaller main-branch workflow. Its expanded inventory contains thirty-one jobs: twenty-three Go race shards, two native smoke jobs, change selection, source/browser checks, packaged qualification, container runtime, validation and trusted-push publication. A full PR runs thirty jobs because it cannot publish. An explicitly selected website-only development push runs six jobs: selector, source, qualification, container, validation and publication. Only race/native are skipped under that existing selection contract. All job names, permissions, steps, event-revision binding, artifact checks and conditional behavior remain unchanged.

Every job acquires one of `firecontroller-ci-slot-0` through `firecontroller-ci-slot-19` with `queue: max` and cancellation disabled. The twenty-three race shards retain their order and use slots 0 through 19, then 0 through 2. Source and validation use slot 2, qualification 3, Windows 4, macOS 5, selector 6, publication 7 and container 8. Matrix parallel limits no longer reserve a separate per-run budget. A full run can occupy twenty lanes after its selector finishes. Validation still waits for all six prerequisite families and retains its executable website-only exception; publication still waits for successful validation and runs only for trusted branch pushes.

Publication previously used `container-publication-${{ github.ref }}`. It now uses the shared slot 7 because a job cannot acquire two Actions concurrency groups. This preserves mutual exclusion between publishers of the same ref and imposes stronger serialization across all publishers and other slot-7 jobs. It can delay publication but does not broaden publication authority, change the tested artifact, create a deployment or require a new credential. The current workflow lock already serializes publication across runs; the stronger lane exclusion matters if interleaving is enabled later.

## Throughput and finite queues

The lane model permits future independent runs to use released lanes during a slow tail. Current workflows remain serialized. Fixed lane affinity is not a work-conserving scheduler: jobs waiting on one occupied lane cannot borrow nineteen idle lanes. Runner platform availability and account capacity shared with FireMUD can further reduce throughput. Repository-local groups neither reserve runners nor impose a combined FireMUD/FireController budget.

GitHub permits one active member and up to one hundred pending members per concurrency group with `queue: max`; further arrivals are cancelled. The current workflow lock can reject additional runs at that limit. With a future interleaving gate, each lane can reject additional jobs, including a latest live revision. One run can contribute several jobs to a lane, so its capacity is not one hundred runs. FIFO follows when a member begins waiting on its group, not workflow dispatch time. There is no supersession policy or automatic overflow recovery. A rejected required check is not a passing result; an owner must rerun the correct current revision after capacity becomes available.

These semantics are documented by [GitHub concurrency guidance](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency). Strict dynamic allocation to any free slot with durable latest-revision admission beyond those limits requires a larger admission/runner service, outside this bounded implementation.

## Port and activation sequence

The main-branch compatibility change and this development port have different inventories and validation contracts. Do not replace the integrated workflow with the smaller main workflow or copy its twenty-two-shard guard. Retain the selector, twenty-third race shard, container and publisher, native artifact handling and website-only qualification rules when resolving merges. Every new job must join a counted lane.

The repository owner must obtain human merges for the intended compatibility changes and align all eligible PR and `main`/`develop` workflow revisions before enabling overlap. Drain all running and queued legacy revisions that lack shared lanes, including historical reruns; a legacy twenty-job run and independently admitted new twenty-job run could otherwise reach forty. The literal compatibility lock prevents that overlap while this source change is reviewed. Publication of this port does not perform the drain, merge or alignment.

A follow-up reviewed gate may retain the old workflow group by default and use a unique run group only when a verified repository setting explicitly enables interleaving. Publish this literal-lock compatibility stage separately. A later activation PR must name the repository operator responsible for verifying the setting and recording its exact observed state before rollout. Until that verification and review are complete, retain the literal lock. Already selected workflow groups are not migrated by a later setting update; lane-bound queued workflows remain safe alongside activated lane-bound workflows, but legacy queued workflows do not. Rolling back a future gate would affect future group selections, not immediately serialize runs already admitted. Keep lane names stable across both workflow versions.

Autonomous preparation can produce this source port, focused tests and a reviewed activation proposal. Human merge, operational drain/alignment, any repository setting mutation and hosted acceptance evidence remain owner-operated steps. No workflow here mutates the setting, generates synthetic checks or relaxes required-check policy.

## Local proof and limits

`make ci-selection-check` verifies the real thirty-one-job inventory, exact names and conditional boundaries, all nine concurrency declarations, literal compatibility lock, explicit matrix slot mapping and absence of revision overrides. Existing development-selector tests execute the real validation shell, including refusal of skipped race/native checks outside the selected website-only development push. Existing package/test slice tests and release/deployment helper checks remain intact.

The bounded scheduler model derives its jobs and lanes from this workflow and respects selector, validation and publication dependencies. It proves single-run twenty-slot use, full PR publication exclusion and the six-job website-only path. Explicitly proposed future interleaving scenarios exercise PR/develop overlap, slow-tail progress on nineteen lanes, selector/validation/publication overlap with another run's tests, and the twenty-job peak including all non-matrix jobs. Tests also cover publisher mutual exclusion, fixed-affinity idle capacity, latest-arrival queue overflow and the legacy/new overlap counterexample. They do not claim interleaving is active in this version.

These are local source/model checks, not observed hosted concurrency, executed publication, deployment proof or operational rollout. Actual GitHub timing, exact-revision required checks, runner contention and safe drain/alignment require separate owner verification. No model triggers CI or publishes containers.
